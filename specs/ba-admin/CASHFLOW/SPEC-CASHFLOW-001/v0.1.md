## 機台金流與場次（實體機台・開發包③，內部，未對客戶開放）

> 📦 **本檔定位**：本檔為實體機台功能的**開發包③（機台金流與場次，純後端）**，自正本 `實體機台_spec_v07.md` 抽錄，**重疊部分如有出入一律以正本為準**。
>
> - **無 proto**：本包無獨立 UI，機台端畫面由機台廠商實作。
> - **相依**：站台列表 v04 的場館設定欄位（`站台列表_spec_v04.md`——額度上限、場次逾時時間、日結時間、核心貨幣；洗分門檻於機台端設定，後台不設）與機台憑證（`創建會員帳號_spec_v01.md`）。
> - **地基**：本包的交易與場次資料模型為開發包④⑤（機台交易紀錄、洗分出金核實／場館日結報表）的地基，**schema 請最先定案**。

### 功能背景

本功能供平台承接「實體遊藝場」型客戶，也就是玩家到現場、坐在實體老虎機前投現金遊玩的經營型態。

**經營架構：**

客戶向平台申請一個機台類型的主站台，可**自行直接經營**（主站台自身即一間場館），也可在主站台底下建立多個子站台、一個子站台對應一間實體遊藝場（凡站台類型為「機台」的站台以下皆稱**場館**）。每間場館內有數台實體老虎機（以下稱**機台**）。

**與線上會員最大的不同：**

線上是一位玩家一個帳號；實體機台則是**一台機台一個帳號，坐在這台機台上的所有玩家共用它**。玩家不需要註冊、不需要登入，走過來投錢就能玩。因此平台**無法辨識個別玩家是誰**，這個前提影響本包許多規則的設計，閱讀時請特別留意。

**現場運作大致如下：**

1. 玩家投入紙鈔，或請店員（現場稱 Operator）收現金後幫忙加分，機台上的可用餘額（以下稱**分數**）增加
2. 玩家開始遊玩，輸贏即時反映在分數上
3. 玩家要離開時有兩種取回方式：
   - 請店員操作**洗分**，店員當場付現金
   - 自行按下前台遊戲畫面上的**結算**鍵（廠商 API 文件稱 CASHOUT），機台印出一張**收據**，玩家持收據到櫃檯兌現

-----

### 名詞對照（本包金流相關）

| 名詞 | 說明 |
| ---- | ---- |
| 開分 | 店員向玩家收取現金後，在機台上為玩家增加分數 |
| 洗分 | 店員在機台上扣除分數，並當場付現金給玩家 |
| 入金 | 玩家投入紙鈔，機台自動增加分數 |
| 出金 | 玩家按下結算鍵，扣除分數並由機台印出收據 |
| 分數 | 機台當下的可用餘額，等同線上會員的「帳戶餘額（主錢包）」 |
| 收據 | 出金時印出的兌現憑證，玩家持收據至櫃檯換現金 |
| 場次 | 機台的連續遊玩區間，作為前台注單顯示的隔離單位；洗分、出金或分數歸 0 即切換（見「場次」小節） |

### 機台帳號的稽核

流水稽核是少數**不排除**的既有機制（機台帳號沿用會員資料，多數會員機制被排除，排除規則詳見正本；稽核照常適用）。機台的開分與入金比照既有的出金設定（見帳務管理），依幣種設定稽核倍數，產生的稽核異動照常寫入稽核明細。

| 項目 | 規則 |
| ---- | ---- |
| 設定位置 | 帳務管理 \> 出金設定，於 TWD 頁籤設定稽核倍數 |
| 預設值 | **0 倍**——即開分與入金不產生稽核門檻，玩家隨時可洗分與出金 |
| 計入的交易 | 機台開分、機台入金 |
| 稽核明細 | 兩種交易照常寫入，類型顯示為「機台開分」「機台入金」 |
| 倍數大於 0 時 | 洗分與出金的核可金額須扣除尚未完成稽核的部分；扣除後為 0 時視同餘額不足，機台畫面顯示餘額不足 |

> ⚠️ **預設 0 倍是刻意的。** 實體現場的玩家隨時會離台，若設了稽核倍數而玩家未達標，當場就洗不出錢，必然引發爭議；且共用帳號的稽核會跨玩家累積，前一位未達標的門檻會卡到下一位。調高倍數前務必評估現場衝擊。

> 📌 **未來活動需求——開分招待（v07 定案：本次不實作）**：客戶回覆（2026-08-21）機台**目前不需要**稽核（維持預設 0 倍），但實務上存在「開分招待」活動——例如開 2,000 分、送 1,000 分，綁打滿 6,000 有效流水才能洗分／結算。此活動**無法以本節的稽核倍數實現**：倍數是幣種層級設定，一設就綁全場館所有開分與入金，而招待只綁特定一筆；且「送分」為無現金流的交易，四種金流中尚無此類型（日結報表的現金淨收也不能把它當一般開分計算）。屆時須另案設計（新交易類型＋單筆流水鎖定），本節現行規格不受影響。

### 四種金流

機台上的分數增減共有四種來源，皆對應現場的實際動作。理解這四種的差異，是看懂交易紀錄與日結報表的前提。

| 金流 | 誰操作 | 現金流向 | 分數變化 | 現場憑據 |
| ---- | ----- | ------- | ------- | ------- |
| 開分 | 店員（需鑰匙） | 玩家 → 店員 | 增加 | 無 |
| 入金 | 玩家自行投鈔 | 玩家 → 機台錢箱 | 增加 | 無 |
| 洗分 | 店員（需鑰匙） | 店員 → 玩家 | 減少 | 無 |
| 出金 | 玩家按畫面上的結算鍵 | 無（憑收據事後兌現） | 減少 | 收據 |

#### 開分

店員以鑰匙開啟機台選單、選擇金額，機台向平台請求後立即生效。玩家的現金是**交給店員本人**，不經過機台，也不經過平台金流。

  - 交易紀錄的類型記為「機台開分」，金額為正值
  - 交易完成（分數入帳）當下直接累計進該機台帳號於會員列表的「存款次數」「存款金額」（不需核實；2026-09-04 定案）
  - 若加上這筆會使**全場館機台分數餘額合計**超過場館額度上限（額度為全場館共用，見正本「場館設定」／`站台列表_spec_v04.md`），平台會拒絕，機台畫面顯示失敗，分數不變
  - 開分收取的現金由店員現場保管，**平台不介入這筆現金的結算**。平台帳務上只呈現為分數增加，場館與客戶之間的現金結算與分潤一律走雙方的分潤合約，以「場館日結報表」作為對帳依據
  - ⚠️ **機台顯示失敗時，先查後台交易紀錄再決定是否重做。** 若平台其實已經開分成功、只是回覆沒回到機台，直接重按會**重複加分**（店員只收了一次現金），且事後從交易紀錄分不出是誤按重做還是店員真的開了兩次同額——機台不會自動重送，重複加分只會出在這種人為重按（見「業務規則」單階段交易防重複）

#### 入金

玩家把紙鈔投入機台，紙鈔機辨識後向平台請求。**紙鈔確實捲入錢箱之後，分數才會增加**——這是為了避免紙鈔卡住或退回卻已經加了分。

  - 交易紀錄的類型記為「機台入金」，金額為正值
  - 交易完成（分數入帳）當下直接累計進該機台帳號於會員列表的「存款次數」「存款金額」（不需核實；2026-09-04 定案）
  - 若加上這筆會使全場館機台分數餘額合計超過場館額度上限，平台會拒絕，機台直接把紙鈔退回。**額度的判定與預留都在請求階段**（v07 定案）：紙鈔投入、平台收到請求當下即以**場館為單位加鎖**判定，通過就把該筆金額**預留**起來（佔用額度直到入帳、逾時或被取消），下一筆請求看到的已用額度已含前一筆。因此超額會在**紙鈔捲入錢箱之前**就被擋下、機台直接退鈔，**不會出現「錢已進錢箱才發現超額」的情況**；入帳階段不再判定額度
  - 從投入紙鈔到分數入帳完成之前，機台不會再接受新的紙鈔
  - 這段期間若平台一直沒有回應，機台會重複回報直到成功為止，即使中途斷電重開機也會繼續。**後台只會記錄一筆，不會重複加分**

⚠️ **「投了錢卻沒加分」怎麼處理**

這是現場最常見的客訴。依後台「機台交易紀錄」查該機台最近的入金：

| 查到的狀況 | 代表什麼 | 處理方式 |
| ------- | ------ | ---- |
| 查無紀錄 | 紙鈔無法辨識，機台直接退回，平台完全不知情 | 紙鈔應已退出，請玩家確認退鈔口 |
| 未成立 | 平台拒絕（多為超過額度上限） | 機台會退鈔，依「未成立原因」向玩家說明 |
| 待確認 | 平台已受理，但機台沒回報收鈔完成——**通常是紙鈔機故障，紙鈔可能卡在機台內** | 現場開機檢查紙鈔位置。該筆待確認 24 小時後自動轉「已逾時」，分數不會增加；**若確認紙鈔已進錢箱、玩家卻沒拿到分數，由櫃檯以人工入金補上** |
| 已完成 | 分數已入帳 | 請玩家重新整理畫面確認餘額 |

⚠️ 人工入金補分**之前**，務必先確認該筆待確認已被取消或已逾時，否則機台稍後補送回報時會再加一次分。

#### 洗分

店員以鑰匙開啟機台選單，選擇「全洗」或指定金額，機台向平台請求後立即扣除分數，店員當場付現金給玩家。

**洗分門檻**：門檻於**機台端設定**（同場館各機台可不同），機台發送洗分請求時會一併帶上門檻值，**平台即以機台送來的門檻計算**（後台不設門檻、前台不顯示門檻——2026-09-01 定案）。門檻是**取錢的單位**，不是「低於這個數就不能洗」：洗分以門檻為單位計算，**不足一個單位的餘數不付現，繼續留在機台帳號上、不會被清除**；門檻設為 **0** 時表示**洗出全部餘額**、不做取整。實際金額由平台計算，**可能與店員輸入的金額不同**。

> **範例（機台餘額 321）：**
>
> | 操作 | 結果 |
> | ---- | ---- |
> | 門檻 100，全洗 | 洗出 **300** 付現給玩家；餘數 **21 留在機台上**，機台餘額變為 21 |
> | 門檻 100，指定金額洗 300 | 洗出 **300** 付現；餘額 **21 留在機台上**，玩家可繼續遊玩 |
> | 門檻 0，全洗 | 洗出 **321** 全額付現，機台餘額歸 **0**（門檻 0＝洗出全部餘額） |
>
> 門檻 100 的兩種操作此例結果相同；差別在全洗不需輸入金額，一律以當下餘額計算可洗上限。

⚠️ **餘數不會被清除。** 洗分（門檻大於 0 時）只付出以門檻為單位捨去後的核可金額，不足一個門檻單位的餘數**繼續留在機台帳號上**，可繼續遊玩，或待餘額再累積到一個門檻單位以上時洗出。餘數單獨存在時因不足一個計算單位，可洗金額為 0、無法洗出（可改按結算出金全額領回，或待門檻調整）。出金不套門檻、一律清空餘額，不產生餘數（見下節）。

  - 交易紀錄的類型記為「機台洗分」，金額為負值
  - 本筆**不於完成當下**累計進會員列表的「提款次數」「提款金額」，而是於「洗分出金核實」頁核實當下才累計（2026-09-04 定案）
  - **每一筆洗分付現後，都必須到後台「洗分出金核實」頁把該筆紀錄轉為已核實**，用以追蹤現金確實交到玩家手上（見正本「洗分出金核實」小節，即開發包⑤）
  - 計算後可洗金額為 0 時，平台拒絕，機台畫面顯示餘額不足
  - ⚠️ 洗分是一次完成的交易，平台回覆成功即代表分數已扣除，不會自動回復

⚠️ **機台顯示失敗時要怎麼辦**

若平台已扣分、但回覆沒回到機台（斷線、當機），機台畫面會顯示失敗，店員因而沒付錢——**分數其實已經扣掉了**。洗分沒有收據之類的現場憑據，玩家一旦離開就無從證明，因此**一律當場以後台「機台交易紀錄」查明後結清**：

| 後台查到的狀態 | 處理方式 |
| ---- | ---- |
| 已完成 | 分數確實已扣，店員**照該筆金額付現**給玩家 |
| 查無此筆／未成立 | 分數未扣，請店員重新操作一次洗分 |

  - ⚠️ **不要直接重按一次洗分，先查後台確認到底扣了沒。** 多數情況下重按會被擋住——全洗之後餘額為 0（門檻 0）或只剩不足一個門檻單位的餘數，第二次計算後可洗金額為 0，一定回「餘額不足」。但**指定金額洗分、且洗完後餘額仍足夠再洗一次同額時，第二次會成功**（例：餘額 1000 洗 300、剩 700，重按再洗 300），玩家就被扣了兩次卻只拿到一次現金（見「業務規則」單階段交易防重複）
  - 極少數情況（例如現場現金不足、當場付不出來）才由櫃檯以**人工入金**把分數補回機台帳號，屬例外處理

#### 出金

玩家按下前台遊戲畫面上的**結算**鍵（廠商 API 文件稱 CASHOUT，非機櫃上的實體按鈕），平台以按下當下的**全部餘額**為出金金額（出金**一律清空餘額、不套門檻、無餘數**——2026-09-01 廠商定義出金即清空餘額）後，機台印出一張收據。**機台把收據交給印表機（送入列印佇列）之後，分數才會扣除。**

> ⚠️ **過渡期：機台暫無印表機（2026-09-03 廠商告知）。** 以下「印出收據」為印表機到位後的正式流程；印表機到位前，出金依本段規則運作，屆時再調整回收據流程：
>
> - 玩家於前台結算畫面按下**結算**鍵後，由**前台自行完成整筆出金**（向平台請求出金 → 取得核可後依回覆內容**立即**回報完成 → 收到完成回覆），完成後前台顯示**結算結果畫面**，內容比照收據：機台編碼、結算時間、**訂單編號**、結算分數，並提示玩家**拍照留存**。
> - 結算結果畫面即代替收據：玩家持照片到櫃檯，櫃檯依畫面上的**訂單編號**查詢、核對後付現（流程同正本「洗分出金核實」（開發包⑤）的收據核銷，不另設狀態）。玩家未拍照或已離開畫面時，櫃檯可於機台交易紀錄以機台帳號查得該筆出金的訂單編號。
> - **扣分時點＝前台回報完成、平台扣分成功當下**（不再以「送入列印佇列」為準）；場次亦於此時結束。前台在請求出金到回報完成之間**不提供取消**，結算畫面的「取消」鍵僅在送出請求前有效。
> - 平台既有規則不變：請求出金未成功時**分數不扣**，再按一次結算即可，平台留下的待確認出金會被新的一筆取代；請求成功但完成回報未送達時，交易停在「待確認」，由櫃檯查後台交易紀錄後以**人工出金**處理並取消該筆。前台在完成回報失敗時的重送策略**待前台定案**。
> - 過渡期不適用：「印出成功」的定義、印表機異常兩種情況、收據延遲印出。
> - 前台設計稿待確認：結算結果畫面標示的「交易編號」須為櫃檯核銷用的**訂單編號**（或兩者並列）；畫面文案「確認結算前，請先拍照留存」須改為結算已完成的語意（依本流程，畫面顯示時扣分已完成）。

⚠️ **請注意「印出成功」的定義**：機台判定成功的時點是**收據已送入印表機的列印佇列**，不是紙張實際吐出來。因此卡紙、缺紙**不會**讓交易失敗——分數照樣扣除，收據留在佇列裡，等現場排除狀況（補紙、清卡紙）之後會自動印出。玩家可能遇到「分數扣了、收據沒出來」，那張收據晚點仍會吐出，**不可視為未出金而重做一次**。

  - 交易紀錄的類型記為「機台出金」，金額為負值
  - 本筆**不於完成當下**累計進會員列表的「提款次數」「提款金額」，而是於「洗分出金核實」頁核實當下才累計（2026-09-04 定案）
  - **出金一律是全額且清空餘額**，沒有指定金額的選項，也**不套門檻取整**：餘額 321 → 收據面額 **321**，機台餘額歸 **0**
  - 收據面額可能含零頭（不像洗分有門檻取整），櫃檯付現須付至個位數
  - 收據上會印出**訂單編號**，玩家持收據到櫃檯，櫃檯依此編號查詢並付現（見正本「洗分出金核實」小節，即開發包⑤）
  - **印表機異常分兩種情況**：
      - **列印還沒開始就偵測到異常**（含按下結算時印表機即有異常）：機台直接結束流程、不通知平台，**分數不扣、保留在機台上**。平台這邊會留下一筆「待確認」的出金，現場其實什麼也沒發生
      - **已送入列印佇列後才實體故障**（卡紙、缺紙）：如上所述，**分數照扣**，收據待狀況排除後自動印出
  - **按了結算卻沒有任何反應**（收據沒印、畫面也沒提示）：通常是機台暫時連不上平台，機台等不到回覆會自行結束流程——**分數一毛都沒扣**，請玩家或店員**再按一次結算**即可。就算平台端留有前一筆待確認的出金，也會被新的一筆自動取代，不需人工處理
  - 印表機或機台**嚴重損毀、收據確定印不出來**時，由櫃檯執行**人工出金**（無收據出金），並一併取消該機台尚未完成的出金交易
  - 出金過程中玩家仍可繼續投鈔，但這次出金的金額以按下結算鍵當下核算的為準，不會把期間新投入的錢算進去
  - ⚠️ **若櫃檯直接對機台帳號做人工出金，系統會同時取消該機台尚未完成的出金**，避免同一筆錢被領兩次

#### 交易不成立的原因

機台請求被平台拒絕時，交易紀錄會記下原因（餘額不足除外，見下表）。站務人員可依下表判讀：

| 未成立原因 | 說明與處理方向 |
| --------- | ----------- |
| 超過額度上限 | 加上這筆後，**全場館機台分數餘額合計**會超過場館額度上限（額度為全場館共用）。請確認該場館的額度上限是否設得過低，或同場館其他機台的餘額已佔掉大部分額度 |
| 餘額不足 | 洗分時可洗金額為 0（含以門檻捨去後為 0），或出金時餘額為 0。屬正常情形。**不寫入交易紀錄**（2026-09-03 定案）——平台僅回覆機台餘額不足；本表其餘原因才會留下「未成立」紀錄 |
| 查無對應交易 | 機台回報的交易在平台找不到，通常是該筆已由櫃檯人工處理過，或已逾時關閉。屬正常情形，機台會自行結束流程 |
| 機台停用中 | 該機台在後台被設為停用。確認是否為刻意停用 |
| 場館未開通 | 該場館的站台狀態不是「開通」。請檢查站台列表 |
| 憑證失效 | 機台使用的憑證已被重置或無效。須由現場重新寫入新憑證 |
| 資料格式錯誤 | 機台送來的資料有誤，例如幣別與主站台核心貨幣不符。**須通知開發團隊查看** |
| 系統錯誤 | 其他未預期的錯誤。**須通知開發團隊查看** |

### 場次

因為一台機台的所有玩家共用同一個帳號，平台無從辨識現在坐在機台前的是誰。場次的**首要目的是前台顯示的隔離**：機台前台的注單與遊戲紀錄僅顯示**當前進行中場次**的內容——玩家洗分或出金離台，場次隨即切換，下一位玩家不會看到前一位的注單。同時，場次也讓交易、注單與報表有一個明確的歸屬單位。

簡單說：**從機台有分數開始玩起算，到洗分、出金或分數歸 0 為止，算一個場次。**

> ⚠️ **場次不等於玩家。** 場次的切分**寧細勿粗**：玩家中途洗分後繼續玩，會被切成兩個場次（前台看不到自己稍早的注單，屬預期行為）；反之玩家未洗分就棄置餘額離台，接手者在逾時前仍落在同一場次。因此場次**不得**用來判定風控、優惠或分潤，只能用於前台顯示隔離、查詢、對帳，以及現場發生爭議時的追溯。

#### 場次如何開始與結束

| 事件 | 規則 |
| ---- | ---- |
| 開始 | 無進行中場次時，開分或入金完成使分數由 0 轉為有餘額，建立新場次；或前一場次因洗分結束後留有餘數，**立即**建立新場次承接（期初餘額＝餘數；出金一律清空餘額、無餘數承接） |
| 進行中 | 期間所有的開分、入金、洗分、出金與注單，一律歸屬於這個場次；結束場次的那筆洗分／出金交易，歸屬於**被它結束的場次** |
| 洗分／出金結束 | **任一筆洗分或出金交易完成（扣分成功）當下，場次即結束**——不分全洗或指定金額、不論是否留有餘數。洗分為單階段、核可即完成；出金以第二階段扣分完成為準；交易被取消或未成立不觸發；**不等核實**（核實僅是付現核銷）。留有餘數時由新場次立即承接（僅洗分可能留餘數；出金一律清空餘額） |
| 歸零結束 | 分數因投注輸完歸 0 時結束 |
| 逾時結束 | 分數還有餘額，但超過場館設定的「場次逾時時間」沒有任何交易與遊玩紀錄時，自動結束並標記為「逾時結束」；之後若再有交易，會建立新場次 |
| 日結結算 | 場館日結時間到達時，所有進行中的場次一律結束並標記為「日結結算」，剩餘分數轉為隔日新場次的期初餘額 |
| 併發 | 一台機台同時間只會有一個進行中的場次 |

> 正常離台動線（洗分或出金）當下就會切換場次，不依賴逾時；逾時規則主要處理玩家**未洗分就棄置餘額離台**的情況。逾時時間長度於**場館設定**調整（見 `站台列表_spec_v04.md`），**預設 1 小時**。設得越短，棄置情境下場次切得越細、下一位玩家越不容易看到前一位的注單；但同一位玩家中途離座稍久就會被切成兩個場次。設得越長則相反。

#### 場次資訊

| 欄位 | 說明 |
| ---- | ---- |
| 場次編號 | 系統產生的唯一識別碼 |
| 場館／機台 | 該場次所屬的場館與機台帳號（會員編號） |
| 場次狀態 | 進行中 / 已結束 / 逾時結束 / 日結結算 |
| 開始時間 / 結束時間 | UTC+0；進行中的場次結束時間顯示「—」 |
| 場次時長 | 開始至結束的時間差；進行中則顯示累計至查詢當下 |
| 期初餘額 | 場次開始時的分數（開分／入金起始者為 0；承接洗分餘數或日結結算轉入者為承接金額） |
| 開分 / 入金金額 | 期間各自的總額 |
| 洗分 / 出金金額 | 期間各自的總額 |
| 投注筆數 | 期間產生的注單數 |
| 有效投注額 | 期間的有效投注總額 |
| 損益 | 期間的投注損益；正值綠色、負值紅色 |
| 期末餘額 | 場次結束時的分數（歸零結束與出金結束為 0；洗分結束留有餘數時為該餘數） |

場次不另設獨立頁面，於下列位置呈現：

  - **機台前台：** 注單與遊戲紀錄僅顯示當前進行中場次的內容；無進行中場次時為空
  - **會員詳細頁「機台資訊」區塊：** 顯示該機台目前進行中的場次摘要（見 `創建會員帳號_spec_v01.md`）
  - **機台交易紀錄：** 可依場次編號篩選，列表顯示所屬場次（見開發包④）
  - **場館日結報表：** 統計維度可選「依場次明細」（見開發包⑤）

### 業務規則與驗證（本包相關）

| 項目 | 規則 |
| ---- | ---- |
| 幣別一致性 | 機台送來的幣別與主站台核心貨幣不符時，拒絕交易並記為「資料格式錯誤」 |
| 稽核倍數 | 開分與入金依出金設定的幣種稽核倍數計算，機台預設 0 倍；倍數大於 0 時，洗分與出金的核可金額須先扣除未完成稽核的部分 |
| 額度上限 | **場館層級設定，該場館所有機台帳號共用同一份額度**（機台不個別調整）；開分與入金加計後，**全場館機台分數餘額合計**超過上限時拒絕；設為 0 代表不限制。入金的判定與**額度預留**於**請求階段**（`req-cashin`）在**場館鎖**內逐筆序列化執行，判定基準含已預留未入帳的入金金額，`end-cashin` 不再判定；預留於入帳、逾時或手動取消時釋放（v07 定案）；開分為單階段，判定即入帳，亦於同一場館鎖內執行 |
| 門檻的意義 | 門檻是**洗分**的計算單位，不是最低可洗金額。洗分核可金額一律以門檻為單位無條件捨去；不足一個單位的餘數不付現，**繼續留在機台帳號上，不會被清除**。門檻為 **0** 時表示洗出全部餘額、不做取整。**出金不套門檻**——一律清空餘額全額出金 |
| 洗分門檻採用值 | 洗分**一律以機台隨請求送上的 `throshold` 為準**參與計算（2026-09-01 定案）——門檻於**機台端設定**，同場館各機台可設定不同值；廠商保證每筆洗分請求**必帶** `throshold`，值為**正值或 0、不會為負**（2026-09-01 廠商回覆）。**後台不實作門檻設定**（站台列表 v04 已移除「洗分／出金最低門檻」欄位）、**前台不顯示門檻**（機台畫面顯示機台端設定值，可洗金額以平台回覆的核可金額為準）。出金請求不帶門檻參數、一律清空餘額，與門檻無關 |
| 餘數保留 | 洗分（門檻大於 0 時）僅扣除核可金額，不足一個門檻單位的餘數**留在機台帳號上**；系統不另記交易、不清空餘額。餘數單獨存在時可洗金額為 0、無法洗出，須待餘額再累積（或按結算出金全額領回）。出金一律清空餘額，**不產生餘數** |
| 入金交易併存 | 同一台機台可同時有多筆尚未完成的入金；新的入金不會取消舊的 |
| 出金交易唯一 | 同一台機台同時只能有一筆尚未完成的出金；玩家再次按下結算鍵時，舊的自動取消 |
| 重複回報 | 機台重複回報同一筆交易時，分數只異動一次，不會重複加減（入金與出金以交易編號辨識） |
| 單階段交易防重複 | ⚠️ 開分與洗分為單階段交易，請求**不帶唯一識別碼**，且機台**不會自動重送**（廠商回覆 2026-08-19）——**平台把每一筆開分／洗分請求一律當作新交易處理**，重複交易不會在無人操作下自行發生，僅可能來自現場人員重新操作。機台顯示失敗時，現場一律**先查後台交易紀錄**再決定是否重做。**開分無任何自然防護**——只要不超過額度上限，重按幾次就加幾次，是最高風險項；**洗分多半會被擋住**（全洗後餘額為 0 或只剩不足一個門檻單位的餘數，第二次計算後可洗金額為 0，必回餘額不足），僅「指定金額洗分且洗完餘額仍足夠再洗一次同額」時會重複扣款。曾向機台廠商爭取於請求中加入唯一識別碼，**廠商回覆 API 已上線、暫無法更動參數欄位（2026-08-19）**——本條的現場 SOP 即為正式因應方式（見 repo 根目錄「機台廠商確認事項」文件） |
| 人工出金連動 | 櫃檯對機台帳號人工出金時，必須同時取消該機台尚未完成的出金 |
| 會員列表累計欄位 | **存款次數／存款金額**累計機台開分與機台入金——兩者不需核實，於交易完成（分數入帳）當下**直接累計**；**提款次數／提款金額**累計機台洗分與機台出金——於「洗分出金核實」頁**核實當下**累計，待核實與已作廢不計。金額一律以站台核心貨幣原值累計（機台場館即 TWD），不換算 USDT。對照線上會員：系統出金於出金審核按「通過」當下累計、機台於核實當下累計；**人工入金與人工出金一律不計入**（線上與機台帳號皆同，例如櫃檯以人工出金結清待確認出金、或以人工入金補分，都不進這四個欄位）（2026-09-04 定案） |
| 人工入金 | 櫃檯對機台帳號人工入金時，不需處理尚未完成的入金 |
| 交易保留期限 | **入金**：尚未完成的交易超過 24 小時自動轉為「已逾時」。**出金：不設逾時**，待確認保留至完成、被新出金取代、人工出金連動取消或 Admin 手動取消為止 |
| 場次唯一性 | 一台機台同時只能有一個進行中的場次 |
| 場次切分 | 無進行中場次時由開分／入金使分數由 0 轉正建立；**任一筆洗分或出金交易完成當下即結束當前場次**（不分全洗或指定金額、不等核實），留有餘數則立即開立新場次承接（期初餘額＝餘數；僅洗分可能留餘數，出金一律清空餘額）；分數歸 0 亦結束場次 |
| 場次欄位於線上帳號 | 與線上會員共用的頁面（交易紀錄查詢、注單查詢等）所帶的場次編號欄位，線上帳號沒有場次，一律顯示「—」（2026-09-03 定案） |
| 場次逾時 | 逾時時間取自場館設定，預設 1 小時；期間內有任何交易或注單即重新起算 |
| 場次歸屬 | 場次期間的所有交易與注單一律歸屬於該場次（結束場次的洗分／出金交易歸屬於被它結束的場次）；場次不得作為風控、優惠或分潤的判定依據 |
| 前台顯示隔離 | 機台前台的注單與遊戲紀錄僅顯示當前進行中場次的內容；前一場次的紀錄一律不顯示 |
| 場次日結 | 日結時間到達時強制結束所有進行中的場次，餘額轉為隔日新場次的期初餘額 |
| 機台停用 | 停用中的機台無法運作；不影響餘額與尚未完成的交易 |
| 場館站台狀態 | 場館站台（含自行經營的機台主站台）不是「開通」狀態時，該場館所有機台一律無法運作 |
| 時區 | 後台所有時間欄位一律顯示為 UTC+0 |

#### API 一覽

所有 API 均為 `POST`、`Content-Type: application/json`、`Authorization: Bearer <token>`（token 為平台簽發的 **JWT** 機台憑證——2026-09-03 定案；驗證除簽章外須比對該機台現行有效的憑證識別，重置後舊 token 一律拒絕；不設有效期限（v07 定案），僅靠重置使舊憑證失效），`dateTime` 一律為 UTC。

| 主文用語 | API | 階段 | 帳務生效時點 |
| ------- | --- | ---- | --------- |
| 開分 | `req-keyin` | 單階段 | 立即 |
| 洗分 | `req-keyout` | 單階段 | 立即 |
| 入金 | `req-cashin` → `end-cashin` | 兩階段 | 第二階段 |
| 出金 | `req-cashout` → `end-cashout` | 兩階段 | 第二階段 |

| 平台 | Central |

#### 狀態碼對照

平台一律以 `status` 表達業務結果，不以 HTTP 狀態碼表達。

| 狀態碼 | 主文的「未成立原因」 | 平台判定條件 |
| ----- | ---------------- | --------- |
| `0-OK` | （成立） | 正常受理 |
| `1-OVER LIMIT` | 超過額度上限 | 本次金額加計後，全場館機台分數餘額合計將超過場館額度上限（額度為全場館共用） |
| `1-NO CREDITS` | 餘額不足 | 洗分可洗金額為 0（含以門檻捨去後為 0），或出金時餘額為 0。**不寫入交易紀錄**，僅回覆本碼（2026-09-03 定案） |
| `1-NO RECORD` | 查無對應交易 | 查無對應 PENDING，或 TXID 不符 |
| `2-OCCUPIED` | （不啟用） | 平台不回此碼。廠商文件在四支第一階段 API 均將此碼標註為 `(reserved)`，其情境為「已被網頁玩家占用」；機台帳號的前台登入僅供機台本身的遊戲畫面使用（帳密不交付玩家，見正本「機台帳號」／`創建會員帳號_spec_v01.md`），平台不把前台登入狀態當作機台交易的阻擋條件，不啟用此碼 |
| `6-BAD DATA/FORMAT` | 資料格式錯誤 | 欄位缺漏、型別錯誤、`currency` 與主站台核心貨幣不符、金額為負 |
| `7-OUT OF SERVICE` | 機台停用中 / 場館未開通 | 機台為停用狀態、場館站台非「開通」，或平台維護中 |
| `9-OTHER ERROR` | 憑證失效 / 系統錯誤 | Token 無效或已重置、機台帳號不存在，或其他未預期錯誤 |

#### 入金（`req-cashin` → `end-cashin`）

  - 收到 `req-cashin` 一律建立新的 PENDING 並產生唯一 TXID，**不使既有 PENDING 失效**；同一帳號可同時存在多筆有效入金 PENDING
  - **額度上限於本階段判定並預留**（v07 定案）：先取得**場館鎖**（額度為全場館共用），在鎖內以「當下全場館機台分數餘額合計 ＋ **已預留未入帳的入金金額** ＋ 本筆金額」判定；未超限才建立 PENDING、把本筆金額計入預留、釋放鎖，超限則回 `1-OVER LIMIT`、不建立 PENDING、不預留。入金因此逐筆序列化，多筆 PENDING 各自通過檢查、合計卻超額的路徑由此堵住
  - **預留額度的釋放**（v07 定案）：入帳成功時預留轉為實際分數餘額；PENDING 逾時（24 小時）由排程關閉時釋放；Admin／站長於交易紀錄手動取消該筆待確認入金時立即釋放。⚠️ 預留與釋放必須成對，漏掉任一條路徑都會讓額度被永久佔用
  - 收到 `end-cashin` 且 TXID 相符時，關閉 PENDING、更新帳務、把預留轉為實際餘額，回 `0-OK`。**本階段不再判定額度上限**——額度已於 `req-cashin` 判定並預留，紙鈔不會在超額的情況下被收進錢箱
  - 收到 `end-cashin` 但查無 PENDING 或 TXID 不符時，僅記錄 log 後丟棄，回 `1-NO RECORD`，不變更任何資料
  - 機台端 15 秒未收到成功回覆即重送 `end-cashin`，且跨 power cycle 續送。平台**必須具備冪等性**：相同 TXID 第二次以後收到時，若該 PENDING 已完成，直接回 `0-OK` 且不重複加值
  - 櫃檯人工入金**不需**使既有入金 PENDING 失效

#### 出金（`req-cashout` → `end-cashout`）

  - **同一帳號同時只允許一筆有效出金 PENDING**；收到 `req-cashout` 時若已有既存 PENDING，必須先標記失效再建立新的
  - `order_id` 由平台產生，一筆出金一組，全系統唯一，印於收據上，並作為櫃檯核銷時的查詢鍵（經廠商確認為流水號；廠商文件 v1.2 歷程誤寫為「營運商代號」）。格式須為**人工可朗讀、可輸入的短碼**——核銷靠櫃檯人工鍵入，不依賴廠商收據的列印長度限制
  - 核可金額 ＝ `req-cashout` 當下的**全部餘額**（**清空餘額、不套門檻**——2026-09-01 廠商定義出金即清空餘額）。`req-cashout` 的請求**不帶 `throshold` 欄位**，其金額參數必定是機台當前顯示的全部餘額
  - 出金完成後機台餘額為 **0**，**不產生餘數**（餘數僅洗分門檻取整時可能發生）
  - **`end-cashout` 扣分完成當下當前場次即結束**，餘額歸 0、無餘數承接（見「場次」小節）；交易被取代或取消不觸發場次結束
  - 核可金額為 0 時回 `1-NO CREDITS`，不建立 PENDING、不寫入交易紀錄
  - 收到 `end-cashout` 但查無 PENDING 或 TXID 不符時，僅記錄 log 後丟棄，回 `1-NO RECORD`
  - 同樣須對相同 TXID 的重複 `end-cashout` 具備冪等性
  - **櫃檯人工出金時必須一併使既有出金 PENDING 失效**；之後機台送來的 `end-cashout` 會因查無對應 PENDING 而自動結束流程
  - 核可金額以 `req-cashout` 當下為準，不受流程期間的入金影響
  - **機台端的「列印成功」判定為「已完整輸出至系統 printing queue」**，非實際出紙；後續卡紙、缺紙由 queue 保證狀況排除後補印，機台仍會送出 `end-cashout`。平台不需、也無法得知實體出紙結果
  - **第一階段有 15 秒逾時**：機台送出 `req-cashout` 後 15 秒未收到回覆即直接結束程序（收據不印）。但平台此時已建立 PENDING，該筆將永遠等不到 `end-cashout`，須由新的 `req-cashout` 取代或 Admin 手動取消收斂
  - 機台在「列印尚未開始」時偵測到印表機異常會**直接結束流程且不發出任何 API**（文件流程圖 case 1：do nothing），平台端表現同上
  - **過渡期（機台暫無印表機，2026-09-03 廠商告知）**：`req-cashout`／`end-cashout` 改由**前台**依序呼叫——按結算鍵送 `req-cashout`，收到回覆後依回覆內容立即送 `end-cashout`，收到第二次回覆後顯示結算結果畫面（含 `order_id`）供玩家拍照，照片代替收據。平台端規則不變：PENDING 建立／取代、`end-cashout` 冪等、扣分於 `end-cashout` 完成時、場次於此時結束。待確認：前台呼叫的認證方式（是否沿用機台憑證）、`req-cashout` 成功後 `end-cashout` 失敗時前台的重送策略；前台無法補送時交易停在 PENDING，依既有人工出金連動取消處理。印表機到位後回歸機台呼叫流程
  - 廠商文件另定：中央確實無法回覆第二階段成功回覆時，現場 Operator 須至機台選單執行 **Reset**。Reset 後機台停止重送，平台端的 PENDING 只能由 Admin 手動取消

#### 開分（`req-keyin`）

單階段，判定後立即更新帳務；判定與入帳於**場館鎖**內執行，與入金的預留共用同一把鎖而序列化，判定基準須含**已預留未入帳的入金金額**（v07 定案）。超過額度上限回 `1-OVER LIMIT`，不寫入任何帳務異動。

  - 機台送出請求後**不會自動重送**（廠商回覆 2026-08-19）；請求不帶唯一識別碼，平台**把每一筆請求都當作新交易受理**，不做也無從做冪等判斷

#### 洗分（`req-keyout`）

  - 同開分：機台**不會自動重送**，**每一筆請求都當作新交易受理**
  - 請求帶 `mode`（`value` 指定金額／`all` 全洗）與 `throshold`（機台端設定的門檻值）
  - **平台計算一律採請求中的 `throshold`**（2026-09-01 定案；後台不設門檻）。廠商保證每筆洗分請求**必帶** `throshold`，值為**正值或 0、不會為負**；`throshold=0` 表示**洗出當前全部餘額**（餘額以平台帳上為準）、不做取整。規格外的值（負值、缺漏、非數值）屬廠商保證外情形，防禦性處理：拒絕該筆、回 `6-BAD DATA/FORMAT`，不寫入任何帳務異動
  - 回覆的 `value` 為平台核可金額，可能與請求金額不同
  - 計算規則：核可金額 ＝ 餘額以門檻為單位無條件捨去。例：門檻 100、餘額 321 → 核可 300；門檻 0、餘額 321 → 核可 321（全額）
  - `mode=all` 時亦僅扣除核可的 300，餘數 21 **繼續留在帳號上**，平台不另記交易、不清空餘額。廠商 API 的回覆只有單一 `value` 欄位，機台端看到核可的 300，扣除後機台與平台餘額一致
  - `mode=value` 時請求金額須不大於可洗金額，否則以可洗金額為準核可；**餘額不清空**，剩下的分數留在機台上
  - 核可金額為 0 時回 `1-NO CREDITS`，不寫入任何帳務異動與交易紀錄
  - 單階段，回 `0-OK` 即已完成扣款，無回滾機制；**完成當下當前場次即結束**，餘數由新場次承接（見「場次」小節）
  - 稽核倍數大於 0 時，可洗金額須先扣除尚未完成稽核的部分再套用門檻計算；扣除後為 0 時回 `1-NO CREDITS`（機台預設 0 倍，不會觸發）

#### PENDING 保留期限

API 文件僅定義機台端行為：第二階段每 15 秒未收到成功回覆即重送，直到成功為止，跨 power cycle 續送；但收到 `1-NO RECORD`、`6-BAD DATA/FORMAT` 這類邏輯錯誤時直接結束流程，不再重送。文件**未定義平台端何時可判定死單**。

平台端規則如下：

  - **入金 PENDING 保留 24 小時**，逾期自動轉「已逾時」；之後再收到 `end-cashin` 一律回 `1-NO RECORD`，機台停止重送，流程收斂。逾時是「現場已人工補分、卻未先取消待確認」情境的自動保險絲——沒有它，機台修復後遲到的重送會使該筆 PENDING 正常完成而**重複加分**
  - **出金 PENDING 不設逾時**，保留至完成、被新的 `req-cashout` 取代、人工出金連動取消或 Admin 手動取消為止。出金的遲到 `end-cashout` 只是補扣分數，不會使玩家多領；重複領錢由核實紀錄「已核實」阻擋與人工出金的連動取消防範，與保留期限無關。且收據不設兌現時效、永久有效，對應交易不應先於收據關閉。死單（如機台報廢）由 Admin 手動取消清理——機台報廢僅停用不刪除，遺留的未完成交易即以此路徑收斂

#### 主文的交易狀態與 PENDING 的對應

| 主文狀態 | 對應 |
| ------- | ---- |
| 待確認 | PENDING 存在，尚未收到第二階段 |
| 已完成 | PENDING 已 completed |
| 已取消 | PENDING 被標記失效（新請求或人工出金覆蓋） |
| 已逾時 | 入金 PENDING 超過 24 小時自動關閉（僅入金；出金不設逾時） |
| 未成立 | 第一階段即被拒絕，未建立 PENDING（入金的額度上限於 `req-cashin` 判定，入帳階段不再判定） |

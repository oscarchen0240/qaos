### 功能說明

本功能供平台承接「實體遊藝場」型客戶，也就是玩家到現場、坐在實體老虎機前投現金遊玩的經營型態。

**經營架構：**

客戶向平台申請一個主站台，在主站台底下建立多個子站台，一個子站台對應一間實體遊藝場（以下稱**場館**）。每間場館內有數台實體老虎機（以下稱**機台**）。

**與線上會員最大的不同：**

線上是一位玩家一個帳號；實體機台則是**一台機台一個帳號，坐在這台機台上的所有玩家共用它**。玩家不需要註冊、不需要登入，走過來投錢就能玩。因此平台**無法辨識個別玩家是誰**，這個前提影響本章許多規則的設計，閱讀時請特別留意。

**現場運作大致如下：**

1. 玩家投入紙鈔，或請店員（現場稱 Operator）收現金後幫忙加分，機台上的可用餘額（以下稱**分數**）增加
2. 玩家開始遊玩，輸贏即時反映在分數上
3. 玩家要離開時有兩種取回方式：
   - 請店員操作**洗分**，店員當場付現金
   - 自行按下前台遊戲畫面上的**結算**鍵（廠商 API 文件稱 CASHOUT），機台印出一張**收據**，玩家持收據到櫃檯兌現

**後台負責的部分：**

  - **場館管理（站台列表）：** 把子站台的站台類型標記為「機台」，設定該場館的額度上限、日結時間等（洗分門檻於**機台端**設定，後台不設）
  - **建立機台（會員列表）：** 以「創建會員帳號」按鈕、帳號類型選「機台」建立機台帳號與機台資料；登入帳號與密碼不論帳號類型一律由系統自動生成（可用於前台登入），機台憑證另於該帳號的會員詳細頁面生成
  - **機台管理（會員列表／詳細頁）：** 機台不設獨立管理頁，查詢用會員列表（帳號類型「機台」），編輯與停用／啟用於會員詳細頁「機台資訊」區塊（額度上限為**場館層級**設定，機台不個別調整；洗分門檻於**機台端**設定，後台不設）
  - **交易查詢（交易紀錄查詢）：** 查詢所有機台的每一筆金錢進出，包含尚未完成的交易
  - **洗分出金核實（帳務管理）：** 洗分或出金完成時自動產生一筆**待核實**紀錄；現金交到玩家手上後，店員在此把該筆轉為**已核實**。出金的紀錄帶收據訂單編號，櫃檯憑收據核實即為核銷
  - **場館日結（各式報表）：** 每日結算各場館與各機台的現金收支，供平台與場館對帳

### 名詞對照（本功能）

| 名詞 | 說明 |
| ---- | ---- |
| 場館 | 一間實體遊藝場，對應站台列表中一個站台類型為「機台」的**站台**——通常為機台主站台底下的子站台；機台主站台**自行直接經營**時，其自身亦為一間場館。本章「機台場館」泛指所有機台類型站台 |
| 機台 | 場館內的一台實體老虎機，以其機台帳號的會員編號識別，不另設機台編號 |
| 機台帳號 | 機台綁定的平台帳號，該機台的所有玩家共用 |
| 分數 | 機台當下的可用餘額，等同線上會員的「帳戶餘額（主錢包）」 |
| Operator | 場館現場的操作店員，持鑰匙可開啟機台選單執行開分與洗分 |
| 開分 | 店員向玩家收取現金後，在機台上為玩家增加分數 |
| 洗分 | 店員在機台上扣除分數，並當場付現金給玩家 |
| 洗分門檻 | 洗分的**計算單位**，於**機台端設定**（同場館各機台可不同），隨每筆洗分請求送至平台；為 **0** 時表示洗出全部餘額。不足一個單位的餘數不付現，**繼續留在機台帳號上**。後台不設門檻、前台不顯示門檻；出金不套門檻（一律清空餘額） |
| 入金 | 玩家投入紙鈔，機台自動增加分數 |
| 結算鍵 | 機台**前台遊戲畫面上**的出金按鍵（非機櫃上的實體按鈕），廠商 API 文件稱 CASHOUT；位於**遊戲首頁點選錢包後的彈窗**內，遊戲進行中沒有結算入口；玩家按下即發起出金 |
| 出金 | 玩家按下結算鍵，扣除分數並由機台印出收據 |
| 紙鈔機 | 機台上接收與辨識紙鈔的裝置 |
| 收據 | 出金時印出的兌現憑證，玩家持收據至櫃檯換現金 |
| 訂單編號 | 印在收據上的識別碼，櫃檯兌現時以此查詢 |
| 交易編號 | 系統為每筆機台交易產生的唯一編號，供追查使用 |
| 機台憑證 | 機台連線平台所需的身分憑證，一台機台一組；憑證失效機台就無法運作 |
| 場次 | 機台的連續遊玩區間，作為前台注單顯示的隔離單位；洗分、出金或分數歸 0 即切換（見「場次」小節） |

### 機台帳號

機台帳號**沿用現有的會員資料**，在會員紀錄上新增「帳號類型」欄位加以區分，不另外建立一套帳號系統。

| 帳號類型 | 說明 |
| ------- | ---- |
| 線上 | 現行所有前台註冊會員，行為完全不變（預設值）。**前台維持開放以帳號密碼方式自行註冊新帳號**（註冊時強制綁定電子信箱），與後台「創建會員帳號」並行為兩條建立途徑 |
| 機台 | 綁定一台實體機台的共用帳號，由後台建立；系統生成的帳號密碼可登入前台，但**僅供機台本身使用、不交付玩家**（前台註冊產生的一律是線上帳號，與此無關） |

**機台帳號的特性：**

| 項目 | 規則 |
| ---- | ---- |
| 會員編號 | 沿用系統既有的會員編號產生規則 |
| 所屬站台 | 固定為該機台所在的場館子站台 |
| 建立方式 | 由後台建立，不經前台註冊；沒有電子信箱、沒有電話號碼；登入帳號與密碼由系統自動生成（與線上帳號的後台建立**統一**，見「新增機台帳號」） |
| 登入 | 可以系統生成的帳號密碼登入前台，**僅供機台本身的前台遊戲畫面登入使用**——帳密由現場人員設定機台時輸入，不交付玩家 |
| 錢包 | 使用主錢包，即機台上顯示的分數 |
| 幣別 | 取自所屬主站台的核心貨幣，不可修改 |

#### 既有功能對機台帳號的排除規則

由於機台帳號沿用會員資料，若不特別排除，既有的會員相關功能會自動對它生效。下表逐一定義處理方式：

> ⚠️ **排除是現階段的營運決策，不代表未來不會加回來。** 實作時應做成**可逐項解除**的集中規則層（policy），不要把「機台帳號不進某模組」寫死散落在各功能內——Free Spin 已是排除規則的既有例外，未來亦可能逐項恢復適用（例如客戶提及的「開分招待」活動，見「機台帳號的稽核」）。某項排除解除時，後台選單的對應頁面須隨之恢復顯示（見「機台場館的後台選單」）。

| 章節 | 功能 | 機台帳號處理方式 |
| ---- | ---- | ------------- |
| 2.1 | 會員列表 | 照常顯示，不預設排除；篩選器新增「帳號類型」欄位（全部／線上／機台，預設「全部」）供區分查詢，總筆數依篩選結果計算；**提款次數／提款金額累計已核實的機台洗分與機台出金**（於「洗分出金核實」頁核實當下累計，交易完成但待核實不計、已作廢永不計；金額以站台核心貨幣原值累計、不換算 USDT，機台場館即 TWD；2026-09-04 定案；**存款次數／存款金額對稱累計機台開分與機台入金**——開分與入金不需核實，於交易完成（分數入帳）當下直接累計，金額同以核心貨幣原值。對照線上會員：系統出金於出金審核按「通過」當下累計；人工入金／人工出金一律不計入） |
| 2.1.5 | 會員詳細資料頁 | 可開啟，但 KYC、等級、優惠、邀請鏈區塊隱藏 |
| 2.2 | 加盟列表 | 機台帳號不可成為加盟商，也不計入任何加盟商的直推人數 |
| 2.4 | 推薦註冊金 | 不適用，機台帳號沒有邀請人 |
| 3.2 | 出金審核 | **不進入本流程**。機台出金為現場即時核可並印出收據，不需後台審核 |
| 3.3 | 優惠彩金審核 | 不適用 |
| 4.1 | 交易紀錄查詢 | 機台交易一併寫入，交易類型新增四項（見「對既有章節的影響」） |
| 4.2 | 注單查詢 | 機台注單照常寫入，會員編號為機台帳號 |
| 4.3 | 返水明細 | 不適用，機台帳號不產生返水 |
| 4.4 | 稽核明細 | **照常寫入**。開分與入金比照既有的出金設定，可依幣種設定稽核倍數，**機台預設為 0 倍**（等同不設稽核門檻）；詳見下方「機台帳號的稽核」 |
| 4.5 / 4.6 | 加盟傭金／代理返傭 | 不適用，機台帳號的投注不計入任何上層的傭金基數 |
| 4.7 | 會員等級異動 | 不適用，機台帳號固定為最低等級且不升降 |
| 6.1 | KYC 設定 | 不適用，機台帳號五個 KYC 階段一律為「未申請」且無法申請 |
| 6.5 | 優惠活動 | 不適用，機台帳號不參與任何優惠活動與簽到 |
| 6.8 | Free Spin 管理 | **適用，同一般會員**。可將機台帳號指定加入 Free Spin 活動；免費旋轉由後台直接派發、不需玩家領取，共用帳號收得到。幣種依主站台核心貨幣（機台場館即 TWD），見「核心貨幣」 |

#### 為何一定要排除

機台帳號的流水是**整台機台所有玩家的總和**，量級與一位線上玩家完全不同。若沿用會員規則會出現下列問題：

| 功能 | 不排除的後果 |
| ---- | --------- |
| 返水 | 一台機台一天的有效投注是數十位玩家的加總，按會員返水率回饋，利潤會被吃掉 |
| 會員等級 | 流水累積極快，機台帳號短時間內升到最高等級，接著享有最高返水率與提領額度 |
| 加盟傭金／代理返傭 | 機台帳號若掛在某加盟商底下，整間店的流水都會算成他的業績 |
| 優惠活動 | 首儲、次儲、累儲獎勵會被反覆觸發；每日簽到變成一台機台一天領一份 |

#### 為何不以「洗分或出金時歸零」取代排除

曾評估以「每次洗分或出金時把機台帳號的累計統計歸零」取代上述排除，讓一個累計區間約略對應一位玩家的一場遊玩。**經評估不採用**：

| 規則類型 | 適用功能 | 歸零是否有效 |
| ------- | ------- | --------- |
| 按每筆注單計算 | 返水、加盟傭金、代理返傭 | **無效**。此類費用是拿結算期間每一筆注單的有效投注去乘費率，與帳號的累計欄位無關；歸零不會讓已產生的注單消失，整店流水仍會全額計入 |
| 首儲／次儲類 | 優惠活動（首儲、次儲） | **反效果**。歸零後每個區間都算「第一次儲值」，首儲獎勵可以重複領，風險比不歸零更高 |
| 累計達標類 | 累儲獎勵、累計簽到 | 歸零後永遠達不到門檻，實際效果等同排除，但規則語意不清 |
| 按累計值計算 | 會員等級 | 有效，但要額外定義歸零後的降級規則；機台等級會長期停在最低級，結果仍等同排除 |

此外，「洗分或出金 ＝ 換玩家」這個前提並不成立：玩家可能留下少額餘額直接離台由下一位接手，也可能中途出金後繼續玩。因此歸零切出的區間無法對應到單一玩家，不能拿來當風控依據。

⚠️ **場館的利潤分配一律走與場館的分潤合約，以「場館日結報表」對帳，不套用線上玩家的返水與傭金體系。** 這是上述所有排除規則的根本理由。

#### 機台帳號的稽核

流水稽核是少數**不排除**的既有機制。機台的開分與入金比照既有的出金設定（見帳務管理），依幣種設定稽核倍數，產生的稽核異動照常寫入稽核明細。

| 項目 | 規則 |
| ---- | ---- |
| 設定位置 | 帳務管理 \> 出金設定，於 TWD 頁籤設定稽核倍數 |
| 預設值 | **0 倍**——即開分與入金不產生稽核門檻，玩家隨時可洗分與出金 |
| 計入的交易 | 機台開分、機台入金 |
| 稽核明細 | 兩種交易照常寫入，類型顯示為「機台開分」「機台入金」 |
| 倍數大於 0 時 | 洗分與出金的核可金額須扣除尚未完成稽核的部分；扣除後為 0 時視同餘額不足，機台畫面顯示餘額不足 |

> ⚠️ **預設 0 倍是刻意的。** 實體現場的玩家隨時會離台，若設了稽核倍數而玩家未達標，當場就洗不出錢，必然引發爭議；且共用帳號的稽核會跨玩家累積，前一位未達標的門檻會卡到下一位。調高倍數前務必評估現場衝擊。

> 📌 **未來活動需求——開分招待（v07 定案：本次不實作）**：客戶回覆（2026-08-21）機台**目前不需要**稽核（維持預設 0 倍），但實務上存在「開分招待」活動——例如開 2,000 分、送 1,000 分，綁打滿 6,000 有效流水才能洗分／結算。此活動**無法以本節的稽核倍數實現**：倍數是幣種層級設定，一設就綁全場館所有開分與入金，而招待只綁特定一筆；且「送分」為無現金流的交易，四種金流中尚無此類型（日結報表的現金淨收也不能把它當一般開分計算）。屆時須另案設計（新交易類型＋單筆流水鎖定），本節現行規格不受影響。

### 場館設定

場館就是「站台列表」中站台類型為「機台」的站台（場館子站台，或自行直接經營的機台主站台），在原有欄位之外擴充下列設定。**站台列表原有的新增／編輯／刪除／網域／模板操作完全不變**，只是多了幾個欄位。

| 欄位 | 說明 |
| ---- | ---- |
| 站台類型 | 線上 / 機台，二擇一；建立後不可修改。**於主站台（根層）選定，子站台一律與主站台同類型**——機台主站台對應一個實體遊藝場經營者，可**自行直接經營**（自身即一間場館），也可在底下建立場館子站台。**凡機台類型站台皆帶以下機台專屬欄位**；每份設定的作用範圍為**該站台自身、不含子站台**（主站台與各場館各自一份、互不影響） |
| 場館幣別 | **唯讀**，自動顯示所屬主站台的核心貨幣，不可於場館層級變更（見下方「核心貨幣」）。新增／編輯視窗**不另設本欄位**——與核心貨幣為同一個值，由核心貨幣欄的子站台唯讀繼承顯示承載；本欄僅用於檢視情境 |
| 場館地址 | 選填，供對帳與稽核識別 |
| 場館聯絡人／電話 | 選填 |
| 額度上限 | **場館層級設定，該場館底下所有機台帳號共用同一份額度**——開分／入金時以「全場館機台分數餘額合計」檢核，不是每台各有一份上限；機台不個別調整；修改後即時生效，不影響既有餘額 |
| 場次逾時時間 | 機台仍有餘額但無任何交易與遊玩時，自動結束場次的時間長度；**預設 1 小時**，站長可調整，操作員唯讀 |
| 日結時間 | 每日結算的截止時刻（UTC+0），用於場館日結報表分日 |

> ⚠️ **洗分門檻不在後台設定**（2026-09-01 定案，v06 起移除原「洗分／出金最低門檻」欄位）：門檻於**機台端設定**、隨每筆洗分請求送至平台（同場館各機台可不同）；出金一律清空餘額、不套門檻。詳見「業務規則」洗分門檻採用值。

#### 核心貨幣

幣別**不在場館層級設定，而是主站台層級的設定**：一個主站台一種核心貨幣，其底下所有子站台一律沿用，不可各自指定。核心貨幣的**可選清單依站台類型過濾**：目前線上主站台＝**USDT**、機台主站台＝**TWD**，各僅一種、等同自動帶入（2026-08-21 客戶定案）；⚠️ 實作不得寫死幣別——清單須可擴充，未來增加幣種只擴充清單、不改邏輯。實體遊藝場客戶的主站台核心貨幣即 **TWD**，該主站台下所有場館與機台一律以 TWD 計價與記帳。

**主站台建立後，核心貨幣不可修改**（v07 定案）：比照「站台類型」，於建立時選定即永久鎖定，編輯視窗唯讀顯示；要換幣別只能另建主站台。既有餘額、注單與報表的幣別語意不會中途改變。

因此本功能不涉及匯率換算，也沒有 USDT 與現金並存的問題：收據面額、交易紀錄金額、日結報表金額全部是同一種貨幣。

> ⚠️ 「核心貨幣」是站台層級的通用設定，不是實體機台專屬。**站台列表 spec 須新增主站台的「核心貨幣」欄位與子站台繼承規則**（見「對既有章節的影響」），本章僅沿用。

#### 機台場館的遊戲更新

實體機台出廠前須送**法規審核**，審核通過後機台內的遊戲不得任意更動。因此機台場館的遊戲上架規則與線上站台不同：

| 項目 | 規則 |
| ---- | ---- |
| 預設停用 | 平台**新增**任何遊戲、或對既有遊戲發佈**更新**後，該遊戲在所有機台場館一律**預設為停用**——包含更新前原已啟用的遊戲（更新視同內容變動，須重新決定是否開放） |
| 通知義務 | 平台於新增或更新後，由**營運窗口**通知站長與場館，由他們自行決定是否開放；採人工通知，**不做系統內通知功能** |
| 開啟方式 | 由**站長**自行於 遊戲商管理 啟用該遊戲；**操作員不可操作**；平台不代為開啟 |
| 適用範圍 | 僅站台類型「機台」的場館；線上站台維持既有行為，不受本規則影響 |

### 機台管理

**功能路徑：** 會員與加盟商 \> 會員列表（帳號類型篩「機台」）；單一機台的管理位於該機台帳號 會員詳細頁 的「機台資訊」區塊

#### 功能說明

機台**不設獨立管理頁**——機台帳號照常列於會員列表，查機台就用會員列表既有的篩選（帳號類型選「機台」、所屬站台選場館、會員編號即機台帳號、餘額即分數）；單一機台的檢視與管理集中在該帳號的**會員詳細頁**，詳細頁新增「**機台資訊**」區塊（機台憑證另為獨立區塊，見下方「機台憑證」）。額度上限為**場館層級**設定（見「場館設定」），不於個別機台調整；洗分門檻於**機台端**設定，後台不設（見「業務規則」）。

#### 機台資訊區塊

| 欄位 | 說明 |
| ---- | ---- |
| 機台名稱 | 即該帳號的「暱稱」欄位（與線上會員同一欄位）；供後台辨識，例如「A 區 03 號」；可修改，修改即更新該帳號的暱稱 |
| 所屬場館 | 場館名稱與站台代碼；唯讀，可點擊回到站台列表該層 |
| 機台狀態 | 啟用 / 停用，Badge 色標呈現 |
| 進行中場次 | 該機台目前進行中的場次摘要（見「場次」）；無進行中場次時顯示「—」 |
| 時間紀錄 | 機台資料的建立時間、修改時間（UTC+0），不開放編輯 |

分數餘額即該帳號的主錢包餘額（詳細頁原有欄位）、未完成的交易於機台交易紀錄查詢，均不在本區塊重複呈現。

#### 操作

**新增機台帳號**

入口在 **會員與加盟商 \> 會員列表**：點擊「**創建會員帳號**」按鈕開啟 Modal，**帳號類型選「機台」**時帶出下列機台欄位（機台帳號沿用會員模型，故由會員列表進入建立，別無其他新增入口）。**帳號一律建立於目前所在的站台底下**（機台主站台自行經營時，機台帳號即建立於主站台自身之下），不提供跨站台指定——機台帳號的所屬場館即目前所在的機台場館，Modal **不設「所屬場館」欄位**（「目前站台」即後台各頁皆有的**站台切換下拉選單**所選站台：選單列出操作者有權限的站台，頁面內容一律以其為範圍，故會員列表也不需「所屬站台」欄位）。**登入帳號與密碼不需輸入——線上與機台兩種帳號類型統一由系統自動生成，且皆可用於前台登入**：

| 欄位名稱 | 必填 | 說明 |
| ------- | ---- | ---- |
| 帳號類型 | 必填 | 線上／機台；**預設值依目前站台的「站台類型」帶入**——機台場館預設「機台」、線上站台預設「線上」。「機台」選項**僅於目前站台為機台場館時可選**（線上站台下停用——機台帳號必屬某一機台場館，而帳號只會建立在目前站台底下）。選「機台」時帶出以下欄位 |
| 機台名稱 | 選填 | **即該會員帳號的「暱稱」欄位**——與線上會員的暱稱為同一欄位，不另設機台專屬欄位（2026-09-03 定案），會員列表照常顯示於會員編號下方。供後台辨識，例如「A 區 03 號」。機台不另設機台編號，識別碼即本次建立的會員編號。後台建立／修改不經「暱稱禁用詞」檢查（該檢查僅作用於前台設定暱稱，機台場館亦不顯示該設定頁）|
| 機台狀態 | 不顯示 | 預設建立為「**啟用**」——憑證未寫入機台前機台本來就無法連線，不需先停用再手動啟用；如需暫停於會員詳細頁「機台資訊」區塊停用 |

**帳號類型選「線上」時不帶額外欄位**：建立一名所屬目前站台的線上會員（電子信箱與電話留空），建立後的行為與前台註冊會員完全相同。後台創建並非線上會員唯一的建立途徑——**前台仍開放玩家以帳號密碼方式自行註冊新帳號**，兩條途徑並行：前台註冊的帳號密碼由玩家於註冊時自訂、不經系統生成，且**註冊時強制綁定電子信箱**；密碼遺失可自行走前台「忘記密碼」機制（見下方「前台忘記密碼」），後台亦可於會員詳細頁「重設密碼」代為處理（見下方「重設密碼」），兩者並行。

額度上限不在此設定——一律套用**所屬場館的場館設定值**；洗分門檻於機台端設定，後台無此設定。

點擊「建立」後，系統建立帳號（餘額為 0，即本次創建的會員帳號）；帳號類型「機台」同時建立機台資料，一個帳號只對應一台機台。建立成功畫面**完整顯示一次**系統生成的登入帳號與密碼，並提供複製按鈕；關閉後不再完整顯示（比照機台憑證的一次性顯示規則），密碼遺失以「重設密碼」處理（見下方）。**憑證不隨建立產生**——於該帳號的會員詳細頁面生成（見下方「機台憑證」）。

> 📖 **機台帳號的帳密用途**：機台的**前台遊戲畫面**即以此帳密登入平台（結算鍵與錢包彈窗都在這個畫面上），由現場人員設定機台時輸入，**不交付玩家**。機台憑證則供機台主控程式與平台 API 通訊，兩者各自獨立、互不影響（見「機台憑證」）。

**編輯機台**

於「機台資訊」區塊點擊「編輯」：

| 欄位名稱 | 可否修改 | 說明 |
| ------- | ------- | ---- |
| 所屬場館 | 不可 | 唯讀；如需搬移須停用本機台後另建新機台帳號 |
| 機台名稱 | 可 | 即會員暱稱，修改即更新該帳號的暱稱 |
| 機台狀態 | 可 | 啟用 / 停用 |

機台與帳號的綁定不可更換（一對一，見「業務規則」）。點擊「儲存變更」後，修改時間自動更新。

**重設密碼**

後台建立的帳號，系統生成的密碼僅於建立成功時完整顯示一次，之後無法查看。會員密碼遺失或外洩時（不論帳號由後台建立或前台註冊），於該帳號的**會員詳細頁**點擊「重設密碼」，二次確認後系統生成新密碼，**連同登入帳號一併完整顯示一次**（各附複製按鈕；現場人員須以成對的帳號密碼重新登入，僅顯示密碼不足以操作），舊密碼立即失效。

  - 適用對象：**所有會員帳號**——後台建立與前台註冊、線上與機台皆適用。前台註冊會員另可自行走前台「忘記密碼」機制（見下方），兩者並行——會員自己忘記密碼走前台，找上客服或站務時由後台代為重設
  - ⚠️ **機台帳號重設密碼後，機台的前台遊戲畫面將無法再以舊密碼登入**，須由現場人員以新帳密重新登入機台——比照重置憑證，非必要不要重設，重設前先與現場確認

**前台忘記密碼（線上會員）**

> 📖 本項為**前台功能**，超出後台手冊的原有範圍；因帳號建立與密碼規則已於本章定義，一併在此定案供前台開發引用。

前台登入頁提供「忘記密碼」入口，流程如下：

1. 會員輸入**帳號與綁定的電子信箱**
2. 兩者相符時，系統寄送**重設密碼連結**至該信箱；連結具時效（**預設 1 小時**），逾時失效須重新申請，重新申請會使先前尚未使用的連結失效
3. 會員點擊連結設定新密碼，完成後**舊密碼立即失效**

| 項目 | 規則 |
| ---- | ---- |
| 適用對象 | 已綁定電子信箱的線上會員，不論由前台註冊或後台建立 |
| 不提示帳號存在 | 查無帳號或信箱不符時，前台一律顯示「若資料相符，重設連結已寄出」，不提示帳號是否存在，避免被用於探測帳號 |
| 機台帳號 | 不適用——機台帳號沒有電子信箱，帳密由後台管理，遺失一律走後台「重設密碼」 |
| 未綁定信箱的帳號 | 無法使用本機制，一律以後台「重設密碼」處理。**前台註冊強制綁定電子信箱**，故未綁定信箱的帳號只會是後台建立者（建立時信箱留空且尚未補綁） |
| 與後台重設密碼的關係 | 兩者獨立、互不影響；後台「重設密碼」適用所有會員帳號（含前台註冊），本機制供已綁定信箱的會員自行操作，兩者並行 |

**機台憑證**

機台憑證是機台連線平台的身分證明，由後台產生後寫入機台。**生成與管理位於該機台帳號的「會員詳細頁面」**——機台帳號的詳細頁多一個「機台憑證」區塊，提供「產生憑證」與「重置憑證」：

  - 憑證內容**只在產生與重置時完整顯示一次**，並提供複製按鈕；之後只顯示前後各 4 碼，中間以遮罩呈現
  - 一台機台同時只有一組有效憑證
  - 點擊「重置憑證」須二次確認；確認後舊憑證立即失效
  - 區塊內顯示憑證建立時間與最後使用時間；尚未產生憑證時顯示「產生憑證」按鈕
  - 憑證格式為 **JWT（JSON Web Token）**（2026-09-03 定案），由平台簽發、機台每次呼叫平台 API 時附帶。字串長達數百字元，一次性顯示畫面須提供複製按鈕並允許換行完整顯示；遮罩顯示沿用前後各 4 碼
  - **重置即失效由平台端保證**：JWT 本身無法被收回，平台驗證憑證時除簽章外須比對該機台目前有效的憑證識別（如 jti 或憑證版本號），舊憑證即使簽章仍有效亦一律拒絕
  - 憑證**不設有效期限**（v07 定案）：設期限就必須定義到期前的換發流程，現場逐台重寫憑證的成本過高；憑證一經簽發長期有效，**僅靠「重置憑證」使舊憑證失效**

> 📖 **機台憑證與登入帳密是兩回事**：憑證供機台主控程式（Kernel）與平台 API 通訊；帳密供機台的前台遊戲畫面登入。重置憑證不影響帳密，重設密碼也不影響憑證。

> ⚠️ 重置憑證會讓機台**立即無法運作**，必須由現場人員把新憑證寫入機台後才會恢復。非必要不要重置，重置前請先與現場確認。

**停用／啟用機台**

於「機台資訊」區塊操作（或編輯時切換機台狀態）。停用後該機台立即無法運作，玩家無法投鈔、遊玩或出金；再次啟用即恢復運作。停用**不會**影響機台帳號上的餘額，也不會取消尚未完成的交易。

機台**不提供刪除操作**，只能停用：

  - 機台報廢或不再使用時，一律以**停用**處理；機台資料與機台帳號都會保留，供歷史紀錄查詢
  - 停用前建議先結清餘額並清理未完成的交易（死單由 Admin 於交易紀錄查詢手動取消，見「機台交易紀錄」）

### 四種金流

機台上的分數增減共有四種來源，皆對應現場的實際動作。理解這四種的差異，是看懂交易紀錄與日結報表的前提。

| 金流 | 誰操作 | 現金流向 | 分數變化 | 現場憑據 |
| ---- | ----- | ------- | ------- | ------- |
| 開分 | 店員（需鑰匙） | 玩家 → 店員 | 增加 | 無 |
| 入金 | 玩家自行投鈔 | 玩家 → 機台錢箱 | 增加 | 無 |
| 洗分 | 店員（需鑰匙） | 店員 → 玩家 | 減少 | 無 |
| 出金 | 玩家按畫面上的結算鍵 | 無（憑收據事後兌現） | 減少 | 收據 |

#### 開分

店員以鑰匙開啟機台選單、選擇金額，機台向平台請求後立即生效。玩家的現金是**交給店員本人**，不經過機台，也不經過平台金流。

  - 交易紀錄的類型記為「機台開分」，金額為正值
  - 交易完成（分數入帳）當下直接累計進該機台帳號於會員列表的「存款次數」「存款金額」（不需核實；2026-09-04 定案）
  - 若加上這筆會使**全場館機台分數餘額合計**超過場館額度上限（額度為全場館共用，見「場館設定」），平台會拒絕，機台畫面顯示失敗，分數不變
  - 開分收取的現金由店員現場保管，**平台不介入這筆現金的結算**。平台帳務上只呈現為分數增加，場館與客戶之間的現金結算與分潤一律走雙方的分潤合約，以「場館日結報表」作為對帳依據
  - ⚠️ **機台顯示失敗時，先查後台交易紀錄再決定是否重做。** 若平台其實已經開分成功、只是回覆沒回到機台，直接重按會**重複加分**（店員只收了一次現金），且事後從交易紀錄分不出是誤按重做還是店員真的開了兩次同額——機台不會自動重送，重複加分只會出在這種人為重按（見「業務規則」單階段交易防重複）

#### 入金

玩家把紙鈔投入機台，紙鈔機辨識後向平台請求。**紙鈔確實捲入錢箱之後，分數才會增加**——這是為了避免紙鈔卡住或退回卻已經加了分。

  - 交易紀錄的類型記為「機台入金」，金額為正值
  - 交易完成（分數入帳）當下直接累計進該機台帳號於會員列表的「存款次數」「存款金額」（不需核實；2026-09-04 定案）
  - 若加上這筆會使全場館機台分數餘額合計超過場館額度上限，平台會拒絕，機台直接把紙鈔退回。**額度的判定與預留都在請求階段**（v07 定案）：紙鈔投入、平台收到請求當下即以**場館為單位加鎖**判定，通過就把該筆金額**預留**起來（佔用額度直到入帳、逾時或被取消），下一筆請求看到的已用額度已含前一筆。因此超額會在**紙鈔捲入錢箱之前**就被擋下、機台直接退鈔，**不會出現「錢已進錢箱才發現超額」的情況**；入帳階段不再判定額度
  - 從投入紙鈔到分數入帳完成之前，機台不會再接受新的紙鈔
  - 這段期間若平台一直沒有回應，機台會重複回報直到成功為止，即使中途斷電重開機也會繼續。**後台只會記錄一筆，不會重複加分**

⚠️ **「投了錢卻沒加分」怎麼處理**

這是現場最常見的客訴。依後台「機台交易紀錄」查該機台最近的入金：

| 查到的狀況 | 代表什麼 | 處理方式 |
| ------- | ------ | ---- |
| 查無紀錄 | 紙鈔無法辨識，機台直接退回，平台完全不知情 | 紙鈔應已退出，請玩家確認退鈔口 |
| 未成立 | 平台拒絕（多為超過額度上限） | 機台會退鈔，依「未成立原因」向玩家說明 |
| 待確認 | 平台已受理，但機台沒回報收鈔完成——**通常是紙鈔機故障，紙鈔可能卡在機台內** | 現場開機檢查紙鈔位置。該筆待確認 24 小時後自動轉「已逾時」，分數不會增加；**若確認紙鈔已進錢箱、玩家卻沒拿到分數，由櫃檯以人工入金補上** |
| 已完成 | 分數已入帳 | 請玩家重新整理畫面確認餘額 |

⚠️ 人工入金補分**之前**，務必先確認該筆待確認已被取消或已逾時，否則機台稍後補送回報時會再加一次分。

#### 洗分

店員以鑰匙開啟機台選單，選擇「全洗」或指定金額，機台向平台請求後立即扣除分數，店員當場付現金給玩家。

**洗分門檻**：門檻於**機台端設定**（同場館各機台可不同），機台發送洗分請求時會一併帶上門檻值，**平台即以機台送來的門檻計算**（後台不設門檻、前台不顯示門檻——2026-09-01 定案）。門檻是**取錢的單位**，不是「低於這個數就不能洗」：洗分以門檻為單位計算，**不足一個單位的餘數不付現，繼續留在機台帳號上、不會被清除**；門檻設為 **0** 時表示**洗出全部餘額**、不做取整。實際金額由平台計算，**可能與店員輸入的金額不同**。

> **範例（機台餘額 321）：**
>
> | 操作 | 結果 |
> | ---- | ---- |
> | 門檻 100，全洗 | 洗出 **300** 付現給玩家；餘數 **21 留在機台上**，機台餘額變為 21 |
> | 門檻 100，指定金額洗 300 | 洗出 **300** 付現；餘額 **21 留在機台上**，玩家可繼續遊玩 |
> | 門檻 0，全洗 | 洗出 **321** 全額付現，機台餘額歸 **0**（門檻 0＝洗出全部餘額） |
>
> 門檻 100 的兩種操作此例結果相同；差別在全洗不需輸入金額，一律以當下餘額計算可洗上限。

⚠️ **餘數不會被清除。** 洗分（門檻大於 0 時）只付出以門檻為單位捨去後的核可金額，不足一個門檻單位的餘數**繼續留在機台帳號上**，可繼續遊玩，或待餘額再累積到一個門檻單位以上時洗出。餘數單獨存在時因不足一個計算單位，可洗金額為 0、無法洗出（可改按結算出金全額領回，或待門檻調整）。出金不套門檻、一律清空餘額，不產生餘數（見下節）。

  - 交易紀錄的類型記為「機台洗分」，金額為負值
  - 本筆**不於完成當下**累計進會員列表的「提款次數」「提款金額」，而是於「洗分出金核實」頁核實當下才累計（2026-09-04 定案）
  - **每一筆洗分付現後，都必須到後台「洗分出金核實」頁把該筆紀錄轉為已核實**，用以追蹤現金確實交到玩家手上（見「洗分出金核實」小節）
  - 計算後可洗金額為 0 時，平台拒絕，機台畫面顯示餘額不足
  - ⚠️ 洗分是一次完成的交易，平台回覆成功即代表分數已扣除，不會自動回復

⚠️ **機台顯示失敗時要怎麼辦**

若平台已扣分、但回覆沒回到機台（斷線、當機），機台畫面會顯示失敗，店員因而沒付錢——**分數其實已經扣掉了**。洗分沒有收據之類的現場憑據，玩家一旦離開就無從證明，因此**一律當場以後台「機台交易紀錄」查明後結清**：

| 後台查到的狀態 | 處理方式 |
| ---- | ---- |
| 已完成 | 分數確實已扣，店員**照該筆金額付現**給玩家 |
| 查無此筆／未成立 | 分數未扣，請店員重新操作一次洗分 |

  - ⚠️ **不要直接重按一次洗分，先查後台確認到底扣了沒。** 多數情況下重按會被擋住——全洗之後餘額為 0（門檻 0）或只剩不足一個門檻單位的餘數，第二次計算後可洗金額為 0，一定回「餘額不足」。但**指定金額洗分、且洗完後餘額仍足夠再洗一次同額時，第二次會成功**（例：餘額 1000 洗 300、剩 700，重按再洗 300），玩家就被扣了兩次卻只拿到一次現金（見「業務規則」單階段交易防重複）
  - 極少數情況（例如現場現金不足、當場付不出來）才由櫃檯以**人工入金**把分數補回機台帳號，屬例外處理

#### 出金

玩家按下前台遊戲畫面上的**結算**鍵（廠商 API 文件稱 CASHOUT，非機櫃上的實體按鈕），平台以按下當下的**全部餘額**為出金金額（出金**一律清空餘額、不套門檻、無餘數**——2026-09-01 廠商定義出金即清空餘額）後，機台印出一張收據。**機台把收據交給印表機（送入列印佇列）之後，分數才會扣除。**

> ⚠️ **過渡期：機台暫無印表機（2026-09-03 廠商告知）。** 以下「印出收據」為印表機到位後的正式流程；印表機到位前，出金依本段規則運作，屆時再調整回收據流程：
>
> - 玩家於前台結算畫面按下**結算**鍵後，由**前台自行完成整筆出金**（向平台請求出金 → 取得核可後依回覆內容**立即**回報完成 → 收到完成回覆），完成後前台顯示**結算結果畫面**，內容比照收據：機台編碼、結算時間、**訂單編號**、結算分數，並提示玩家**拍照留存**。
> - 結算結果畫面即代替收據：玩家持照片到櫃檯，櫃檯依畫面上的**訂單編號**查詢、核對後付現（流程同「洗分出金核實」的收據核銷，不另設狀態）。玩家未拍照或已離開畫面時，櫃檯可於機台交易紀錄以機台帳號查得該筆出金的訂單編號。
> - **扣分時點＝前台回報完成、平台扣分成功當下**（不再以「送入列印佇列」為準）；場次亦於此時結束。前台在請求出金到回報完成之間**不提供取消**，結算畫面的「取消」鍵僅在送出請求前有效。
> - 平台既有規則不變：請求出金未成功時**分數不扣**，再按一次結算即可，平台留下的待確認出金會被新的一筆取代；請求成功但完成回報未送達時，交易停在「待確認」，由櫃檯查後台交易紀錄後以**人工出金**處理並取消該筆。前台在完成回報失敗時的重送策略**待前台定案**。
> - 過渡期不適用：「印出成功」的定義、印表機異常兩種情況、收據延遲印出。
> - 前台設計稿待確認：結算結果畫面標示的「交易編號」須為櫃檯核銷用的**訂單編號**（或兩者並列）；畫面文案「確認結算前，請先拍照留存」須改為結算已完成的語意（依本流程，畫面顯示時扣分已完成）。

⚠️ **請注意「印出成功」的定義**：機台判定成功的時點是**收據已送入印表機的列印佇列**，不是紙張實際吐出來。因此卡紙、缺紙**不會**讓交易失敗——分數照樣扣除，收據留在佇列裡，等現場排除狀況（補紙、清卡紙）之後會自動印出。玩家可能遇到「分數扣了、收據沒出來」，那張收據晚點仍會吐出，**不可視為未出金而重做一次**。

  - 交易紀錄的類型記為「機台出金」，金額為負值
  - 本筆**不於完成當下**累計進會員列表的「提款次數」「提款金額」，而是於「洗分出金核實」頁核實當下才累計（2026-09-04 定案）
  - **出金一律是全額且清空餘額**，沒有指定金額的選項，也**不套門檻取整**：餘額 321 → 收據面額 **321**，機台餘額歸 **0**
  - 收據面額可能含零頭（不像洗分有門檻取整），櫃檯付現須付至個位數
  - 收據上會印出**訂單編號**，玩家持收據到櫃檯，櫃檯依此編號查詢並付現（見「洗分出金核實」小節）
  - **印表機異常分兩種情況**：
      - **列印還沒開始就偵測到異常**（含按下結算時印表機即有異常）：機台直接結束流程、不通知平台，**分數不扣、保留在機台上**。平台這邊會留下一筆「待確認」的出金，現場其實什麼也沒發生
      - **已送入列印佇列後才實體故障**（卡紙、缺紙）：如上所述，**分數照扣**，收據待狀況排除後自動印出
  - **按了結算卻沒有任何反應**（收據沒印、畫面也沒提示）：通常是機台暫時連不上平台，機台等不到回覆會自行結束流程——**分數一毛都沒扣**，請玩家或店員**再按一次結算**即可。就算平台端留有前一筆待確認的出金，也會被新的一筆自動取代，不需人工處理
  - 印表機或機台**嚴重損毀、收據確定印不出來**時，由櫃檯執行**人工出金**（無收據出金），並一併取消該機台尚未完成的出金交易
  - 出金過程中玩家仍可繼續投鈔，但這次出金的金額以按下結算鍵當下核算的為準，不會把期間新投入的錢算進去
  - ⚠️ **若櫃檯直接對機台帳號做人工出金，系統會同時取消該機台尚未完成的出金**，避免同一筆錢被領兩次

#### 交易不成立的原因

機台請求被平台拒絕時，交易紀錄會記下原因（餘額不足除外，見下表）。站務人員可依下表判讀：

| 未成立原因 | 說明與處理方向 |
| --------- | ----------- |
| 超過額度上限 | 加上這筆後，**全場館機台分數餘額合計**會超過場館額度上限（額度為全場館共用）。請確認該場館的額度上限是否設得過低，或同場館其他機台的餘額已佔掉大部分額度 |
| 餘額不足 | 洗分時可洗金額為 0（含以門檻捨去後為 0），或出金時餘額為 0。屬正常情形。**不寫入交易紀錄**（2026-09-03 定案）——平台僅回覆機台餘額不足；本表其餘原因才會留下「未成立」紀錄 |
| 查無對應交易 | 機台回報的交易在平台找不到，通常是該筆已由櫃檯人工處理過，或已逾時關閉。屬正常情形，機台會自行結束流程 |
| 機台停用中 | 該機台在後台被設為停用。確認是否為刻意停用 |
| 場館未開通 | 該場館的站台狀態不是「開通」。請檢查站台列表 |
| 憑證失效 | 機台使用的憑證已被重置或無效。須由現場重新寫入新憑證 |
| 資料格式錯誤 | 機台送來的資料有誤，例如幣別與主站台核心貨幣不符。**須通知開發團隊查看** |
| 系統錯誤 | 其他未預期的錯誤。**須通知開發團隊查看** |

### 場次

因為一台機台的所有玩家共用同一個帳號，平台無從辨識現在坐在機台前的是誰。場次的**首要目的是前台顯示的隔離**：機台前台的注單與遊戲紀錄僅顯示**當前進行中場次**的內容——玩家洗分或出金離台，場次隨即切換，下一位玩家不會看到前一位的注單。同時，場次也讓交易、注單與報表有一個明確的歸屬單位。

簡單說：**從機台有分數開始玩起算，到洗分、出金或分數歸 0 為止，算一個場次。**

> ⚠️ **場次不等於玩家。** 場次的切分**寧細勿粗**：玩家中途洗分後繼續玩，會被切成兩個場次（前台看不到自己稍早的注單，屬預期行為）；反之玩家未洗分就棄置餘額離台，接手者在逾時前仍落在同一場次。因此場次**不得**用來判定風控、優惠或分潤，只能用於前台顯示隔離、查詢、對帳，以及現場發生爭議時的追溯。

#### 場次如何開始與結束

| 事件 | 規則 |
| ---- | ---- |
| 開始 | 無進行中場次時，開分或入金完成使分數由 0 轉為有餘額，建立新場次；或前一場次因洗分結束後留有餘數，**立即**建立新場次承接（期初餘額＝餘數；出金一律清空餘額、無餘數承接） |
| 進行中 | 期間所有的開分、入金、洗分、出金與注單，一律歸屬於這個場次；結束場次的那筆洗分／出金交易，歸屬於**被它結束的場次** |
| 洗分／出金結束 | **任一筆洗分或出金交易完成（扣分成功）當下，場次即結束**——不分全洗或指定金額、不論是否留有餘數。洗分為單階段、核可即完成；出金以第二階段扣分完成為準；交易被取消或未成立不觸發；**不等核實**（核實僅是付現核銷）。留有餘數時由新場次立即承接（僅洗分可能留餘數；出金一律清空餘額） |
| 歸零結束 | 分數因投注輸完歸 0 時結束 |
| 逾時結束 | 分數還有餘額，但超過場館設定的「場次逾時時間」沒有任何交易與遊玩紀錄時，自動結束並標記為「逾時結束」；之後若再有交易，會建立新場次 |
| 日結結算 | 場館日結時間到達時，所有進行中的場次一律結束並標記為「日結結算」，剩餘分數轉為隔日新場次的期初餘額 |
| 併發 | 一台機台同時間只會有一個進行中的場次 |

> 正常離台動線（洗分或出金）當下就會切換場次，不依賴逾時；逾時規則主要處理玩家**未洗分就棄置餘額離台**的情況。逾時時間長度於**場館設定**調整，**預設 1 小時**。設得越短，棄置情境下場次切得越細、下一位玩家越不容易看到前一位的注單；但同一位玩家中途離座稍久就會被切成兩個場次。設得越長則相反。

#### 場次資訊

| 欄位 | 說明 |
| ---- | ---- |
| 場次編號 | 系統產生的唯一識別碼 |
| 場館／機台 | 該場次所屬的場館與機台帳號（會員編號） |
| 場次狀態 | 進行中 / 已結束 / 逾時結束 / 日結結算 |
| 開始時間 / 結束時間 | UTC+0；進行中的場次結束時間顯示「—」 |
| 場次時長 | 開始至結束的時間差；進行中則顯示累計至查詢當下 |
| 期初餘額 | 場次開始時的分數（開分／入金起始者為 0；承接洗分餘數或日結結算轉入者為承接金額） |
| 開分 / 入金金額 | 期間各自的總額 |
| 洗分 / 出金金額 | 期間各自的總額 |
| 投注筆數 | 期間產生的注單數 |
| 有效投注額 | 期間的有效投注總額，以主站台核心貨幣計算（機台場館為 TWD） |
| 損益 | 期間的投注損益，以主站台核心貨幣計算；正值綠色、負值紅色 |
| 期末餘額 | 場次結束時的分數（歸零結束與出金結束為 0；洗分結束留有餘數時為該餘數） |

場次不另設獨立頁面，於下列位置呈現：

  - **機台前台：** 注單與遊戲紀錄僅顯示當前進行中場次的內容；無進行中場次時為空
  - **會員詳細頁「機台資訊」區塊：** 顯示該機台目前進行中的場次摘要
  - **機台交易紀錄：** 可依場次編號篩選，列表顯示所屬場次
  - **場館日結報表：** 統計維度可選「依場次明細」

### 機台交易紀錄

**功能路徑：** 併入 各式報表 \> 交易紀錄查詢——**不另設頁面**，本節規格為 `4.1 交易紀錄查詢` 的**機台視角擴充**。

#### 功能說明

查詢所有機台的每一筆金錢進出，**包含尚未完成與被拒絕的交易**。這是現場發生爭議時（例如玩家反映「我投了錢但分數沒加」）的主要查核工具。

既有的 4.1 只顯示已經生效的錢包異動；併入後，查詢範圍含機台交易時**另外顯示尚未完成、被取消與被拒絕的交易**，並提供機台與場次視角的篩選與欄位（即本節以下規格）。非機台交易的既有行為不變。

#### 篩選器

| 篩選欄位 | 類型 | 說明 |
| ------- | ---- | ---- |
| 機台帳號 | 文字輸入 | 輸入會員編號查詢；支援多筆，以「,」分隔 |
| 交易編號 | 文字輸入 | 查詢特定一筆交易 |
| 場次編號 | 文字輸入 | 查詢某個場次內的所有交易 |
| 訂單編號 | 文字輸入 | 出金專用，即收據上印製的編號 |
| 交易類型 | 下拉選單 | 全部 / 機台開分 / 機台洗分 / 機台入金 / 機台出金 |
| 交易狀態 | 下拉選單 | 全部 / 待確認 / 已完成 / 已取消 / 已逾時 / 未成立 |
| 核實狀態 | 下拉選單 | 全部 / 待核實 / 已核實 / 已作廢 / 不適用；僅對「機台洗分」與「機台出金」有意義（核實於「洗分出金核實」頁操作，本頁僅供查詢） |
| 交易時間 | 日期範圍 | 依交易發生時間篩選 |
| 金額 | 範圍輸入（min ～ max） | — |

設定後點擊「搜尋」執行，點擊「清除」重置所有條件。

#### 交易狀態

| 狀態 | 說明 |
| ---- | ---- |
| 待確認 | 交易已受理，但尚未收到機台的完成回報；**分數尚未異動** |
| 已完成 | 交易完成，分數已異動 |
| 已取消 | 出金交易被新的出金請求或櫃檯人工出金取代而作廢；分數未異動 |
| 已逾時 | **僅入金會出現**：超過 24 小時仍未收到機台回報而自動關閉；分數未異動。出金不設逾時，見下方說明 |
| 未成立 | 平台拒絕了這筆請求；分數未異動，原因見「未成立原因」欄（餘額不足不寫入紀錄，故本狀態不含餘額不足） |

> ⚠️ 「待確認」代表交易卡在中間狀態——機台已經動作（例如紙鈔已收、收據已印），但平台還沒收到完成回報。若某台機台長時間累積多筆「待確認」，通常代表該機台網路或設備異常，應通知現場檢查。
>
> 入金與出金的收斂方式不同：**入金**超過 24 小時自動轉「已逾時」；**出金不設逾時**，待確認會一直保留，直到機台補完回報、被新的出金取代、櫃檯人工出金連動取消，或由 Admin 手動取消為止（收據永久有效，對應的交易不先於收據關閉）。

#### 操作

  - **查看明細：** 點擊任一列開啟右側面板，顯示該筆交易的完整往來紀錄。⚠️ 面板下半部為技術欄位，供開發團隊排查用，站務人員以上半部的摘要為準即可
  - **手動取消：** 僅 Admin 可對「待確認」狀態的交易執行；二次確認後標記為「已取消」，分數不異動。用於機台故障造成的卡單清理

> 本頁**不提供核實操作**——洗分與出金的核實一律於 帳務管理 \>「洗分出金核實」執行（見該小節），本頁的核實狀態欄位僅供查帳。

> ⚠️ **手動取消前務必先與現場確認實體狀況**——紙鈔是否已進錢箱、收據是否已印出。取消後平台會告知機台這筆交易不存在，機台就會停止重試；若現場實際上已經收了錢或印了收據，會造成帳實不符。
>
> ⚠️ **收據可能延遲印出**：機台把收據送進列印佇列就視為成功，卡紙或缺紙時收據會等狀況排除後才吐出來（見「出金」）。因此「現場沒看到收據」**不等於**沒印，取消前務必先確認印表機狀態。
>
> ⚠️ **現場若在機台的 Operator 選單執行過 Reset，機台就不會再回報這筆交易**——該待確認會永遠留著，必須由 Admin 手動取消清理。執行 Reset 後請一併通知後台。

### 洗分出金核實

**功能路徑：** 帳務管理 \> 洗分出金核實（與出金審核並列）

#### 功能說明

洗分與出金都是**把現金交給玩家**的交易。每一筆「已完成」的機台洗分或機台出金，系統會自動在本頁產生一筆**待核實**紀錄；現金確實交到玩家手上後，操作人員在本頁把該筆紀錄轉為**已核實**。本頁是**全平台唯一的核實入口**——機台交易紀錄只顯示核實狀態，不提供操作。

兩種交易的現場流程不同，但在本頁做的事相同：

| 交易類型 | 現場流程 | 核實時點 |
| ------- | ------- | ------- |
| 機台洗分 | 店員操作洗分、當場付現，沒有任何憑據 | 付現後**立即**在本頁核實；應付金額以本頁「實際金額」欄為準 |
| 機台出金 | 機台印出收據，玩家持收據到櫃檯兌現 | 櫃檯輸入收據上的**訂單編號**查到該筆，核對後核實並付現——**核實即收據核銷** |

> ⚠️ 機台廠商提供的規格中，出金流程到「收據印出」就結束了，**沒有定義收據要如何兌現與核銷**。本頁的核銷（＝核實）為後台自訂，機台本身不參與。核銷方式採**櫃檯人工輸入訂單編號**，不引入掃碼設備（收據不需印製條碼或 QR Code）。訂單編號由平台產生，**設計為人工可朗讀、可輸入的短碼**，不依賴廠商收據的列印長度限制。

#### 核實狀態

| 狀態 | 色標 | 說明 |
| ---- | ---- | ---- |
| 待核實 | 藍色 | 交易已完成，現金尚未確認交付。**待核實的洗分**以醒目色標提示（現金可能未交付或現場漏登記）；待核實的出金屬正常（收據不設兌現時效，玩家隔幾天才來兌現很常見） |
| 已核實 | 綠色 | 現金已交付並完成登記；出金即「已兌現」。**核實當下**該筆累計進該機台帳號於會員列表的「提款次數」「提款金額」（2026-09-04 定案） |
| 已作廢 | 灰色 | 僅出金：收據經人工作廢，不再兌付 |

#### 紀錄產生規則

  - 僅交易狀態為「已完成」的機台洗分與機台出金會出現在本頁；待確認、已取消、已逾時、未成立的交易**不會出現**。⚠️ 機台畫面顯示失敗、本頁又查無該筆時，代表交易可能沒有完成——請先到「機台交易紀錄」查明狀態再決定付不付錢，**不要憑本頁有沒有紀錄以外的印象判斷**
  - 開分與入金不需核實，不會出現在本頁（兩者都不是付錢給玩家）

| 交易時間 | 日期範圍 | 出金即收據印出時間 |

#### 操作

**核實（洗分）**

店員當場付現後的登記流程：

1. 依機台帳號（會員編號）或交易時間找到該筆待核實洗分，點擊「核實」
2. 確認彈窗顯示機台帳號、實際金額與交易時間，**核對無誤後**點擊確認
3. 系統標記為「已核實」，並記錄核實人員與時間

**核實（出金＝核銷收據）**

玩家持收據到櫃檯時的標準流程：

1. 於頁面上方輸入收據上的訂單編號查詢，或直接在列表點擊「核實」
2. 確認彈窗顯示訂單編號、機台帳號、金額與收據印出時間，**核對無誤後**點擊確認
3. 系統標記為「已核實」，並記錄核實人員與時間
4. 櫃檯付現金給玩家

| 項目 | 規則 |
| ---- | ---- |
| 可核實的狀態 | 僅「待核實」；已核實或已作廢的紀錄再次核實時，系統阻擋並提示，**避免重複付款** |
| 權限 | Admin、站長、操作員皆可執行（操作員限自身場館） |
| 連動 | 核實結果回寫機台交易紀錄的「核實狀態」「核實人員／時間」欄位；並於核實當下把該筆累計進該機台帳號於會員列表的「提款次數」「提款金額」（金額以站台核心貨幣原值累計、不換算 USDT；待核實與已作廢不計） |
| **不可撤銷** | ⚠️ **核實一經確認即無法撤銷**，誤按無法回復，只能透過後台操作紀錄追溯執行人員與時間。因此操作前務必核對彈窗內容 |

**作廢（僅出金）**

  - 僅 Admin 與站長可執行，須填寫作廢原因（必填）；用於收據遺失、爭議或確認不再兌付的情況
  - ⚠️ 作廢後不可復原，分數也不會退回機台

> ⚠️ **核實不等於付錢，是付錢之後的登記。** 現場的正確順序是：交易成功 → 現金交給玩家 → 到本頁核實。

> 洗分長時間停留在「待核實」，代表現金可能還沒交給玩家、或現場忘了登記，場館日結報表會把待核實洗分獨立計算。**出金停在「待核實」則屬正常**——收據不設兌現時效，該金額對應報表的「未兌現金額」。

> 收據**不設兌現時效、不自動作廢**。待核實的出金（未兌現收據）永久有效，一律由人工判斷後以「作廢」處理。因此日結報表的「未兌現金額」會長期累積，該金額代表場館端尚未付出的負債。

### 場館日結報表

**功能路徑：** 各式報表 \> 場館日結報表

#### 功能說明

結算各場館與各機台的現金收支，供平台與場館對帳、分潤。營業日的切分依場館設定的「日結時間」；除逐日檢視外，可依週、月或自訂區間彙總計算。

#### 篩選器

| 篩選欄位 | 類型 | 說明 |
| ------- | ---- | ---- |
| 機台帳號 | 文字輸入 | 輸入會員編號；留空為場館全部機台 |
| 結算日期 | 日期範圍 | 必填；不設區間上限，與手冊其他報表一致 |
| 統計週期 | 下拉選單 | 按日（預設）／按週／按月／區間合計。按週以週一為週起；非按日時，每列為該週期內各營業日的彙總 |
| 統計維度 | 下拉選單 | 依場館彙總 / 依機台明細 / 依場次明細；「依場次明細」時統計週期僅決定查詢範圍，列表仍逐場次列出、不彙總 |

#### 列表欄位

| 欄位 | 說明 |
| ---- | ---- |
| 結算期間 | 按日顯示營業日（依場館日結時間切分）；按週／按月／區間合計顯示該週期的起訖日期 |
| 場館／機台 | 依統計維度顯示至場館、機台或場次層級 |
| 場次編號 | 僅「依場次明細」維度顯示；另附開始／結束時間與場次時長 |
| 場次數 | 「依場館彙總」與「依機台明細」維度顯示，為當日結束的場次筆數：依機台明細＝該機台帳號當日的場次數；依場館彙總＝**該場館底下所有機台帳號當日場次數的加總**（2026-09-03 定案） |
| 開分金額 | 當日開分總額（店員現場收現） |
| 洗分金額 | 當日洗分總額（店員現場付現） |
| 已核實洗分 | 當日洗分中已在「洗分出金核實」頁核實的金額合計 |
| 待核實洗分 | 當日洗分中仍為待核實的金額合計；不為 0 時標示提醒，代表現金可能未交付或現場漏登記 |
| 進鈔金額 | 當日入金總額（紙鈔機收現） |
| 收據金額 | 當日出金總額（印出的收據面額合計） |
| 已兌現金額 | 當日已核實（核銷）的收據金額合計 |
| 未兌現金額 | 截至查詢當下仍為待核實的收據金額合計 |
| 現金淨收 | 開分 ＋ 進鈔 － **已核實洗分** － 已兌現（**不扣待核實洗分**——尚未確認付出） |
| 有效投注額 | 當日該場館／機台的投注總額，以主站台核心貨幣計算（機台場館為 TWD；2026-09-03 定案） |
| 損益 | 當日投注損益，以主站台核心貨幣計算；正值綠色、負值紅色 |
| 期末餘額 | 該日結算時點各機台的分數合計 |

列表底部顯示當前篩選結果的各欄總計。頁面右上角提供「匯出 CSV」。

> 欄位說明以「當日」敘述；統計週期非按日時，各金額與筆數欄為**該週期內各營業日的合計**，「期末餘額」取該週期**最後一個營業日**結算時點的值，「未兌現金額」不受週期影響、一律為截至查詢當下的累計。

> ⚠️ 「現金淨收」是**推算值**，代表場館端當日現金應該增減多少，尚未兌現的收據不算在內（那是未來要付出去的錢）。與現場實際點鈔金額的差異須由人工查核。

| 建立站台歸屬 | 「創建會員帳號」建立的帳號一律歸屬**操作當下所在的站台**（＝頁面站台切換下拉選單所選站台，後台各頁皆有、列出操作者有權限的站台），不提供跨站台指定（Modal 不設「所屬場館」欄位）；機台帳號的所屬場館即目前所在的機台場館（含自行經營的機台主站台），「機台」選項僅於機台場館可選，建立後所屬站台不可修改 |
| 帳號密碼生成 | 「創建會員帳號」不論帳號類型（線上／機台），登入帳號與密碼一律由系統自動生成、**可用於前台登入**；建立成功時完整顯示一次並提供複製，之後不再完整顯示 |
| 前台自行註冊 | **線上站台**的前台維持開放以帳號密碼方式自行註冊，僅產生線上帳號；帳號密碼由玩家於註冊時自訂、不經系統生成，**註冊時強制綁定電子信箱**；密碼遺失走前台「忘記密碼」（不適用本章後台「重設密碼」）。**機台場館的前台暫不開放自行註冊**（未來營運需求、開放時程未定） |
| 前台忘記密碼 | 已綁定電子信箱的線上會員可於前台申請重設：寄送具時效的重設連結（預設 1 小時，重新申請使舊連結失效），完成後舊密碼立即失效；查無帳號或信箱不符時前台不提示帳號是否存在。機台帳號與未綁定信箱的後台建立帳號不適用，一律走後台「重設密碼」 |
| 機台帳號登入 | 機台帳號的帳密僅供機台本身的前台遊戲畫面登入使用，由現場人員設定機台時輸入，**不交付玩家** |
| 重設密碼 | **所有會員帳號**（後台建立與前台註冊、線上與機台）皆可於會員詳細頁重設密碼，新密碼**連同登入帳號**僅於重設當下完整顯示一次，舊密碼立即失效；機台帳號重設後須由現場以新帳密重新登入機台。重設密碼與機台憑證互不影響 |
| 幣別一致性 | 機台送來的幣別與主站台核心貨幣不符時，拒絕交易並記為「資料格式錯誤」 |
| 稽核倍數 | 開分與入金依出金設定的幣種稽核倍數計算，機台預設 0 倍；倍數大於 0 時，洗分與出金的核可金額須先扣除未完成稽核的部分 |
| 額度上限 | **場館層級設定，該場館所有機台帳號共用同一份額度**（機台不個別調整）；開分與入金加計後，**全場館機台分數餘額合計**超過上限時拒絕；設為 0 代表不限制。入金的判定與**額度預留**於**請求階段**（`req-cashin`）在**場館鎖**內逐筆序列化執行，判定基準含已預留未入帳的入金金額，`end-cashin` 不再判定；預留於入帳、逾時或手動取消時釋放（v07 定案）；開分為單階段，判定即入帳，亦於同一場館鎖內執行 |
| 門檻的意義 | 門檻是**洗分**的計算單位，不是最低可洗金額。洗分核可金額一律以門檻為單位無條件捨去；不足一個單位的餘數不付現，**繼續留在機台帳號上，不會被清除**。門檻為 **0** 時表示洗出全部餘額、不做取整。**出金不套門檻**——一律清空餘額全額出金 |
| 洗分門檻採用值 | 洗分**一律以機台隨請求送上的 `throshold` 為準**參與計算（2026-09-01 定案）——門檻於**機台端設定**，同場館各機台可設定不同值；廠商保證每筆洗分請求**必帶** `throshold`，值為**正值或 0、不會為負**（2026-09-01 廠商回覆）。**後台不實作門檻設定**（站台列表 v04 已移除「洗分／出金最低門檻」欄位）、**前台不顯示門檻**（機台畫面顯示機台端設定值，可洗金額以平台回覆的核可金額為準）。出金請求不帶門檻參數、一律清空餘額，與門檻無關 |
| 餘數保留 | 洗分（門檻大於 0 時）僅扣除核可金額，不足一個門檻單位的餘數**留在機台帳號上**；系統不另記交易、不清空餘額。餘數單獨存在時可洗金額為 0、無法洗出，須待餘額再累積（或按結算出金全額領回）。出金一律清空餘額，**不產生餘數** |
| 交易核實 | 洗分與出金完成時，系統自動於「洗分出金核實」頁產生一筆**待核實**紀錄；現金交付後於該頁轉為已核實（出金的核實即收據核銷），**機台交易紀錄不提供核實操作**。僅「已完成」的交易產生核實紀錄，已核實者不可重複核實。核實與否**不影響分數與交易狀態**；**核實當下**該筆累計進會員列表的「提款次數」「提款金額」（金額以站台核心貨幣原值累計、不換算 USDT；待核實與已作廢不計；2026-09-04 定案），此外僅供對帳與稽核 |
| 會員列表累計欄位 | **存款次數／存款金額**累計機台開分與機台入金——兩者不需核實，於交易完成（分數入帳）當下**直接累計**；**提款次數／提款金額**累計機台洗分與機台出金——於「洗分出金核實」頁**核實當下**累計，待核實與已作廢不計。金額一律以站台核心貨幣原值累計（機台場館即 TWD），不換算 USDT。對照線上會員：系統出金於出金審核按「通過」當下累計、機台於核實當下累計；**人工入金與人工出金一律不計入**（線上與機台帳號皆同，例如櫃檯以人工出金結清待確認出金、或以人工入金補分，都不進這四個欄位）（2026-09-04 定案） |
| 核實不可撤銷 | ⚠️ 核實與作廢**一經確認皆無法撤銷**，誤操作無法回復，僅能透過後台操作紀錄追溯執行人員與時間 |
| 現金淨收計算 | 只計入**已核實**的洗分；待核實洗分不扣除 |
| 憑證唯一性 | 一台機台同時只有一組有效憑證；重置後舊憑證立即失效。憑證為 JWT（2026-09-03 定案），重置即失效須由平台端比對現行憑證識別保證，不能只驗簽章；不設有效期限（v07 定案） |
| 機台停用 | 停用中的機台無法運作；不影響餘額與尚未完成的交易 |
| 場館站台狀態 | 場館站台（含自行經營的機台主站台）不是「開通」狀態時，該場館所有機台一律無法運作 |
| 機台場館選單顯示 | 站台切換選到機台場館時，後台選單依「機台場館的後台選單」表隱藏不適用頁面（鏈上錢包管理僅顯示法幣 TWD 頁籤）；切回線上站台恢復完整選單。隱藏**跟著排除規則走**——排除為現階段營運決策，某項排除解除時對應頁面隨之恢復顯示 |
| 場館範圍跟隨站台切換 | 後台各頁皆有頁面標題下方的**站台切換下拉選單**，一次僅顯示所選站台的資料——本功能各頁（機台交易紀錄、洗分出金核實、場館日結報表等）的場館範圍一律由它決定，**不另設「場館」篩選欄位** |
| 遊戲更新預設停用 | 因法規（機台出廠前送審，審核通過後不得任意更動機台內遊戲），平台新增或更新遊戲後，機台場館一律預設停用（含更新前已啟用者），由營運窗口人工通知站長與場館（不做系統內通知功能），由**站長**自行於遊戲商管理啟用（操作員不可）；線上站台不受影響 |
| 入金交易併存 | 同一台機台可同時有多筆尚未完成的入金；新的入金不會取消舊的 |
| 出金交易唯一 | 同一台機台同時只能有一筆尚未完成的出金；玩家再次按下結算鍵時，舊的自動取消 |
| 重複回報 | 機台重複回報同一筆交易時，分數只異動一次，不會重複加減（入金與出金以交易編號辨識） |
| 單階段交易防重複 | ⚠️ 開分與洗分為單階段交易，請求**不帶唯一識別碼**，且機台**不會自動重送**（廠商回覆 2026-08-19）——**平台把每一筆開分／洗分請求一律當作新交易處理**，重複交易不會在無人操作下自行發生，僅可能來自現場人員重新操作。機台顯示失敗時，現場一律**先查後台交易紀錄**再決定是否重做。**開分無任何自然防護**——只要不超過額度上限，重按幾次就加幾次，是最高風險項；**洗分多半會被擋住**（全洗後餘額為 0 或只剩不足一個門檻單位的餘數，第二次計算後可洗金額為 0，必回餘額不足），僅「指定金額洗分且洗完餘額仍足夠再洗一次同額」時會重複扣款。曾向機台廠商爭取於請求中加入唯一識別碼，**廠商回覆 API 已上線、暫無法更動參數欄位（2026-08-19）**——本條的現場 SOP 即為正式因應方式（見 repo 根目錄「機台廠商確認事項」文件） |
| 人工出金連動 | 櫃檯對機台帳號人工出金時，必須同時取消該機台尚未完成的出金 |
| 人工入金 | 櫃檯對機台帳號人工入金時，不需處理尚未完成的入金 |
| 交易保留期限 | **入金**：尚未完成的交易超過 24 小時自動轉為「已逾時」。**出金：不設逾時**，待確認保留至完成、被新出金取代、人工出金連動取消或 Admin 手動取消為止 |
| 場次唯一性 | 一台機台同時只能有一個進行中的場次 |
| 場次切分 | 無進行中場次時由開分／入金使分數由 0 轉正建立；**任一筆洗分或出金交易完成當下即結束當前場次**（不分全洗或指定金額、不等核實），留有餘數則立即開立新場次承接（期初餘額＝餘數；僅洗分可能留餘數，出金一律清空餘額）；分數歸 0 亦結束場次 |
| 場次欄位於線上帳號 | 與線上會員共用的頁面（交易紀錄查詢、注單查詢等）所帶的場次編號欄位，線上帳號沒有場次，一律顯示「—」（2026-09-03 定案） |
| 場次逾時 | 逾時時間取自場館設定，預設 1 小時；期間內有任何交易或注單即重新起算 |
| 場次歸屬 | 場次期間的所有交易與注單一律歸屬於該場次（結束場次的洗分／出金交易歸屬於被它結束的場次）；場次不得作為風控、優惠或分潤的判定依據 |
| 前台顯示隔離 | 機台前台的注單與遊戲紀錄僅顯示當前進行中場次的內容；前一場次的紀錄一律不顯示 |
| 場次日結 | 日結時間到達時強制結束所有進行中的場次，餘額轉為隔日新場次的期初餘額 |
| 機台不可刪除 | 機台與機台帳號不提供刪除操作；報廢或不再使用一律以停用處理，資料保留供歷史紀錄查詢 |
| 收據核銷 | 出金紀錄只有「待核實」狀態可核實（核銷）；重複核實阻擋並提示 |
| 時區 | 後台所有時間欄位一律顯示為 UTC+0 |

#### API 一覽

所有 API 均為 `POST`、`Content-Type: application/json`、`Authorization: Bearer <token>`（token 為平台簽發的 **JWT** 機台憑證——2026-09-03 定案；驗證除簽章外須比對該機台現行有效的憑證識別，重置後舊 token 一律拒絕；不設有效期限（v07 定案），僅靠重置使舊憑證失效），`dateTime` 一律為 UTC。

| 主文用語 | API | 階段 | 帳務生效時點 |
| ------- | --- | ---- | --------- |
| 開分 | `req-keyin` | 單階段 | 立即 |
| 洗分 | `req-keyout` | 單階段 | 立即 |
| 入金 | `req-cashin` → `end-cashin` | 兩階段 | 第二階段 |
| 出金 | `req-cashout` → `end-cashout` | 兩階段 | 第二階段 |

#### 狀態碼對照

平台一律以 `status` 表達業務結果，不以 HTTP 狀態碼表達。

| 狀態碼 | 主文的「未成立原因」 | 平台判定條件 |
| ----- | ---------------- | --------- |
| `0-OK` | （成立） | 正常受理 |
| `1-OVER LIMIT` | 超過額度上限 | 本次金額加計後，全場館機台分數餘額合計將超過場館額度上限（額度為全場館共用） |
| `1-NO CREDITS` | 餘額不足 | 洗分可洗金額為 0（含以門檻捨去後為 0），或出金時餘額為 0。**不寫入交易紀錄**，僅回覆本碼（2026-09-03 定案） |
| `1-NO RECORD` | 查無對應交易 | 查無對應 PENDING，或 TXID 不符 |
| `2-OCCUPIED` | （不啟用） | 平台不回此碼。廠商文件在四支第一階段 API 均將此碼標註為 `(reserved)`，其情境為「已被網頁玩家占用」；機台帳號的前台登入僅供機台本身的遊戲畫面使用（帳密不交付玩家，見「機台帳號」），平台不把前台登入狀態當作機台交易的阻擋條件，不啟用此碼 |
| `6-BAD DATA/FORMAT` | 資料格式錯誤 | 欄位缺漏、型別錯誤、`currency` 與主站台核心貨幣不符、金額為負 |
| `7-OUT OF SERVICE` | 機台停用中 / 場館未開通 | 機台為停用狀態、場館站台非「開通」，或平台維護中 |
| `9-OTHER ERROR` | 憑證失效 / 系統錯誤 | Token 無效或已重置、機台帳號不存在，或其他未預期錯誤 |

#### 入金（`req-cashin` → `end-cashin`）

  - 收到 `req-cashin` 一律建立新的 PENDING 並產生唯一 TXID，**不使既有 PENDING 失效**；同一帳號可同時存在多筆有效入金 PENDING
  - **額度上限於本階段判定並預留**（v07 定案）：先取得**場館鎖**（額度為全場館共用），在鎖內以「當下全場館機台分數餘額合計 ＋ **已預留未入帳的入金金額** ＋ 本筆金額」判定；未超限才建立 PENDING、把本筆金額計入預留、釋放鎖，超限則回 `1-OVER LIMIT`、不建立 PENDING、不預留。入金因此逐筆序列化，多筆 PENDING 各自通過檢查、合計卻超額的路徑由此堵住
  - **預留額度的釋放**（v07 定案）：入帳成功時預留轉為實際分數餘額；PENDING 逾時（24 小時）由排程關閉時釋放；Admin／站長於交易紀錄手動取消該筆待確認入金時立即釋放。⚠️ 預留與釋放必須成對，漏掉任一條路徑都會讓額度被永久佔用
  - 收到 `end-cashin` 且 TXID 相符時，關閉 PENDING、更新帳務、把預留轉為實際餘額，回 `0-OK`。**本階段不再判定額度上限**——額度已於 `req-cashin` 判定並預留，紙鈔不會在超額的情況下被收進錢箱
  - 收到 `end-cashin` 但查無 PENDING 或 TXID 不符時，僅記錄 log 後丟棄，回 `1-NO RECORD`，不變更任何資料
  - 機台端 15 秒未收到成功回覆即重送 `end-cashin`，且跨 power cycle 續送。平台**必須具備冪等性**：相同 TXID 第二次以後收到時，若該 PENDING 已完成，直接回 `0-OK` 且不重複加值
  - 櫃檯人工入金**不需**使既有入金 PENDING 失效

#### 出金（`req-cashout` → `end-cashout`）

  - **同一帳號同時只允許一筆有效出金 PENDING**；收到 `req-cashout` 時若已有既存 PENDING，必須先標記失效再建立新的
  - `order_id` 由平台產生，一筆出金一組，全系統唯一，印於收據上，並作為櫃檯核銷時的查詢鍵（經廠商確認為流水號；廠商文件 v1.2 歷程誤寫為「營運商代號」）。格式須為**人工可朗讀、可輸入的短碼**——核銷靠櫃檯人工鍵入，不依賴廠商收據的列印長度限制
  - 核可金額 ＝ `req-cashout` 當下的**全部餘額**（**清空餘額、不套門檻**——2026-09-01 廠商定義出金即清空餘額）。`req-cashout` 的請求**不帶 `throshold` 欄位**，其金額參數必定是機台當前顯示的全部餘額
  - 出金完成後機台餘額為 **0**，**不產生餘數**（餘數僅洗分門檻取整時可能發生）
  - **`end-cashout` 扣分完成當下當前場次即結束**，餘額歸 0、無餘數承接（見主文「場次」）；交易被取代或取消不觸發場次結束
  - 核可金額為 0 時回 `1-NO CREDITS`，不建立 PENDING、不寫入交易紀錄
  - 收到 `end-cashout` 但查無 PENDING 或 TXID 不符時，僅記錄 log 後丟棄，回 `1-NO RECORD`
  - 同樣須對相同 TXID 的重複 `end-cashout` 具備冪等性
  - **櫃檯人工出金時必須一併使既有出金 PENDING 失效**；之後機台送來的 `end-cashout` 會因查無對應 PENDING 而自動結束流程
  - 核可金額以 `req-cashout` 當下為準，不受流程期間的入金影響
  - **機台端的「列印成功」判定為「已完整輸出至系統 printing queue」**，非實際出紙；後續卡紙、缺紙由 queue 保證狀況排除後補印，機台仍會送出 `end-cashout`。平台不需、也無法得知實體出紙結果
  - **第一階段有 15 秒逾時**：機台送出 `req-cashout` 後 15 秒未收到回覆即直接結束程序（收據不印）。但平台此時已建立 PENDING，該筆將永遠等不到 `end-cashout`，須由新的 `req-cashout` 取代或 Admin 手動取消收斂
  - 機台在「列印尚未開始」時偵測到印表機異常會**直接結束流程且不發出任何 API**（文件流程圖 case 1：do nothing），平台端表現同上
  - **過渡期（機台暫無印表機，2026-09-03 廠商告知）**：`req-cashout`／`end-cashout` 改由**前台**依序呼叫——按結算鍵送 `req-cashout`，收到回覆後依回覆內容立即送 `end-cashout`，收到第二次回覆後顯示結算結果畫面（含 `order_id`）供玩家拍照，照片代替收據。平台端規則不變：PENDING 建立／取代、`end-cashout` 冪等、扣分於 `end-cashout` 完成時、場次於此時結束。待確認：前台呼叫的認證方式（是否沿用機台憑證）、`req-cashout` 成功後 `end-cashout` 失敗時前台的重送策略；前台無法補送時交易停在 PENDING，依既有人工出金連動取消處理。印表機到位後回歸機台呼叫流程
  - 廠商文件另定：中央確實無法回覆第二階段成功回覆時，現場 Operator 須至機台選單執行 **Reset**。Reset 後機台停止重送，平台端的 PENDING 只能由 Admin 手動取消

#### 開分（`req-keyin`）

單階段，判定後立即更新帳務；判定與入帳於**場館鎖**內執行，與入金的預留共用同一把鎖而序列化，判定基準須含**已預留未入帳的入金金額**（v07 定案）。超過額度上限回 `1-OVER LIMIT`，不寫入任何帳務異動。

  - 機台送出請求後**不會自動重送**（廠商回覆 2026-08-19）；請求不帶唯一識別碼，平台**把每一筆請求都當作新交易受理**，不做也無從做冪等判斷

#### 洗分（`req-keyout`）

  - 同開分：機台**不會自動重送**，**每一筆請求都當作新交易受理**
  - 請求帶 `mode`（`value` 指定金額／`all` 全洗）與 `throshold`（機台端設定的門檻值）
  - **平台計算一律採請求中的 `throshold`**（2026-09-01 定案；後台不設門檻）。廠商保證每筆洗分請求**必帶** `throshold`，值為**正值或 0、不會為負**；`throshold=0` 表示**洗出當前全部餘額**（餘額以平台帳上為準）、不做取整。規格外的值（負值、缺漏、非數值）屬廠商保證外情形，防禦性處理：拒絕該筆、回 `6-BAD DATA/FORMAT`，不寫入任何帳務異動
  - 回覆的 `value` 為平台核可金額，可能與請求金額不同
  - 計算規則：核可金額 ＝ 餘額以門檻為單位無條件捨去。例：門檻 100、餘額 321 → 核可 300；門檻 0、餘額 321 → 核可 321（全額）
  - `mode=all` 時亦僅扣除核可的 300，餘數 21 **繼續留在帳號上**，平台不另記交易、不清空餘額。廠商 API 的回覆只有單一 `value` 欄位，機台端看到核可的 300，扣除後機台與平台餘額一致
  - `mode=value` 時請求金額須不大於可洗金額，否則以可洗金額為準核可；**餘額不清空**，剩下的分數留在機台上
  - 核可金額為 0 時回 `1-NO CREDITS`，不寫入任何帳務異動與交易紀錄
  - 單階段，回 `0-OK` 即已完成扣款，無回滾機制；**完成當下當前場次即結束**，餘數由新場次承接（見主文「場次」）
  - 稽核倍數大於 0 時，可洗金額須先扣除尚未完成稽核的部分再套用門檻計算；扣除後為 0 時回 `1-NO CREDITS`（機台預設 0 倍，不會觸發）

#### PENDING 保留期限

API 文件僅定義機台端行為：第二階段每 15 秒未收到成功回覆即重送，直到成功為止，跨 power cycle 續送；但收到 `1-NO RECORD`、`6-BAD DATA/FORMAT` 這類邏輯錯誤時直接結束流程，不再重送。文件**未定義平台端何時可判定死單**。

平台端規則如下：

  - **入金 PENDING 保留 24 小時**，逾期自動轉「已逾時」；之後再收到 `end-cashin` 一律回 `1-NO RECORD`，機台停止重送，流程收斂。逾時是「現場已人工補分、卻未先取消待確認」情境的自動保險絲——沒有它，機台修復後遲到的重送會使該筆 PENDING 正常完成而**重複加分**
  - **出金 PENDING 不設逾時**，保留至完成、被新的 `req-cashout` 取代、人工出金連動取消或 Admin 手動取消為止。出金的遲到 `end-cashout` 只是補扣分數，不會使玩家多領；重複領錢由核實紀錄「已核實」阻擋與人工出金的連動取消防範，與保留期限無關。且收據不設兌現時效、永久有效，對應交易不應先於收據關閉。死單（如機台報廢）由 Admin 手動取消清理——機台報廢僅停用不刪除，遺留的未完成交易即以此路徑收斂

#### 主文的交易狀態與 PENDING 的對應

| 主文狀態 | 對應 |
| ------- | ---- |
| 待確認 | PENDING 存在，尚未收到第二階段 |
| 已完成 | PENDING 已 completed |
| 已取消 | PENDING 被標記失效（新請求或人工出金覆蓋） |
| 已逾時 | 入金 PENDING 超過 24 小時自動關閉（僅入金；出金不設逾時） |
| 未成立 | 第一階段即被拒絕，未建立 PENDING（入金的額度上限於 `req-cashin` 判定，入帳階段不再判定） |

## 後台角色與權限（開發包⑧）

> ⚠️ **內部章節**：本功能尚未對客戶開放。本檔首行帶 `<!-- INTERNAL -->` 標記，`build_manual.sh` 產出客戶版手冊時會自動略過（客戶完全看不到本章）；`build_skill.sh` 與 Claude Code 端仍完整包含，供團隊查閱。角色表中「管理員」一角**永不對客戶揭露**，即使本功能將來對客戶開放，該角色仍須維持在 `INTERNAL` 區塊內。
>
> ⚠️ **開發包說明**：本檔為**開發包⑧（後台角色與權限——跨頁權限模型）**，是後台授權層的**完整實作依據，可獨立閱讀、不需再翻其他檔案**。與開發包①～⑦不同，本包**不是自 `實體機台_spec_v08.md` 抽錄**，而是把原本散落在 `後台管理員系統_spec_v03.md`（7.1.1 角色定義）、`站台列表_spec_v07.md`（管轄範圍、根站台、自身站台限制）、`實體機台_spec_v08.md`（操作員與機台權限矩陣）三處的規則整合為單一依據。**角色與權限模型以本檔為準**；各功能頁面的欄位、流程與畫面仍以該功能自己的 spec 為準（本檔只定義「誰能對誰做什麼」，不定義頁面長什麼樣）。本包為跨頁權限模型，**無獨立 proto**。
>
> 🎯 **核心架構要求**：權限必須做成**集中的授權層（authorization layer）**——「這個帳號能不能對這個站台做這件事」由單一模組回答，各功能頁面只負責呼叫，**不得自行硬編碼角色字串判斷**。管轄範圍（scope）為樹狀查詢，須在**後端每一支 API 強制執行**，前端的隱藏與唯讀僅是輔助。
>
> 📦 **相依關係**：本包為**開發包①～⑦的前置相依**——①（創建會員帳號）、②（站台列表）、④（機台交易紀錄）、⑤（洗分出金核實、場館日結報表）、⑥（機台場館平台規則）、⑦（機台更新包）的權限表皆引用本包定義的角色。本包自身**不相依於任何機台功能**，可獨立先行開發。

### 一、功能說明

後台帳號的權限由兩個維度決定：

  1. **角色（role）** —— 這個帳號能用哪些功能模組、能做到多深
  2. **所屬站台（home site）** —— 這個帳號看得到哪些資料

兩者相乘才是實際權限。**同一個角色在不同站台，權限範圍完全不同**——根站台 `admin` 的管理員看得到全平台，某個場館的管理員只看得到該場館及其子站台，兩者角色相同、範圍不同。

> ⚠️ 這是本包最容易實作錯的地方：**不要把「管理員」理解成一個平台方的超級帳號**。管理員是每個站台都有的角色，「看得到全部」是所屬站台剛好是樹根造成的結果，不是角色特權。

-----

### 二、站台結構（權限的座標系）

管轄範圍建立在站台的樹狀結構上，實作授權層前必須先理解這棵樹。本節為 `站台列表_spec_v07.md` 相關規則的完整內容。

#### 2.1 單一一棵樹

全平台的站台構成**單一一棵樹**，樹根為系統建置的**根站台 `admin`**（代碼 `ZZ`，站台類型「線上」）。所有站台——含各客戶的主站台——一律掛在它底下，**不存在第二個根、也不存在無上層的站台**。

```
admin（根站台，代碼 ZZ，線上）
  ├─ 主站台 A（線上，USDT）
  │    ├─ 子站台 A1
  │    │    └─ 子站台 A1a
  │    └─ 子站台 A2
  └─ 主站台 B（機台，TWD）＝ 實體遊藝場經營者
       ├─ 場館 B1
       └─ 場館 B2
```

#### 2.2 根站台 `admin`

| 項目 | 規則 |
| ---- | ---- |
| 數量 | 全平台**恰好一個**，由系統建置，不開放新增第二個 |
| 上層站台 | 無，且**不可指定**；新增／編輯視窗的「上層站台」欄不適用 |
| 刪除 | **不可刪除**（所有站台皆不可刪除，見 5.1），列表不顯示刪除按鈕；即使以 API 直接呼叫也須擋下 |
| 狀態 | **不可變更**，恆為「開通」；列表與編輯視窗的狀態欄唯讀，不可切為暫停／關閉／更新待審 |
| 站台類型／核心貨幣 | **不參與繼承鏈**——根站台自身的類型與貨幣不往下傳，類型與貨幣改由各主站台各自選定 |
| 可見者 | 僅**根站台自身的管理員**看得到根站台這一列；主站台以下的管理員與站長進入後台的起點都是自身所屬站台，看不到根站台，也看不到平行的其他主站台 |
| 網域／模板 | 可設定，行為與一般站台相同 |

> ⚠️ 根站台是整個平台的**單一失效點**——被刪除或被切為非「開通」狀態時，其下所有站台與前台皆受影響。上述保護規則須在**後端一併實作**，不能只靠前端隱藏按鈕。

#### 2.3 主站台

**主站台＝根站台 `admin` 底下的第一層站台**，即一個客戶（營運方）的頂層站台，其下可再展開無限層子站台。

  - **站台類型（線上／機台）與核心貨幣在主站台這一層選定**，其下所有子站台一律繼承、不可各自指定——機台主站台對應一個實體遊藝場經營者，其子站台即場館
  - 根站台本身**不是**主站台，其類型（線上）與貨幣不會傳給底下的主站台；因此機台類型的主站台可以直接掛在根站台底下，不受根站台為「線上」的影響
  - 站長的管轄範圍即自身所屬的主站台及其所有子站台

#### 2.4 階層瀏覽

  - **上下層關係：** 每個站台指定一個上層站台，層數不限；唯一的例外是根站台 `admin`，它沒有上層
  - **起始層顯示：** 一律顯示**自身所屬站台**這一列，點入即為其子站台；根站台的管理員因所屬站台就是 `admin`，起始層即根站台這一列（點入為各主站台）
  - **可見範圍：** 僅能看到自身所屬站台及其所有子站台，不包含平行站台或上層站台

### 三、角色總表

後台共七種角色。本表為完整定義（原出處為 `後台管理員系統_spec_v03.md` 7.1.1，內容一致）。

| 角色 | 對客戶 | 權限範圍 |
| ---- | ----- | ------- |
| 遊客 | 公開 | 無；註冊後等待配發權限 |
| 客服 | 公開 | 會員與代理商（不含人工出入金）、各式報表 |
| 清稽核客服 | 公開 | 會員與代理商（含人工出入金）、各式報表 |
| 財務 | 公開 | 會員與代理商（含人工出入金）、各式報表、財務管理、遊戲商管理、系統管理；可接收出金審核與 KYC 審核的提醒聲音 |
| 站長 | 公開 | 會員與代理商（含人工出入金）、各式報表、財務管理、遊戲商管理、系統管理；可接收出金審核與 KYC 審核的提醒聲音；可分配站長以下的角色權限 |
| **管理員** | **不揭露** | 每個站台皆有的最高管理者，層級高於同站台的站長：可操作自身站台及其所有子站台的全部功能，並可直接指派管理員與站長；站長唯讀的欄位（上層站台、模板）與「開通」狀態切換僅本角色可執行 |
| **操作員** | 未開放 | 場館現場人員，權限小於站長，可見範圍僅自身所屬場館；限實體機台場館使用 |

同一站台內的層級：**管理員 > 站長 > 財務 > 清稽核客服 > 客服 > 遊客**；操作員為機台場館專用，層級小於站長。

**對客戶的說法**：一律以**站長為後台最高權限**。「前言與通用規則」名詞對照的站長定義（「擁有後台最高權限的管理者」）是對客戶的說法，**維持不改**；管理員一角永遠留在 `INTERNAL` 區塊內，客戶版手冊不輸出。

**名詞區分**：「操作員」是**後台帳號的權限角色**；「Operator（店員）」指現場持鑰匙操作機台的人員。兩者常是同一批人，但概念不同——店員要執行核實等後台操作，須另持有操作員角色的後台帳號。

**機台場館只用三種角色**：管理員／站長／操作員。客服、清稽核客服、財務、遊客四種不適用於機台場景（2026-09-04 定案）。

### 四、管轄範圍（scope）

  - **定義：** 一個帳號的管轄範圍＝**其所屬站台，加上該站台的所有子站台**（整棵子樹），不含平行站台與上層站台
  - **管理員與站長的可見範圍相同**，差別在能操作到什麼深度（見第五節）
  - **操作員**的範圍更窄——僅自身所屬場館，**不含**該場館的子站台
  - 根站台 `admin` 的管理員，其子樹即整棵樹，故等同看到全平台

| 所屬站台 | 角色 | 看得到 |
| ------- | ---- | ----- |
| `admin`（根站台） | 管理員 | 全平台所有站台與場館 |
| 主站台 A | 管理員／站長 | A 及 A 底下所有子站台 |
| 子站台 A1 | 管理員／站長 | A1 及 A1 底下所有子站台（看不到 A、也看不到平行的 A2） |
| 場館 B1 | 操作員 | 僅 B1 自身 |

**實作要求：**

  - 範圍判定為樹狀祖先查詢：`目標站台 == 自身站台 或 目標站台為自身站台的後代`
  - **須在後端每一支 API 強制執行**。前端隱藏選單、把欄位設為唯讀、不渲染按鈕，都只是輔助，不可作為唯一防線
  - 站台切換下拉、列表查詢、報表匯出、明細頁直連網址，全部走同一個範圍判定
  - **越權操作一律回「無權限」**（2026-10-05 定案）：範圍外站台、自身站台限制（5.2）、越級指派角色（第六節）等越權操作，後端一律拒絕並回傳「無權限」錯誤、資料不變；不採「當作不存在／回空結果」。錯誤代碼由後端定義。全系統一致（含場館日結報表查詢、匯出範圍外場館）

### 五、站台列表的角色權限

管理員與站長在站台列表的完整權限差異。管理員對**子站台**有完整權限，對**自身所屬站台**受限兩項（見 5.2）。**站台一律不可刪除**（2026-10-05 定案，線上與機台皆同；刪除會影響站台的樹狀結構），停止服務改切暫停或關閉。

#### 5.1 權限矩陣

| 功能項目 | 管理員 | 站長 |
| ------- | ----- | ---- |
| 可見站台範圍 | 自身站台及所有子站台（不含平行或上層站台）；根站台的管理員＝全平台 | 同左 |
| 新增子站台 | 可新增，可於管轄範圍內自由選取上層站台 | 可新增，上層站台固定為當前所在層，不可修改 |
| 子站台：上層站台（編輯） | 可於管轄範圍內自由修改 | 唯讀顯示；如需變更須通知管理員操作 |
| 子站台：模板（新增／編輯） | 可選取或修改 | 唯讀顯示；如需變更須通知管理員操作 |
| 子站台：狀態切換 | 可切換為任意狀態（含「開通」） | 僅可切換為「暫停」或「關閉」 |
| 網域新增／刪除 | 可操作 | 可操作；操作後若站台為「開通」或「更新待審」，系統自動切換為「更新待審」 |
| 角色指派 | 可在管轄範圍內指派**管理員與站長**（及以下所有角色，含操作員） | 僅可分配站長以下的角色權限（含操作員），**不可指派管理員與站長** |
| **自身站台：上層站台** | **不可修改**——須由上層站台的管理員操作 | 不可修改 |
| **自身站台：狀態切換** | 可切「暫停」「關閉」；**不可切為「開通」**（含由「更新待審」切回）——須由上層站台的管理員操作 | 同左 |

#### 5.2 管理員對自身所屬站台的限制

管理員對**子站台**有完整權限，但對**自身所屬站台**受限兩項（2026-09-04 定案；原第三項「不可刪除自身站台」因 2026-10-05 定案所有站台皆不可刪除而併除）：

| 項目 | 規則 |
| ---- | ---- |
| 上層站台 | **不可修改**——避免把自己連同整棵子樹搬到別處；須由上層站台的管理員操作 |
| 狀態切為「開通」 | **不可**（含由「更新待審」切回）——上線與否由上層決定；須由上層站台的管理員操作 |
| 其餘 | 「暫停」「關閉」可自行切換（與站長相同）；名稱、網域、模板、場館設定皆可自行編輯 |

> 📖 為什麼「暫停／關閉」不禁：站長現行規則本就可將自身站台切為暫停或關閉（暫停自家服務屬營運決策）。若連這兩項都禁，管理員對自身站台的狀態權限會低於同站台的站長，模型自相矛盾。

根站台 `admin` 無上層，故這兩項對它一律不成立——它另有完整的保護規則（見 2.2）。

#### 5.3 站台狀態與誰能切換

共五種狀態（列表以 Badge 色標呈現）：

| 狀態 | 色標 | 觸發方式 | 說明 |
| ---- | ---- | ------- | ---- |
| 待開通 | 灰色 | 新建站台自動設定 | 尚未上線，模板可留空 |
| 開通 | 綠色 | **上層站台的管理員**手動切換 | 站台正常運作中；切換為此狀態時模板為必填；站台自身的管理員與站長皆不可自行切為開通 |
| 暫停 | 黃色 | 該站台的管理員或站長切換，上層站台的管理員亦可 | 站台暫停服務，可由上層站台的管理員恢復為開通 |
| 關閉 | 紅色 | 該站台的管理員或站長切換，上層站台的管理員亦可 | 站台已永久停止服務 |
| 更新待審 | 紫色 | 系統自動觸發 | 站台處於「開通」或「更新待審」狀態下，若前台或後台網域有異動，儲存後自動切換；待技術部門完成設定後由**上層站台的管理員**人工切回「開通」 |

「更新待審」為系統自動觸發，不開放手動選取；上層站台的管理員可在此狀態下手動切換為其他任意狀態。

### 六、角色指派

| 操作者 | 可指派的角色 | 可指派的範圍 |
| ------ | --------- | --------- |
| 管理員 | 管理員、站長、操作員、財務、清稽核客服、客服、遊客（＝所有角色） | 管轄範圍內的站台 |
| 站長 | 站長以下（操作員、財務、清稽核客服、客服、遊客）；**不可指派管理員與站長**（2026-10-05 定案） | 管轄範圍內的站台 |
| 其餘角色 | 不可指派 | — |

**規則：可指派的角色須低於操作者自身角色；唯管理員可指派管理員。**（2026-10-05 定案，原「不得高於」會讓站長可指派站長，與上表矛盾）。站長的角色下拉選單不出現管理員與站長；以 API 越級指派時後端拒絕、回傳「無權限」（見第四節實作要求）。

#### 6.1 現行的後台帳號建立流程（7.1.2）

新增後台人員的操作步驟：

  1. 提供後台註冊連結給新人員，對方自行完成註冊
  2. 取得對方的系統人員編號
  3. 於系統使用者列表中找到該帳號，調整角色為對應職位

新帳號預設角色為「遊客」，無法存取任何功能，須手動調整角色後方可使用對應功能。

**調整角色**：點擊列表中角色欄位，從下拉選單選擇新角色，確認後即時生效。

#### 6.2 系統使用者列表需要的調整

| 項目 | 調整內容 |
| ---- | ------- |
| 角色下拉選單 | 需納入「管理員」與「操作員」；可選項目依**操作者自身角色**過濾——管理員可選到管理員，站長僅能選站長以下（不含站長） |
| 列表可見範圍 | 僅顯示**管轄範圍內**的後台帳號，不跨站台 |
| 篩選器 | 現行為系統人員編號、角色兩欄；角色下拉同步納入新角色 |
| proto | `protos/系統使用者列表_proto_v01.html` 為 splitter 產物，**不可手改**；上線時須改 `protos/_src/blac_admin_proto_v01.html` 再重跑 `python3 tools/split_proto.py protos/_src/blac_admin_proto_v01.html protos`（見 repo 根目錄 `CLAUDE.md`）|

### 十、業務規則

| 規則 | 說明 |
| ---- | ---- |
| 權限＝角色 × 所屬站台 | 同一角色在不同站台的實際權限範圍不同；「管理員看得到全部」僅在所屬站台為根站台 `admin` 時成立 |
| 管轄範圍後端強制 | 範圍判定須在每一支 API 執行，前端隱藏與唯讀僅為輔助 |
| 集中授權層 | 「某帳號能否對某站台做某事」由單一模組回答，各功能頁面不得自行硬編碼角色字串 |
| 管理員自身站台限制 | 不可改自身站台的上層站台、不可將自身站台切為「開通」；一律由上層站台的管理員執行 |
| 站台不可刪除 | 所有站台（線上、機台、根站台）一律不可刪除，前後端皆擋；停止服務改切暫停或關閉（2026-10-05 定案） |
| 越權回應 | 越權操作一律拒絕並回傳「無權限」錯誤、資料不變；錯誤代碼由後端定義（2026-10-05 定案） |
| 角色指派上限 | 可指派的角色須低於操作者自身角色，唯管理員可指派管理員——站長最高只能指派到站長以下（含操作員），不可指派站長（2026-10-05 定案） |
| 新帳號預設角色 | 一律為「遊客」，無任何權限，須由有權者指派角色後方可使用 |
| 根站台保護 | 唯一、不可刪除、狀態恆為「開通」、不可指定上層、不參與類型與貨幣繼承；後端須一併實作 |
| 上層站台不可留空 | 一般站台一律須指定上層站台；唯一無上層者為系統建置的根站台 `admin` |
| 上層站台循環防護 | 編輯時不可將自身或自身的子站台選為上層站台 |
| 管理員不對客戶揭露 | 客戶版手冊、對外文件與教育訓練一律以站長為後台最高權限；本角色永遠留在 `INTERNAL` 區塊內 |
| 機台場館三種角色 | 機台場館的後台帳號僅使用 管理員／站長／操作員；其餘四種角色不適用於機台場景 |

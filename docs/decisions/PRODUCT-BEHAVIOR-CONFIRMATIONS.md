# 產品行為確認紀錄（Spec vs. 實際產品）

## 用途

`specs/` 底下的各份 spec.md 是從「實體機台開發包」原始文件抽錄、匯入的快照，會跟實際上線的產品行為出現落差——原文寫錯、原文沒更新、或原文本來就沒定義。每次遇到這種落差，處理方式是：**直接依 Oscar（PM／產品負責人，必要時會同 RD／後端工程師）的確認為準**，在對應 Requirement 的 `statement` / `spec_reference` 裡清楚標注確認來源與日期，視為 grounded（不當成 exploratory 假設、不需要走 `assumptions[]` + `needs_human_confirmation` 流程）。

這份文件把散落在各功能區 `requirements.yaml` 裡的確認記錄集中列出，供之後的 Validator、新加入的協作者，或回頭比對 spec 是否已更新時快速查找依據，不需要逐條個別詢問。

**這裡列出的每一項，最終都應該回報並合入對應 spec 的正本**（各 spec.md 開頭都寫明「兩檔規格如有出入，一律以正本為準，並回報修正本檔」）——這份文件是在正本更新前的過渡紀錄，不是取代正本。

## SITELIST（站台列表，SPEC-SITELIST-001）

### REQ-SITELIST-016｜狀態切換權限（待開通是否可手動選取）
- **spec 原文**：§站台狀態 只列出「待開通」的觸發方式為「新建站台自動設定」，未列為 Admin 可手動選取的目標狀態；「任意狀態」範圍未明確定義是否含待開通。
- **實際行為**：Admin 的「任意狀態」**含待開通**，可將既有（如已開通）站台手動切回待開通；操作員因後台完全不顯示站台列表頁面，不具備任何狀態調整能力（含查看）。
- **確認**：Oscar，2026-09-14，口頭補充。
- **影響**：TC-SITELIST-028（原為雙情境探索式斷言，改為單一定論）；新增 TC 覆蓋操作員無頁面存取權（AC-SITELIST-0164）。

### REQ-SITELIST-022／023｜刪除站台功能不存在
- **spec 原文**：§操作/刪除站台 描述「點擊列表刪除後顯示確認彈窗、二次確認後執行」為可正常運作的功能。
- **實際行為**：任何站台類型（線上／機台）**前端皆無刪除入口、後端 API 也拒絕刪除請求**。原因是刪除站台會影響站台樹狀結構（子站台歸屬、上下層關係）。原本「刪除有子站台的站台時如何處理子站台」的疑慮因此消失（刪除永遠不會執行）。
- **確認**：PM／後端，2026-09-14，經 `CLR-SITELIST-007`／`CLR-SITELIST-008`／`CLR-SITELIST-009` 三張澄清單確認。
- **影響**：TC-SITELIST-040/041/043/044 退役；TC-SITELIST-042 修訂為「前端無入口」＋「後端 API 拒絕」兩條案例。

### REQ-SITELIST-002｜「子站台強制跟隨主站台類型」在 admin 根站台底下不適用（特例）
- **spec 原文**：無——spec.md 全文沒有任何「admin」相關的例外描述；正文只有「站台類型於主站台（根層）選定，子站台一律與主站台同類型、不可個別選擇」這條通用規則。
- **實際行為**：**這條通用規則只適用於「上層站台不是 admin」的一般情況**。當上層站台是 admin（最上層的根站台）時，底下建立子站台**可以自由選擇機台或線上類型**，不強制跟隨 admin 自身的類型；核心貨幣會依所選類型連動建立（例如選機台就連動啟用 TWD），不需要 admin 自己的鏈上錢包管理預先啟用該幣別。Oscar 表示這是他先前發現舊版行為有問題、上報後才調整定案的結果，不是本次新發現的缺陷。
- **確認**：Oscar，2026-09-15，口頭確認，特例僅限 admin 根站台；一般主站台（如 Arcade、SpringKyle）底下子站台仍強制跟隨主站台類型，REQ-SITELIST-002／TC-SITELIST-003／TC-SITELIST-004（含 API 層拒絕）維持有效、不需修改。
- **影響**：這是一個「已核准規則的例外情況」，過去沒有任何 TC 覆蓋 admin 這個特例路徑。待評估是否要新增一條 Requirement／TC 明確覆蓋（見待回報合入正本表）。

## TXLOG（機台交易紀錄查詢，SPEC-TXLOG-001）

### REQ-TXLOG-008｜交易類型篩選實際為多選 chip，標籤不含「機台」字首
- **spec 原文**：§篩選器 描述交易類型為單選下拉選單，選項含「全部／機台開分／機台洗分／機台入金／機台出金」。
- **實際行為**：實際為**多選 chip**（可同時勾選多個），標籤為「開分／入鈔／出鈔／洗分」，不含「機台」字首。
- **確認**：Oscar，2026-09-14，依實際畫面截圖。

### REQ-TXLOG-009｜交易狀態篩選依交易類型分兩組技術值
- **spec 原文**：交易狀態為統一的 5 種分類文字（待確認／已完成／已取消／已逾時／未成立）。
- **實際行為**：可選項目依交易類型分兩組**後端技術值**：開分／入鈔＝已逾時、錯誤、無、成功、等待中、已取消、無效（7 項）；出鈔／洗分＝失效、待處理、已拒絕、等待中、錯誤、已處理（6 項，含第一輪截圖遺漏、Oscar 事後補上的「已處理」）。兩組技術值與 spec 的 5 種概念分類對應關係已由 Oscar 確認（見 requirements.yaml 內對應表），唯開分/入鈔組的「無」語意尚未確認，標記為 minor ambiguity。
- **確認**：Oscar，2026-09-14，依實際畫面截圖，分兩輪（第一輪漏了「已處理」，第二輪補上）。

### REQ-TXLOG-010｜核實狀態篩選只有 3 個可選值
- **spec 原文**：核實狀態下拉選單含「全部／待核實／已核實／已作廢／不適用」。
- **實際行為**：篩選器只有 3 個可選值（待核實／已核實／已作廢），**沒有「不適用」**；「不適用」只是列表欄位本身的顯示值，不是篩選器選項。
- **確認**：Oscar，2026-09-14，依實際畫面截圖。

### REQ-TXLOG-017｜出金待確認的收斂路徑不含「Admin 手動取消」
- **spec 原文**：出金待確認可透過「機台補完回報、被新出金取代、櫃檯人工出金連動取消，或 Admin 手動取消」收斂。
- **實際行為**：「Admin 手動取消」這條路徑不存在（見 REQ-TXLOG-028）；改為「轉介至洗分出金核實頁由人工處理」。
- **確認**：隨 REQ-TXLOG-028 一併確認，2026-09-14。

### REQ-TXLOG-025／026｜重送次數、來源欄位目前固定顯示「—」
- **spec 原文**：重送次數欄依實際重複回報次數顯示數字（0 時顯示「—」）；來源欄顯示交易發生位置（空值顯示「大廳」）。
- **實際行為**：**兩個欄位目前都固定顯示「—」**，不論資料為何，皆尚未實作對應顯示邏輯。重複回報分數只變一次的底層冪等性規則本身仍成立（由 SPEC-CASHFLOW-001 驗證），只是這兩個欄位的「呈現」還沒做。
- **確認**：Oscar 與 PM／RD，2026-09-14。

### REQ-TXLOG-028／029／030｜「手動取消」操作不存在
- **spec 原文**：§操作 描述「手動取消：僅 Admin 可對待確認狀態的交易執行；二次確認後標記為已取消」。
- **實際行為**：交易紀錄查詢頁**完全不提供手動取消操作**，查無可手動取消的交易；待確認／待核實交易需要的人工處理，一律在「洗分出金核實」頁（SPEC-CASHOUT-001）進行。原本「非 Admin 或非待確認狀態時的阻擋機制」（REQ-TXLOG-029）因此 moot。
- **確認**：Oscar，2026-09-14；`CLR-TXLOG-001` 同步標記為 moot 並回覆。

## CASHOUT（洗分出金核實，SPEC-CASHOUT-001）

### REQ-CASHOUT-004｜本頁沒有「交易狀態」欄位，只有「核實狀態」
- **原始寫法**：Requirement 用「一筆交易狀態為待確認」描述測試前提，容易誤導成本頁有交易狀態篩選/欄位。
- **澄清**：本頁的篩選器與列表欄位本來就沒有「交易狀態」，只有「核實狀態」；判斷依據是「核實狀態紀錄是否存在」，而非本頁顯示或篩選交易狀態。
- **確認**：Oscar，2026-09-14。

### REQ-CASHOUT-011｜訂單編號查無結果時的失敗提示文案
- **spec 原文**：只說訂單編號是「櫃檯兌現時的主要查詢方式」，未定義查無結果時的系統反應。
- **實際行為**：前端顯示明確的失敗 toast：「失敗：查無此訂單編號，請先到「機台交易記錄」查明交易狀態，不要憑印象付款」。
- **確認**：Oscar，2026-09-14，依實際畫面截圖（逐字文案）。

### REQ-CASHOUT-025｜操作員的場館限制機制是「無站台切換權限」，非核實動作被個別攔截
- **spec 原文**：只寫結果「操作員限自身場館」，未定義機制。
- **實際行為**：操作員**完全沒有切換站台的權限**——前端沒有切換入口、後端 API 也拒絕操作員指定其他場館。已補上深連結繞過的防禦深度測試。
- **確認**：Oscar，2026-09-14。

### REQ-CASHOUT-031｜現金淨收計算「需先核實才計入」規則出金比照洗分
- **spec 原文**：§相關業務規則 逐字只提「只計入已核實的洗分」。
- **實際行為**：出金比照辦理，同樣需要已核實才計入現金淨收，spec 原文只提洗分是遺漏，非刻意排除出金。
- **確認**：Oscar，2026-09-14。

### REQ-CASHOUT-020/028｜「作廢」操作僅在機台出金且核實狀態為「待核實」時才提供，已核實後作廢按鈕消失
- **spec 原文**：只定義「已作廢僅出金適用」「作廢僅Admin/站長可執行」，沒有明講「作廢」這個操作本身的觸發條件是否受核實狀態限制。
- **實際行為**：附實際畫面截圖確認——「核實」「作廢」兩個操作按鈕只出現在核實狀態為「待核實」的機台出金列；機台洗分列完全不提供作廢按鈕（符合既有 REQ-CASHOUT-020）；**已核實的出金列，作廢按鈕也一併消失**，無法對已核實交易再執行作廢。
- **確認**：Oscar，2026-09-15，依實際畫面截圖。
- **關聯**：這個澄清是 CLR-CASHFLOW-004 的延伸——確認了「作廢」操作的適用範圍僅限「已完成、待核實」的出金交易，跟 CASHFLOW-008/026 描述的「待確認」狀態 PENDING 死單完全是不同階段，兩者對不上，佐證了 REQ-CASHFLOW-008/026 移除「Admin手動取消」路徑的修正方向正確。

## CASHFLOW（機台金流與場次，SPEC-CASHFLOW-001）

### REQ-CASHFLOW-008/026｜「Admin 手動取消」收斂路徑不存在，交易紀錄查詢頁沒有此功能
- **spec 原文**：正本 SPEC-ARCADE-001 §機台交易紀錄／操作小節反覆 9 處明確定義「手動取消：僅 Admin 可對『待確認』狀態的交易執行」。
- **實際行為**：交易紀錄查詢頁不存在任何手動取消功能。所有待核實交易一律於「洗分出金核實」頁操作，但該頁的「作廢」僅適用於已完成、待核實的出金交易（見上一條），範圍對不上「待確認」狀態的 PENDING，不是同一件事。
- **影響**：REQ-CASHFLOW-008（入金預留釋放）現在僅剩「PENDING 逾時 24 小時自動釋放」一條路徑，沒有立即處理的手動路徑（不是資金卡死風險，只是無法立即處理）；REQ-CASHFLOW-026（出金15秒逾時死單）仍有「新請求取代」與「人工出金連動取消（REQ-CASHFLOW-027）」兩條路徑可收斂。
- **確認**：Oscar，2026-09-15（CLR-CASHFLOW-004，經撤回問法不精確的 CLR-CASHFLOW-003 後重開）。

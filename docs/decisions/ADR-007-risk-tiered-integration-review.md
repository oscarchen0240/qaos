# ADR-007 · Phase 2 × Phase 3 整合審查依風險分級，不是每條 TC 都跑全套

- **Status**: Accepted — 2026-09-15，Oscar 於 SPEC-MEMBER-001 影子測試交叉整合結束後提出
- **Context**:
  SPEC-MEMBER-001 的 Phase 2（人工版 26 條 TC）× Phase 3（agent 版 24 條 TC）交叉比對整合，最終有 14 條 Phase 2 TC 被修訂。每一條修訂——不論是「REQ-MEMBER-005 邊界值佈置機制」這種財務敏感的深度defect，還是「TC-MEMBER-012 補一個選填欄位」這種低風險精修——都跑了同一套全套流程：結構化 Gate → 獨立 Validator subagent 審查 → Oscar 逐條核准；FAIL 就打回重寫再跑一輪。多輪 FAIL 有兩類根因：(a) 真正需要抓的品質問題（欄位名稱抄錯、驗證範圍界定不清、design_rationale 與資料矛盾），(b) 低風險項目也被要求跟高風險項目一樣的審查深度，導致 Oscar 為了同一份 spec 反覆審核，耗時遠超過必要程度。

- **Decision**:
  往後任何一次 Phase 2 × Phase 3（或未來任何兩個獨立來源）的交叉整合，動手修訂 TC 之前先做風險分級：

  1. **高風險/財務/合規類**（涉及金流計算、權限判定、資料不可復原的刪除、法遵相關欄位）：維持現行全套流程——獨立 Validator subagent 審查 + Oscar 逐條核准。這類錯誤的代價（誤判）遠高於審查時間成本。

  2. **低風險/精修類**（措辭精確化、補一個已知安全的驗證步驟、欄位揭露但不影響判定邏輯）：只跑結構化 Gate（G-DESIGN structural），不啟動獨立 Validator subagent；同一批次的多條低風險修訂**打包成一份核准單**一次送 Oscar 核准，不要一條一份。

  3. **開始批次整合前，先把所有「spec 未定義」的產品機制疑問一次收集完、一次性問 Oscar**，不要在逐條修訂的過程中一個一個發現、一個一個打回重來。稽核=0 的真實效果、KYC「已停用」在會員列表的實際顯示這類資訊，如果在交叉比對階段就先問清楚，可以省掉後續好幾輪 reject→重新修訂→再審查的往返。

  4. Test Designer 端（不論是人工扮演或 Phase 3 agent）在 submit 前，對照 spec 原文逐字核對自己引用的欄位名稱、規則措辭，**不要讓 Validator 或 Oscar 的審查去兜底本可自查的抄寫錯誤**——這類低級錯誤造成的往返本身就是本次案例中最大的時間浪費來源之一。

- **Consequences**:
  - 本 ADR 不追溯套用到 SPEC-MEMBER-001 已完成的整合（TC-004/005/007/008/012/014/015/016/018/019/020/021/022/025），該批已全數走完全套流程並核准。
  - 往後新的 spec 交叉整合，需要先做風險分級表（哪些 requirement 屬於高風險）才能開始批次修訂。
  - 低風險項目省略獨立 Validator subagent，代表這類項目的把關依賴「結構化 Gate + Oscar 對打包核准單的審閱」，比現行全套流程鬆——這是刻意的取捨：風險本來就集中在少數高風險 requirement，把審查力氣集中在那裡，而不是均攤到每一條 TC。

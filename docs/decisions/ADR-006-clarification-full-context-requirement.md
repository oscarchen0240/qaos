# ADR-006 · 開 Clarification 前必須完整讀取並附上 spec 原文段落

- **Status**: Accepted — 2026-09-15，Oscar 於 Phase 3 影子測試期間提出
- **Context**:
  `CLR-CASHFLOW-003`（問「交易紀錄查詢頁的手動取消操作是否存在」）在開單時只引用了「612/620/584行」幾個行號與簡短摘要，沒有把正本裡「手動取消」操作被反覆定義的完整段落（612/616/620/778/809/829/894/913/916/944 行，共 9 處）讀完、交叉核對過。

  事後完整讀取後發現：正本第 609-620 行「#### 操作」小節清楚把「查看明細」「手動取消」列為兩個獨立條列項目，另有一句獨立的警語「本頁**不提供核實操作**——洗分與出金的核實一律於帳務管理『洗分出金核實』執行」。這句話講的是**核實**（verification）這件事，跟**手動取消**（cancel）是完全不同的兩個操作，不應該被混淆或誤讀成「手動取消也不提供」。

  這代表 `CLR-CASHFLOW-003` 原本的問法（「這個操作到底存不存在」，開放式三選項）並不精確——spec 對這個操作的定義本身完全不模糊，反覆 9 處交叉印證。真正該問的問題是「`REQ-TXLOG-028`（Oscar 2026-09-14 依實際畫面確認此操作不存在）能否重新核實」，而不是含糊地問規則是什麼。

- **Decision**:
  往後任何一次要開 Clarification（不論是這個 session 手動扮演 Spec Analyst 時，或是 Phase 3 正式的 spec-analyst agent），在動筆寫 `--question`/`--context` 之前，強制先完成兩步：

  1. **完整讀取**：對問題涉及的每一個關鍵詞/操作/欄位，在相關的 spec 全文（不只是 RequirementModel 裡摘錄的 quote）裡搜尋所有出現的位置，逐一讀完上下文，確認不同段落之間是否互相印證或矛盾。不能只看 requirements.yaml 的 `spec_reference.quote`（那本身可能就是節錄）。
  2. **完整附上原文**：讀完後如果確認真的還有問題需要問人，Clarification 的 `--context` 必須包含**完整的相關 spec 原文段落**（不是行號＋一句話摘要），讓 PM/RD 收到單子時能直接核對原文，不需要自己再去翻 spec 確認 QAOS 有沒有斷章取義或誤讀。

  如果完整讀完之後，發現規則其實已經很清楚（像 CLR-CASHFLOW-003 這次的情況），就不該開一張「規則是什麼」的開放式問題單——如果矛盾的根源是「spec 明確定義 vs 實際系統行為不符」，該問的是「請重新核實實際畫面」，如果矛盾的根源是「兩份不同 spec 對同一件事的定義本身衝突」，才問「以哪一份為準」。問題的框架要對應矛盾的真正性質。

- **Consequences**:
  - `CLR-CASHFLOW-003` 已撤回（`bin/qaos clarification withdraw`），改開 `CLR-CASHFLOW-004`，問法聚焦在「請重新核實實際畫面」，`--context` 附完整原文段落。
  - Phase 3 的 spec-analyst agent（未來若建立）system prompt 必須包含這條 SOP。
  - 這條規則不影響「Oscar/PM 直接口頭確認即視為 grounded」這個既有原則（見 `PRODUCT-BEHAVIOR-CONFIRMATIONS.md`）——兩者是不同情境：口頭確認是在「spec 沒寫清楚、由人補充」時適用；本 ADR 處理的是「spec 寫得很清楚，但開單前沒讀完整」的情況。

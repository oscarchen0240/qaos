01 · 為什麼做 QAOS

解決什麼問題

QAOS 是一套 QA Agent Operating System：把「讀 Spec → 設計測試案例 / 找 Bug → 驗證 → 核准上線」變成可稽核的產線，而不是一個人（或一顆 AI）憑經驗做完就結案。

人工作業的痛點

  • 一份 Spec 從頭設計測試案例，人工要扮演分析、設計、驗證每個角色，逐一手動完成
  • 判斷過程留在腦中或對話記憶裡，事後很難重建「這條測試案例當初為什麼這樣寫」
  • 沒有結構化關卡，容易把「未經證實的假設」當成「已驗證的規則」寫進測試案例
~2 小時人工扮演一輪角色、跑完一份 Spec 的實測耗時

QAOS 的作法

  • 每一步的產出都是通過 Schema 檢查的 Artifact 檔案，可重放、可 diff、可離線稽核
  • 結構化 Gate（程式碼機械檢查）＋獨立 Validator（語意審查）＋ Human 核准，三關卡都過才算數
  • 任何一條測試案例、任何一個 Bug 都能回溯到 Spec 原文哪一句話

02 · 一句話

QAOS 是什麼

不是 Prompt 聊天機器人接力
而是以 Artifact 為中心的狀態機
✕ 對話記憶傳遞

Agent 之間靠聊天記錄接力，無法重放、無法離線驗證

✓ Artifact 接力

每個 Agent 唯一輸出是通過 Schema 的檔案；狀態轉換必須引用觸發它的 artifact_id

03 · 架構

系統五層

貫穿五層的橫切關注點：Schema Validation、State Machine、Quality Gate、Permission Boundary、Audit Trail。

層內容決策性質
L0 人工層QA 工程師發起 Task、回答 [NEEDS_DECISION]、做 approve / reject / override最終業務決策
L1 協調層Supervisor（LLM 分類/routing）＋ Deterministic Runtime（Schema/State/Gate/Permission，非 LLM）Task 分派、Gate 觸發
L2 代理層8 個 Role Agent，在 Allowed Actions 邊界內產生 ArtifactPropose / Draft / Validate
L3 技能層可重用方法論（test-design、traceability、change-impact…）無決策權，純能力
L4 儲存層Registry / Suite / Bug / Artifact / Execution / Evidence / Approval / Run，皆為版本化檔案唯一事實來源
04 · 核心不變式

系統遵守的規則（節錄 4 條）

INVARIANT 1

沒有 Artifact，就沒有狀態轉換

Workflow 狀態只能由「通過 Schema 驗證的 Artifact」推進，不靠對話記憶。

INVARIANT 2

沒有通過驗證，就不能進 Registry

只有 VALIDATED 以上的 Test Case 才能存在於 Registry。

INVARIANT 3

沒有核准，正式環境就不能變更

Registry ACTIVE 版本、Suite Membership、Bug OPEN 以後狀態，只能由 Human ApprovalDecision 觸發。

INVARIANT 9

業務決策的最終權力屬於人

Agent 只有 propose / draft / analyze / validate / compare / recommend 的權力，不能自己下業務決定。

05 · Workflow（一）

Spec → Test Case：三個角色接力

每個角色只做一件事，把結果交給下一棒；任何一關沒過，退回上一關重做。

1Spec Analyst讀 Spec 原文，整理成結構化的需求與驗收條件
→
2Test Designer依需求設計測試案例，不驗證自己的產出
→
3Test Validator獨立重新審查，判斷是否符合 Spec
→
✓人工核准審查通過後，人按下核准，才正式寫入測試案例庫
任何一關沒過 → 退回上一關重做；同一個問題反覆卡 3 次仍過不了、或 Spec 本身有模糊地帶 → 停下來交給人裁決。
06 · Workflow（二）

Spec → Bug：兩個角色接力

前提：要先有證據（截圖、log），沒有證據這一關直接卡住。

1Bug Analyst比對「Spec 說應該怎樣」跟「證據顯示實際怎樣」，寫成 Bug 草稿
→
2Bug Validator獨立驗證是否成立，順便檢查是不是重複單
→
✓人工核准確認後，人核准 Bug 正式登記，RD 才看得到
沒有證據 → 連第一關都過不了；判斷是重複單、或規則本身有模糊地帶 → 交給人確認。

08 · 限制與收斂

Agent 不能做什麼、怎麼收斂

FORBIDDEN（節錄自 agents/*.yaml）

全域禁止MODIFY_SPEC——Spec 只能由 Human 匯入新版本，沒有任何 Agent 可以改
Test Designer不得 VALIDATE_TESTCASE 並自我宣告 PASS；不得自行配發正式 testcase_id；不得為了湊數量產生重複案例
Test Validator不得 UPDATE_DRAFT（只能在 issue 裡建議）；不得讀取 Test Designer 的推理過程（避免同源偏誤）
Supervisor不得自行設計 Test Case／撰寫 Bug 內容；不得跳過任何 Gate；不得代替 Human 做 approve/reject/override

收斂機制

Schema——唯一結構契約，欄位/型別不對直接擋下，不進入下一步
Gate——結構化 Gate（程式碼機械檢查）+ 語意 Gate（獨立 Validator 產出的 TestValidationReport）
迭代上限——`max_validation_iterations` 預設 3，Validator 連續 FAIL 達上限，Runtime 自動升級為 HUMAN_OVERRIDE，不會無限重試
問人——Spec 模糊、Agent 判斷不出來的分岔，一律走 Clarification / [NEEDS_DECISION]，不准自己腦補
09 · 模型政策

預設 Sonnet，升級是例外

Default
Sonnet

Schema/CLI/workflow、日常 Spec Analyst / Test Designer / Bug Analyst / Regression Curator、Supervisor 分類與 Summary、一般 coding/debug，全部預設 Sonnet。

例外 1 改架構決策——architecture / state machine / permission / agent 邊界 / workflow 依賴衝突
例外 2 Validator 語義失敗達迭代上限（預設 3）仍修不好——只升「這一次修訂」，不是整顆 Agent 換模型
例外 3 跨多檔／跨 workflow 的 architecture audit——例如整體一致性／traceability 斷裂排查
升級權目前在 Human 手上，Agent／Supervisor 不得自行申請 Opus；Spec 模糊、業務假設不明，永遠用 Clarification 問人，不准用換模型解決。
10 · 影子測試

Phase 3 怎麼驗證信任：影子測試

同一份 RequirementModel，讓 Agent 完全獨立重做一次（不給看人工版答案），送進同一套獨立 Validator 機制審查，跟人工版本比較品質。

ROUND 1 · FAIL
系統邊界誤判
假設後台有「申請出金」按鈕（blocker）；assumptions 未誠實揭露；design_technique 系統性亂貼
ROUND 2 · FAIL
同類問題換位重演
修好了 Round 1 的問題，但新藏了一個「稽核=1」假設，跟同批另一條 TC 自相矛盾
ROUND 3 · FAIL → 觸頂
迭代上限，升級人工
Agent 自主抓到並修正一個沒被點名的新問題，但同一類系統性疏漏仍未窮盡排查——觸發 HUMAN_OVERRIDE
關鍵發現：Agent 學會了「修正被明確點名的錯誤」，但沒有「窮盡式自我審查」的能力——同一類問題會換個位置重演。這正是「限制與收斂」那頁規則的由來。
HUMAN_OVERRIDE 不是「整批核准進 Registry」——是人裁決「可以進入下一步」，後續仍要逐條跟人工版本交叉整合（見下兩頁）。
11 · 案例對照

同一個需求，兩份獨立產出

REQ-MEMBER-005（可提領餘額須大於 10 USDT 才可申請出金）：Phase 2 人工版與 Phase 3 Agent 版各自獨立設計了一條邊界值測試案例，寫法差很多。

Phase 2 · 人工版 TC-MEMBER-007 v1
前置條件：「可透過人工存入/人工提出功能（稽核倍數設為 1，避免投注門檻影響判斷），將可提領餘額精確調整為 10.00 USDT」
步驟：僅 1 步——「嘗試申請出金」
test_level: ui_e2eassumptions: 0
Phase 3 · Agent 版 TC-MEMBER-033
前置條件：「後台『申請出金』入口不存在，是前台功能……spec 全文並未給出換算公式……佈置方式：反覆調整人工存入/提出，直到顯示值恰為 10.00 USDT」
步驟：3 步——後台確認顯示 → 登入前台 → 送出申請
test_level: integrationassumptions: 2
兩份都通過各自的結構化 Gate 與 Validator 審查——格式跟邏輯自洽都沒問題，但這不代表任何一份是「完整正確」的最終答案。
12 · 整合邏輯

怎麼判斷關係、合成同一份

深度底線（不能誤判）> 廣度覆蓋（不能留白）> 深度精進（可以慢慢做）
1逐項比對差異同一個需求，兩份寫法哪裡不一樣
→
2拆開判斷對錯分開看每份各自的洞見與缺陷，不比較「哪份整體比較好」
→
3找出共同缺口兩份都沒有的關鍵資訊，問人補齊
→
✓合成最終版採對的部分＋補新資訊，寫成一份比兩邊都完整的 TC

Phase 2 · TC-MEMBER-007

  • ✓ 洞見：後台欄位是唯讀顯示，抓對了觀察起點
  • ✕ 缺陷：「稽核＝1 可避免干擾」是編的，跟同批另一條 TC 自相矛盾——誤判風險，直接丟棄

Phase 3 · TC-MEMBER-033

  • ✓ 洞見：判斷出這是前台驗證行為，系統邊界抓對了，誠實揭露換算公式未知
  • ✕ 缺陷：「反覆調整湊數值」不是精確方法，仍不算真正解法
兩邊都沒有的關鍵資訊——稽核倍數到底怎麼影響餘額——問了 Oscar 才補上「稽核＝0」這個精確機制，合成出 TC-MEMBER-007 v4（2026-09-15 核准）。但這不是故事的結尾——下一頁會看到，連核准過的版本隔天都還被推翻。

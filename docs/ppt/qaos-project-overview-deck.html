01 · What

這套系統在做什麼

02 · Why

為什麼要這樣做

核心好處不是「讓 AI 寫測試比較快」，是讓 AI 產出的東西變得可信任、可審計。

01

可追溯

任何一條測試案例、任何一個 Bug，都能回溯到 Spec 原文的哪一段、哪一句話——不是「AI 說有這條規則」就算數。

02

可稽核

每次狀態變化都留下 Artifact，可重放、可 diff，不靠對話記憶傳遞——事後任何人都能重建「這個決定是怎麼發生的」。

03

擋住 AI 亂寫

結構化 Gate（程式碼機械檢查）+ 語意 Gate（獨立 Validator 審查）+ 人工核准，三關卡都過才能生效——AI 說「這樣沒問題」不算數。

04

規模化不犧牲嚴謹

人工扮演一輪角色跑完一份 Spec 約需 2 小時；Agent 化之後可以規模化產出，但走的仍是同一套關卡，不是抄捷徑。

03 · Architecture

核心架構三個決定

Phase 1 定案、目前仍在遵守的三條架構決策（ADR），是整套系統「AI 產出不能自己說了算」的根基。

ADR-001

Artifact 為中心的狀態機

Agent 之間不靠對話記憶傳遞，唯一輸出是通過 Schema 的 Artifact 檔案；狀態轉換必須引用觸發它的 artifact_id。

ADR-002

Runtime 與 LLM Agent 分工

結構化規則（Gate、狀態轉換、權限、ID 配發）全部由程式碼 `tools/qaos` 執行，不是 LLM 判斷；語意層的審查由獨立 Validator Agent 產出 Artifact，Runtime 只讀取結果欄位。

ADR-003

單一事實來源

測試案例是否在某個回歸套件裡，只查 Suite Membership，不在 TC 上雙寫狀態——避免兩份紀錄互相矛盾。

05 · Phase 2

Phase 2：人工先把地基踩穩

做了什麼

  • `tools/qaos` CLI：狀態轉換、Gate、核准、ID 配發全部程式碼把關
  • Schema 定義每種 Artifact 的必要欄位，寫錯格式直接擋下
  • Phase 3 Agent 還沒做出來之前，由人扮演 Spec Analyst / Test Designer / Test Validator，寫一次性腳本組出 Artifact，走真實 Spec 全流程

產出

  • SPEC-MEMBER-001：18 項需求 → 26 條 ACTIVE 測試案例（本次簡報案例）
~2 小時
人工扮演一輪角色、跑完一份 Spec 的耗時
這個觀察直接促成了 Phase 3：既然人工扮演角色本身就很耗時，把這個角色換成 Agent 才有意義。
06 · Phase 3

Phase 3：Agent 上場，用「影子測試」驗證信任

怎麼做

  • 建立 `qaos-test-designer` Agent，職責跟人工扮演版本一樣：讀 RequirementModel + Spec 原文，產出 Test Case Draft，不自我驗證
  • 影子測試法：同一份 Spec，讓 Agent 完全獨立重做一次（不給看人工版答案），送進同一套獨立 Validator 機制審查，跟人工版本比較品質

結果

  • 三輪迭代：FAIL → 修正被點名的錯誤 → 仍有系統性問題重演 → 觸發 HUMAN_OVERRIDE，交由人工裁決
3 轮
Validator 審查輪次，觸及 `max_validation_iterations` 上限
Agent 學會了「修正被明確點名的錯誤」，但沒有「窮盡式自我審查」的能力——同一類問題會換個位置重演。這是本次影子測試最重要的觀察。
07 · Integration

Phase 2 × 3 怎麼整合：交叉比對，不是二選一

關鍵決策：不是「整批採用 Phase 3」或「維持 Phase 2」二選一，而是逐條交叉比對，取兩邊之中更深入或更完整的處理方式。

08 · Human + Agent

人工在哪裡 · Sub-agent 怎麼分工

人工決策點

核准每一條測試案例上線——ACTIVATE_TESTCASE 是唯一能把 Artifact 變成正式 Registry 條目的動作，只有人能觸發
補充 Spec 沒定義的產品知識——例如「稽核=0 的實際效果」「KYC 已停用的真實顯示」，這些是 Agent 無法憑空推論、必須由人補的 grounding
結構性卡關的裁決——HUMAN_OVERRIDE（Agent 反覆 FAIL）、NEEDS_DECISION（Agent 判斷不出來的分岔）
流程與風險策略方向——整合原則怎麼訂、審查該分幾級，這類「規則本身」的決定

Sub-agent 職責（節錄）

角色職責
Test Designer讀 Spec + RequirementModel，產出 Test Case Draft；不自我驗證
Test Validator獨立 subagent、乾淨 context，重新審查 Draft，不信任 Designer 的自我宣告
Supervisor任務分派、監控迭代次數、觸發斷路器（HUMAN_OVERRIDE），不做語意判斷
Spec Analyst讀 Spec 原文，產出 Requirement / AC，模糊處交人工裁決
關鍵原則：設計者與審查者永遠是不同角色、不同 context——避免「自己改自己的作業、自己打分數」（ADR-002 同源偏誤緩解）。

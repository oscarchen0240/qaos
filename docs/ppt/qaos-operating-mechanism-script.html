QAOS 運作機制

大家好，今天要跟大家介紹 QAOS——QA Agent Operating System。這份簡報會涵蓋幾件事：QAOS 是什麼、怎麼運作、主要的 Workflow 長什麼樣子、Agent 的職責跟限制、還有我們現在的模型使用政策。今天用的範例是我們已經跑過完整流程的 SPEC-MEMBER-001。

01 · 為什麼做 QAOS

解決什麼問題

先講為什麼要做這套系統。QAOS 要解決的核心問題，是把「讀 Spec、設計測試案例、找 Bug、驗證、核准上線」這整個流程，變成一條可以被稽核的產線，而不是靠一個人——或一顆 AI——憑經驗做完就結案。

先看人工作業的痛點：過去要從一份 Spec 設計測試案例，得靠人工扮演分析、設計、驗證每一個角色，一步一步手動做完；判斷過程留在腦子裡或聊天記錄裡，事後很難重建「這條測試案例當初到底為什麼這樣寫」；而且因為沒有結構化的關卡，很容易把「還沒證實的假設」誤當成「已經驗證過的規則」寫進測試案例裡。實測下來，人工跑完一份 Spec 的一輪角色扮演，大概要花兩個小時。

QAOS 的作法是：每一步的產出都變成一個通過 Schema 檢查的 Artifact 檔案，可以重放、可以 diff、可以離線稽核；結構化 Gate、獨立 Validator、跟人工核准，三關都要過才算數；而且任何一條測試案例、任何一個 Bug，都能回溯到 Spec 原文的哪一句話。現在 SPEC-MEMBER-001 已經有 26 條 ACTIVE 測試案例，全部都可以追溯回需求跟 Spec 原文。

02 · 一句話

QAOS 是什麼

用一句話講 QAOS 是什麼：它不是一堆 Prompt 聊天機器人互相接力，而是一個以 Artifact 為中心的狀態機。

差別在哪？如果 Agent 之間靠對話記憶接力，沒辦法重放、也沒辦法離線驗證；但 QAOS 的做法是，每個 Agent 唯一的輸出就是一個通過 Schema 檢查的檔案，狀態要往前推進，必須引用是哪一個 artifact 觸發的。

03 · 架構

系統五層

這是整個系統的五層架構，貫穿五層的橫切關注點是 Schema 驗證、狀態機、品質關卡、權限邊界、還有稽核紀錄。

L0 是人工層，QA 工程師在這裡發起任務、回答模糊地帶的問題、做核准或駁回的決定，這是最終的業務決策。

L1 是協調層，這裡比較特別，是兩個角色合體：Supervisor 是 LLM，負責分類跟路由；但真正的 Schema 檢查、狀態機、Gate、權限判斷，是 L1 裡的 Deterministic Runtime——完全不靠 LLM，是純程式碼。

L2 是代理層，8 個角色 Agent，在被允許的動作範圍內產生 Artifact。L3 是技能層，是可重用的方法論，沒有決策權，純粹是能力。L4 是儲存層，Registry、Suite、Bug 等等，全部都是版本化的檔案，是系統唯一的事實來源。

如果被追問「為什麼 Supervisor 不能自己判斷就好」因為如果連「判斷對不對」這件事本身都是 AI 做的，等於是 AI 自己審自己，審查就沒有意義了——所以刻意把「分類/路由」（可以有彈性）跟「規則把關」（不能有彈性）拆成兩個不同性質的東西。
04 · 核心不變式

系統遵守的規則（節錄 4 條）

這套系統其實遵守著十條不變的規則，這裡挑跟今天主題最相關的四條來講。

第一條，沒有 Artifact 就沒有狀態轉換——工作流程的狀態只能靠通過 Schema 驗證的檔案推進，不能靠對話記憶。

第二條，沒有通過驗證就不能進 Registry——只有 VALIDATED 以上的測試案例才能存在於正式的測試案例庫。

第三條，沒有核准，正式環境就不能變更——不管是測試案例上線、Suite 的成員異動，還是 Bug 狀態往下走，都只能由人的核准動作觸發。

第九條，業務決策的最終權力屬於人——Agent 永遠只能提議、草擬、分析、驗證、比較、建議，不能自己下業務決定。

05 · Workflow（一）

Spec → Test Case：三個角色接力

接下來看主要的 Workflow 怎麼跑，先看 Spec 到測試案例這條線，用角色接力的方式來講。

第一棒，Spec Analyst，讀 Spec 原文，整理成結構化的需求跟驗收條件。第二棒，Test Designer，依照需求設計測試案例，但注意——他不驗證自己的產出。第三棒，Test Validator，用獨立的角度重新審查，判斷符不符合 Spec。最後，人工核准，審查通過之後，人按下核准，這條測試案例才會正式寫進測試案例庫。

任何一關沒過，就退回上一關重做；如果同一個問題連續卡三次還是過不了，或者 Spec 本身有模糊地帶，就會停下來交給人來裁決。

06 · Workflow（二）

Spec → Bug：兩個角色接力

Bug 的流程更短，只有兩個 Agent。但有一個前提：一定要先有證據，像截圖或 log，沒有證據這一關直接卡住，連進到下一步驗證都不行。

第一棒，Bug Analyst，比對 Spec 說應該怎樣、跟證據顯示實際上怎樣，寫成 Bug 草稿。第二棒，Bug Validator，獨立驗證這個 Bug 成不成立，同時檢查是不是重複單。最後一樣要人核准，Bug 才會正式登記，RD 才看得到。

07 · Agent 職責

8 個 Role Agent 一覽

這是系統裡全部 8 個角色 Agent 的一覽表，這份表格是 Phase 1 就定案的正式文件，不是我後來歸納的。

Supervisor 負責任務分類、建立工作流程、路由、觸發 Gate，但不自己設計內容；Spec Analyst 讀 Spec 建立需求；Test Designer 設計測試案例但不驗證自己；Test Validator 獨立審查；Bug Analyst 跟 Bug Validator 是 Bug 那條線對應的角色；Change Impact Analyst 負責 Spec 改版的影響分析；Regression Curator 維護回歸測試套件。

這裡想特別強調一件事：「產出」跟「驗證」永遠是不同的 Agent，沒有一個角色可以同時設計又驗證自己的東西。

08 · 限制與收斂

Agent 不能做什麼、怎麼收斂

這頁講兩件事：Agent 不能做什麼，還有系統怎麼收斂、不會失控。

左邊是真實寫在 Agent 設定檔裡的禁止清單，不是我編的。全域禁止的是修改 Spec 本身——Spec 只能由人匯入新版本，沒有任何 Agent 可以改。Test Designer 不能自己驗證自己、宣告通過，不能自己配發正式的案例編號，也不能為了湊數量產生重複案例。Test Validator 不能修改草稿，只能在意見裡建議；而且刻意設計成不能讀取 Test Designer 的推理過程，只能看草稿本身——這是為了避免「同源偏誤」，因為兩邊都是 LLM，如果互相看得到對方的邏輯，反而容易互相說服。Supervisor 不能自己設計測試案例或寫 Bug 內容，不能跳過任何 Gate，也不能代替人做核准或駁回。

右邊是收斂機制：Schema 是唯一的結構契約，格式不對直接擋下；Gate 分結構化跟語意兩層；有迭代上限，預設 3 次，Validator 連續卡 3 次還過不了，Runtime 會自動升級成人工裁決，不會無限重試；最後，Spec 本身模糊、Agent 判斷不出來的分岔，一律走 Clarification 問人，不准自己腦補。

09 · 模型政策

預設 Sonnet，升級是例外

這是我們現在使用模型的政策。預設是 Sonnet——不管是 Schema、CLI、workflow 這些工程工作，還是日常的 Spec Analyst、Test Designer 這些 Agent 角色，全部預設用 Sonnet。

只有三種例外才會升到 Opus：第一，改架構決策，像是架構、狀態機、權限、Agent 邊界這些；第二，Validator 語義失敗達到迭代上限還修不好，這時候只升「這一次修訂」，不是把整個Agent換掉；第三，跨多個檔案或跨 workflow 的架構稽核——這個意思是，不是在看單一個 Bug 或單一條測試案例，而是回頭檢查整個系統有沒有內部矛盾、有沒有卡死的迴圈、有沒有哪裡的追溯鏈斷掉了，這種需要同時盯著很多檔案、判斷整體一致性的稽核工作，才會用到 Opus。

升級的權力現在在人手上，Agent 或 Supervisor 不能自己申請升級 Opus；如果是 Spec 本身模糊、業務假設不明確，永遠用問人的方式解決，不准用換模型去矇混過去。

這裡順便回答一個常見的問題：為什麼不乾脆讓不同的 Agent 用不同的模型，比如 Test Designer 用一個、Test Validator 用另一個？這個做法通常是想避免「同源偏誤」——擔心兩邊都是同一家模型、盲點也一樣。但我們處理這個問題的方式不是換模型，是用架構解決：Test Validator 本來就是一個乾淨 context 的獨立 subagent 重新審查，而且明文禁止它讀取 Test Designer 的推理過程，只能看草稿本身——這個設計已經把「互相說服」的風險擋掉了，不需要再疊加一層換模型。而且更根本的原因是，現在也還沒有足夠的 run log 數據能證明「分模型」真的比較好，政策的原則是規則要等數據夠了才訂，不能憑感覺先做，所以現在刻意不做這件事。

10 · 影子測試

Phase 3 怎麼驗證信任：影子測試

在講怎麼整合之前，先講一下 Phase 3 是怎麼驗證「這個 Agent 值不值得信任」的——我們做了一次影子測試。

做法是：拿同一份需求模型，讓 Agent 完全獨立重做一次，不給他看人工版的答案，然後送進同一套獨立 Validator 審查，跟人工版本比較品質。

結果是三輪都 FAIL。第一輪，Agent 誤判了系統邊界，假設後台有一個「申請出金」的按鈕，這是編出來的；也沒有誠實揭露假設，設計技巧的標籤也亂貼。第二輪，第一輪的問題修好了，但又藏了一個新的假設——「稽核設為 1」——這個假設剛好跟同一批的另一條測試案例互相矛盾。第三輪，Agent 自己抓到並修正了一個沒被點名的新問題，但同一類的系統性疏漏還是沒有被徹底排查，最後撞到了迭代上限，觸發人工裁決。

這次測試最重要的發現是：Agent 學會了「修正被明確點名的錯誤」，但沒有「窮盡式自我審查」的能力——同一類的問題會換個位置重演。這正是前面「限制與收斂」那些規則的由來。

要注意，人工裁決放行，不等於整批直接核准進 Registry——後面還是要逐條跟人工版本做交叉整合，這就是接下來兩頁要講的。

11 · 案例對照

同一個需求，兩份獨立產出

這裡用一個實際案例，讓大家看清楚兩邊的差異。同一條需求——可提領餘額必須大於 10 USDT 才能申請出金——人工版跟 Agent 版各自獨立設計出來的測試案例，寫法差很多。

人工版，前置條件說「可以透過人工存入/提出功能，稽核倍數設為 1，避免投注門檻影響判斷，把可提領餘額精確調整為 10 塊」，步驟只有一步，就是「嘗試申請出金」。沒有標記任何假設。

Agent 版，前置條件寫得長很多，誠實承認「後台沒有申請出金的入口，這是前台功能」，也承認「spec 全文並沒有給出換算公式」，佈置方式是「反覆調整人工存入提出，直到顯示值剛好等於 10 塊」。步驟有三步，而且標記了兩個假設。

這兩份都通過了各自的結構化 Gate 跟 Validator 審查，格式跟邏輯都沒問題——但這不代表任何一份就是「完整正確」的最終答案。這兩份原始草案本身是歷史紀錄，內容不會變；但先預告一下，等一下到「現況」那一頁，會揭曉一件事——連這次整合出來的「最終版」，隔天都還被推翻過一次。

12 · 整合邏輯

怎麼判斷關係、合成同一份

那怎麼判斷這兩份的關係、把它們合成同一份呢？我們定的原則是：深度底線不能誤判，優先於廣度覆蓋不能留白，優先於深度精進可以慢慢做。

具體的判斷流程是四步：先逐項比對兩份寫法哪裡不一樣；再拆開來看，每一份各自的洞見跟缺陷分開判斷，不是整體比較「哪份寫得比較好」；然後找出兩份都沒有的關鍵資訊，這個要問人補齊；最後才合成最終版本。

拿剛剛那個例子來看：人工版的洞見是抓對了「後台欄位是唯讀顯示」這個觀察起點，但缺陷是「稽核等於 1 可以避免干擾」這個假設是編的，跟同一批另一條測試案例自相矛盾，這是會讓人誤判的風險，直接丟棄。Agent 版的洞見是判斷對了「這是前台驗證行為」的系統邊界，而且誠實揭露了換算公式未知；但缺陷是「反覆調整湊數值」並不是一個精確的方法，也不算真正的解法。

最後，兩邊都沒有的關鍵資訊——稽核倍數到底怎麼影響餘額——這個問了 Oscar 才補上「稽核等於 0」這個精確機制。合成出來的版本，在 9 月 15 號核准上線，等於 Agent 版的系統邊界判斷，加上人工版的簡潔步驟結構，再加上新問到的精確佈置方法。

但這不是故事的結尾。這套整合方法論——拆開看洞見跟缺陷、找出共同缺口問人補齊——本身是對的，只是有時候不會一次到位。下一頁會看到，隔天這條測試案例又發生了什麼事。

13 · 現況

現在進度與下一步

最後看現在的進度。SPEC-MEMBER-001 現在有 26 條 ACTIVE 測試案例，其中 14 條是經過 Phase 2 跟 Phase 3 交叉整合修訂過的。Phase 2 的骨架已經拿真實 Spec 跑通，不只是單元測試而已；Phase 3 現在只有 Test Designer 這個角色真正 Agent 化，並且完成了影子測試驗證，其他角色目前還是由人工扮演。

剛剛答應大家要揭曉的事情，就是這個：TC-MEMBER-007 這條測試案例，核准之後隔天又被推翻了一次。第一版，人工版的前置條件假設「稽核設為 1 可以避免干擾」，結果跟同一批另一條測試案例自相矛盾。9 月 15 號整合之後的版本，改用「稽核等於 0 的單筆人工存入提出」，精確把「可提領餘額」佈置到 10.00 或 10.01，門檻是「大於 10、不含 10」，這個版本當天就核准上線了。結果這個核准過的版本後來又被推翻了：真正的門檻，其實只看「會員實際填寫的提領金額本身」是否大於等於 10、含 10，跟可提領餘額的精確數值、跟出金手續費完全無關。這樣一來，測試設計反而變得更簡單，不需要再精密佈置餘額了。

我想特別強調這件事的意義：這不是失敗案例，是系統設計本來就支援的正常流程。核准不代表「封版」，只代表「目前資訊下的最佳版本」；只要有新的確認資訊出現，任何一條 ACTIVE 的測試案例都可以透過修訂流程重新走一次 Gate、獨立 Validator、人工核准，把它更新到更正確的狀態。

接下來的規劃：Phase 4 是 Workflow 層，處理 Spec 變更影響、回歸套件、還有人工測試案例納管；Phase 5 是自動化，串接 CI、自動執行測試；Phase 6 是更進階的協作，Agent 並行、Supervisor 自主重新規劃。今天的簡報就到這裡，謝謝大家。

## REQ-SITELIST-001 站台類型二擇一且建立後不可修改

**需求**：每個站台的站台類型為線上或機台二擇一；建立後不可修改

- 類型 constraint · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§站台類型與機台專屬欄位 + §業務規則-站台類型鎖定　引句：「每個站台的「站台類型」為線上 / 機台，二擇一；建立後不可修改」
- 驗收條件：
  - 0011：給定 新增站台；當 根層站台選擇線上或機台；則 系統接受並依所選類型建立
  - 0012：給定 站台已建立；當 進入編輯畫面檢視站台類型欄位；則 欄位為唯讀（置灰），無法修改
  - 0013：給定 站台已建立；當 嘗試透過編輯送出不同的站台類型值；則 系統不得變更站台類型
- 不符合時系統怎麼做：spec 有寫——編輯彈窗顯示為唯讀（置灰）即為拒絕修改的方式
- 對應 TC：TC-SITELIST-002 v1, TC-SITELIST-131 v1, TC-SITELIST-065 v1, TC-SITELIST-064 v1, TC-SITELIST-066 v1, TC-SITELIST-132 v1, TC-SITELIST-001 v1

## REQ-SITELIST-002 站台類型由主站台決定，子站台強制繼承

**需求**：站台類型於主站台（根層）選定，子站台一律與主站台同類型，不可個別選擇；例外：當上層站台為 admin（最上層根站台）時，此強制跟隨規則不適用——底下子站台可自由選擇機台或線上類型，核心貨幣依所選類型連動建立（此為 PM 最終決定，已開發完成並上線，非待定或實驗性設計；正式確認見 CLR-SITELIST-010，spec.md 原文尚未反映此例外，屬 spec 文件落後於實際已上線行為的已知落差）

- 類型 constraint · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§站台類型與機台專屬欄位 + §業務規則-站台類型隨主站台　引句：「站台類型於主站台（根層）選定，子站台一律與主站台同類型、不可個別選擇」
- 驗收條件：
  - 0021：給定 上層站台為機台類型；當 新增子站台；則 子站台的站台類型固定為機台，UI 不開放選擇
  - 0022：給定 上層站台為線上類型；當 新增子站台；則 子站台的站台類型固定為線上，UI 不開放選擇
  - 0023：給定 上層站台為 admin（最上層根站台）；當 新增子站台；則 站台類型欄位可自由選擇機台或線上，不強制跟隨 admin 自身的站台類型；核心貨幣依所選類型連動建立（例如選機台則連動啟用 TWD）。此連動建立與「鏈上錢包管理」（platform級幣種出入金啟用/禁用的風險控管開關）完全無關、不互相依賴——依 CLR-SITELIST-011 之陳述兩者為互不相依的獨立概念，但獨立Validator審查指出CLR-011的稽核強度弱於本文件其他CLR案例（同帳號短時間內自行提出/回答/套用、無第三方可查核來源），建議取得更具外部可查核性的來源後再升級為確定規則；對應TC已標記exploratory，核心貨幣連動建立不需要、也不會檢查鏈上錢包管理的任何狀態
- 不符合時系統怎麼做：spec v0.4 沒寫 → **PM 已回答**（見下）
- ✅ PM 回答（CLR-SITELIST-001）：後端也會拒絕：若透過 API 帶入與上層站台不同的站台類型，後端會擋下，不只是前端唯讀限制。
- ✅ PM 回答（CLR-SITELIST-010）：admin 例外規則為 PM 最終決定，非資料錯誤或臆測：根層站台（無上層站台）建立時，型別可自由選擇（機台或線上），核心貨幣依所選類型連動建立，不受REQ-SITELIST-002子站台強制跟隨規則約束。此為PM已定案且已開發完成上線的產品行為，非待定或實驗性設計。spec.md原文尚未反映此例外，屬spec文件落後於實際已上線行為的已知落差。
- ✅ PM 回答（CLR-SITELIST-011）：鏈上錢包管理與站台核心貨幣是兩個完全不同、互不相依的概念。鏈上錢包管理管理的是「此平台整體能使用的幣種有哪些」，啟用/禁用代表該幣種能否出入金，目的是作為平台出問題時的即時止損開關（platform級風險控管，不分站台）。站台的核心貨幣則是站台建立時依站台類型連動決定的設定欄位（例如機台類型連動TWD），屬SITELIST頁面自身的站台設定，跟鏈上錢包管理的啟用狀態無關、不互相依賴。因此AC-SITELIST-0023「不需admin自身的鏈上錢包管理預先啟用該幣別」這句話，本質是在說明這兩個系統彼此獨立、互不閘門——站台核心貨幣的連動建立不需要、也不會去檢查鏈上錢包管理的任何狀態。
- ✅ PM 回答（CLR-SITELIST-012）：修正CLR-SITELIST-011：鏈上錢包管理與站台核心貨幣不是「完全無關」，而是「性質不同但有連動關係」。(1)鏈上錢包管理是每個站台各自獨立一份的設定，管理該站台能使用的幣種之啟用/禁用（代表能否出入金），目的是平台/站台出問題時的即時止損開關，此開關可在建立後隨時調整。(2)站台核心貨幣則是站台建立時就依類型決定的corecurrency欄位，不可更改、也不能在後台關閉，屬於站台建立當下就定案的不可變屬性。(3)兩者的連動關係：新站台建立時，核心貨幣連動建立的同時，會自動在該站台自己的鏈上錢包管理啟用對應幣別（例如機台類型建立時TWD會自動連動啟用）；此連動不需要admin自身的鏈上錢包管理預先啟用對應幣別（即不依賴上層/admin的狀態，是該新站台自己獨立產生的初始啟用狀態）。此修正有獨立既有證據佐證：TC-SITELIST-063（ACTIVE，建立時間早於本次CLR-010/011/012的討論）已完整斷言此機制，並非本次對話中臨時產生的說法。
- 對應 TC：TC-SITELIST-130 v1, TC-SITELIST-063 v1, TC-SITELIST-003 v1, TC-SITELIST-004 v1, TC-SITELIST-064 v1, TC-SITELIST-068 v1, TC-SITELIST-196 v1, TC-SITELIST-067 v1, TC-SITELIST-134 v1, TC-SITELIST-133 v1

## REQ-SITELIST-023 刪除操作不可復原

**需求**：原描述「刪除操作不可復原」，惟刪除功能經 CLR-SITELIST-009 確認前後端皆不提供（見 REQ-SITELIST-022），此需求描述的情境（刪除已執行、事後不可復原）不會發生，原先「刪除有子站台的站台時系統如何處理子站台」的疑慮亦隨之消失（因為刪除永遠不會執行）。本條保留僅供追溯，不作為 grounded TC 設計依據

- 類型 constraint · 行為 rejection · 風險 high · 狀態 ACTIVE
- spec 位置：§操作/刪除站台 + §業務規則-刪除確認　引句：「⚠️ 刪除操作不可復原」
- 驗收條件：
  - 0231：給定 站台已被刪除；當 嘗試尋找該站台或復原；則 系統無提供復原機制，該站台資料不再存在
- 不符合時系統怎麼做：spec v0.4 沒寫 → **PM 已回答**（見下）
- ✅ PM 回答（CLR-SITELIST-007）：機台類型站台不提供刪除操作，只能停用（暫停／關閉）；不會出現在確認刪除的流程裡。（原問題「有子站台時如何刪除」對機台類型不再適用，因為機台本來就不能刪除；線上類型站台若帶有子站台時的刪除行為，本次回覆未涵蓋，另開單追蹤）
- ✅ PM 回答（CLR-SITELIST-008）：不論線上或機台類型，站台皆不支援刪除功能，僅能暫停或關閉（停用）。此為對 spec 原文「刪除站台」一節（點擊列表刪除、二次確認、不可復原）的重大修正——該流程實際上不存在於任何站台類型，CLR-SITELIST-007 先前確認的「機台類型不可刪除」應擴大為「所有類型皆不可刪除」。
- ✅ PM 回答（CLR-SITELIST-009）：已確認：前端與後端皆拒絕刪除站台，不論線上或機台類型皆同（與 CLR-SITELIST-008 的結論一致，非誤答）。原因是刪除站台會影響站台樹狀結構（子站台歸屬、上下層關係），故刻意不提供刪除功能，僅能暫停／關閉（停用）。spec.md v0.4 原文「刪除站台可正常執行」一節與此結論牴觸，屬 spec 需修正的錯誤敘述，非目前產品行為。
- ⚠ 歧義（major）：刪除有子站台的站台時，系統應如何處理其子站台？spec 未提及【已解決】已由 CLR-SITELIST-009 確認為 moot：刪除功能本身前後端皆不提供，此疑慮不會發生　可能解讀：阻擋刪除，需先刪除或移轉所有子站台 / 串聯刪除所有子站台（含孫層） / 子站台自動上移為根層或掛到被刪站台的上層
- 對應 TC：TC-SITELIST-043 v1, TC-SITELIST-042 v1, TC-SITELIST-044 v1

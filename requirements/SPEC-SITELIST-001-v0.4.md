## REQ-SITELIST-001 站台類型二擇一且建立後不可修改

**需求**：每個站台的站台類型為線上或機台二擇一；建立後不可修改

- 類型 constraint · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§站台類型與機台專屬欄位 + §業務規則-站台類型鎖定　引句：「每個站台的「站台類型」為線上 / 機台，二擇一；建立後不可修改」
- 驗收條件：
  - 0011：給定 新增站台；當 根層站台選擇線上或機台；則 系統接受並依所選類型建立
  - 0012：給定 站台已建立；當 進入編輯畫面檢視站台類型欄位；則 欄位為唯讀（置灰），無法修改
  - 0013：給定 站台已建立；當 嘗試透過編輯送出不同的站台類型值；則 系統不得變更站台類型
- 不符合時系統怎麼做：spec 有寫——編輯彈窗顯示為唯讀（置灰）即為拒絕修改的方式
- 對應 TC：（尚無）

## REQ-SITELIST-002 站台類型由主站台決定，子站台強制繼承

**需求**：站台類型於主站台（根層）選定，子站台一律與主站台同類型，不可個別選擇

- 類型 constraint · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§站台類型與機台專屬欄位 + §業務規則-站台類型隨主站台　引句：「站台類型於主站台（根層）選定，子站台一律與主站台同類型、不可個別選擇」
- 驗收條件：
  - 0021：給定 上層站台為機台類型；當 新增子站台；則 子站台的站台類型固定為機台，UI 不開放選擇
  - 0022：給定 上層站台為線上類型；當 新增子站台；則 子站台的站台類型固定為線上，UI 不開放選擇

- ✅ PM 回答（CLR-SITELIST-001）：後端也會拒絕：若透過 API 帶入與上層站台不同的站台類型，後端會擋下，不只是前端唯讀限制。

## REQ-SITELIST-003 機台專屬欄位僅機台類型顯示

- 不符合時系統怎麼做：spec 有寫——顯示與否即為規則本身，無額外拒絕情境

## REQ-SITELIST-011 可見範圍依角色

**需求**：Admin 可見全部站台；站長僅可見自身所屬站台及其所有子站台，不包含平行或上層站台

- 類型 security · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§角色與權限 + §階層結構與逐層瀏覽-根層顯示　引句：「可見站台範圍 | 全部站台 | 僅自身站台及所有子站台（不含平行或上層站台）」
- 驗收條件：
  - 0111：給定 以 Admin 登入；當 檢視站台列表根層；則 顯示所有無上層站台的根層站台
  - 0112：給定 以站長登入；當 檢視站台列表；則 預設顯示自身所屬站台，且僅能看到自身及其所有子站台
  - 0113：給定 以站長登入；當 嘗試瀏覽平行站台或上層站台；則 系統不得顯示該站台資料
- 不符合時系統怎麼做：spec v0.4 沒寫 → **PM 已回答**（見下）
- ✅ PM 回答（CLR-SITELIST-004）：以「三個角色的關係」權限範圍圖為準（同 CLR-PLATFORMRULE-001 附圖）：範圍由所屬站台決定，不是角色本身。站長掛在主站台 A → 可見範圍＝A 及其子樹；操作員只看自身場館。層級可指派範圍：管理員可指派管理員/站長及以下，站長只能指派站長以下，操作員不可指派。站長嘗試存取平行或上層站台（含直接以站台 ID 呼叫查詢），依此範圍模型應無法取得資料。
- 對應 TC：（尚無）

## REQ-SITELIST-012 新增站台時上層站台欄位權限

**需求**：Admin 新增站台時可自由選取上層站台（留空為根層）；站長新增站台時上層站台固定為當前所在層，不可修改

- 類型 security · 行為 constraint · 風險 high · 狀態 ACTIVE
- spec 位置：§角色與權限 + §操作/新增站台　引句：「上層站台 | 自動帶入當前所在層；可搜尋改選任意站台…留空為根層 | 預帶當前所在層，唯讀不可修改」
- 驗收條件：
  - 0121：給定 以 Admin 登入；當 新增站台，搜尋並改選上層站台；則 系統接受所選的任意站台為上層站台；留空則建立為根層站台
  - 0122：給定 以站長登入；當 新增站台；則 上層站台欄位唯讀，固定顯示當前所在層，無法改選
- 不符合時系統怎麼做：spec v0.4 沒寫 → **PM 已回答**（見下）
- ✅ PM 回答（CLR-SITELIST-005）：已修改：站長不可自由選取上層站台，需點進不同子站後新增站台，上層站台選單會自動帶入其選擇的站台；後端已拒絕（不接受繞過前端指定其他上層站台）。此前 RD 回報的「直接呼叫 API 仍會成功」風險已修復。
- ⚠ 歧義（major）：「站長固定為當前所在層，不可修改」是否為前端限制、還是後端也必須驗證並拒絕不同的上層站台？spec 未區分前後端層級　可能解讀：僅前端限制即符合規格（後端不需額外驗證） / 前後端皆須拒絕，後端也必須驗證並拒絕站長帶入非當前層的上層站台
- 對應 TC：（尚無）

## REQ-SITELIST-015 模板必填規則（切換開通）

**需求**：新建站台時模板可留空；當狀態切換為「開通」時，模板為必填，否則阻擋儲存並提示錯誤

- 類型 constraint · 行為 rejection · 風險 high · 狀態 ACTIVE
- spec 位置：§模板設定/填寫規則 + §業務規則-模板（切換開通）　引句：「當狀態切換為「開通」時，模板為必填，否則阻擋儲存並提示錯誤」
- 驗收條件：
  - 0151：給定 新建站台；當 模板留空並送出；則 系統接受建立（狀態為待開通）
  - 0152：給定 站台狀態非開通，模板為空；當 將狀態切換為開通並儲存；則 系統阻擋儲存，顯示錯誤提示

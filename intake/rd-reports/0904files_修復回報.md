## bug單_ZZAA00264上層站台異常可自由選取

狀態: 已修復, 待驗

### 問題

站長帳號 ZZAA00264 新增站台時,「上層站台」是可互動的下拉選單, 可以搜尋改選任意站台。
其餘站長帳號 (ACAA00263, YAAA00265) 都正確鎖成唯讀純文字。

### 原因

前端判斷「是不是管理員」時, 用的是後端回的「登入者所屬站台是不是 admin 站台」,
而不是登入者的角色。

ZZAA00264 是站長, 但他被指派在 admin 站台上, 所以這個判斷回 true, 前端就把他當成管理員。
其他站長掛在中間層或深層站台, 判斷回 false, 行為才正常。

依 PM 2026-09-04 確認的權限原則: 可見範圍由所屬站台決定, 權限層級由角色決定, 兩者是分開的。
被指派在 admin 只會讓可見範圍變成全平台, 不會讓權限升級成管理員。

### 修改

把上述兩個概念拆開:

- 欄位可否編輯 -> 一律改看角色 (管理員為 role-000)
- 站台樹的最上界 (判斷哪些站台算主站台) -> 維持看所屬站台, 不受角色影響

### 影響範圍

ZZAA00264 這類「站長但被指派在 admin」的帳號, 以下五項會從管理員權限收回站長權限:

- 上層站台: 可搜尋改選 -> 唯讀純文字, 顯示 `admin`
- 站台移轉 (編輯站台時直接改上層): 可操作 -> 關閉
- 站台狀態: 全部可選 -> 僅可選「暫停」「關閉」
- 模板欄位: 可編輯 -> 新增時不顯示, 編輯時唯讀
- 可見範圍: 不變, 仍是全平台

管理員帳號與其他站長帳號行為完全不變。

### 驗證重點

- ZZAA00264 登入, 新增站台, 確認上述五項都正確
- **真正的管理員帳號要重點測**: 上層站台, 站台移轉, 狀態, 模板四項都應維持可操作。
  若管理員也被鎖住, 表示該帳號在後端的角色不是 role-000, 要回報給 RD 確認
- ACAA00263 (Arcade 站長), YAAA00265 (SpringKyle 站長): 應完全不受影響, 維持原本的正確鎖定
- 三個帳號都測「根層新增」與「鑽入子站台後新增」兩種情境

### 備註

- bug 單提到要一併處理的「發現三」(admin 層級類型繼承錯誤) 屬另一張單, 不在本次範圍
- 前端只是不給操作, 真正的權限把關仍須後端。直接呼叫建立站台 API 帶別的上層站台, 目前仍會成功

## bug單_上層站台選單異常與根層機台建立受阻

狀態: 發現二已修復待驗; 發現一, 三, 四無須另外修改, 列為待驗

本單四個發現, 比對後只有發現二需要動程式碼, 其餘三項已被先前的修正涵蓋。

### 發現一: 上層站台看似可互動, 實際不能改

狀態: 已修復, 待驗 (不在本次改動範圍)

站長的上層站台欄位目前已是唯讀純文字 (灰底方框, 沒有下拉箭頭), 不是下拉選單, 與 spec 一致。
bug 單自己在 2026-09-04 的補充驗證也確認欄位確實為唯讀。

單內提到的 ZZAA00264 例外, 已獨立修復, 詳見本檔上一節。

### 發現二: 下拉的「根層」選項互動後消失

狀態: 已修復, 待驗

**問題**

管理員新增站台時, 上層站台欄位一開啟顯示「－ 根層（無上層站台）」, 看起來已經選好了;
但點開下拉清單裡根本沒有這個選項, 所以只要選了任何一個站台, 就再也選不回根層,
只能關掉整個視窗重開。

**原因**

根層選項在先前開發「站台移轉」功能時被整段註解掉了。

當時拿掉的理由本身是對的: 移轉 API 規定必須指定一個目標站台, 沒辦法把站台移到根層。
但這個限制被連坐套用到「新增」上 —— 而建立站台的 API 本來就允許不指定上層站台。
結果是編輯 (移轉) 的限制誤傷了新增。

**修改**

根層選項還原, 但只在「新增」時提供; 「編輯」時不提供, 因為移轉 API 確實不支援。
同時在程式碼註記兩支 API 的差異, 避免日後又被整段拿掉。

### 發現三: admin 層級不該套用類型繼承

狀態: 已修復, 待驗 (併在同批未提交的調整內)

上層站台選 admin 時, 核心貨幣會自動繼承 admin 的 USDT, 導致無法在 admin 底下建立
第二個機台類型站台 (與現存的 Arcade 同層)。

現行邏輯已把 admin 平台站台視為站台樹的最上界, 掛在它底下的一律當成主站台, 
站台類型與核心貨幣皆可自行選擇, 不繼承 admin 的值。

### 發現四: 鑽入 admin 後選不到根層

狀態: 已修復, 待驗 (與發現二同源, 同一個修改一併解決)

鑽入 admin 之後, 上層站台預設帶 admin, 而清單裡沒有根層選項可以切回去, 
所以看起來像是「換頁之後根層就消失了」。發現二修好後這項一併恢復。

### 影響範圍

- 只影響**管理員**。上層站台下拉本來就只有管理員看得到, 站長是唯讀純文字, 完全不受影響。
- 編輯站台時的行為完全不變, 仍然沒有根層選項 (移轉 API 不支援)。

### 驗證重點

- 管理員登入, 最外層「站台列表」點「＋ 新增站台」: 下拉應看得到「－ 根層（無上層站台）」
- 選一個站台之後再點開下拉, 根層選項**應該還在**, 且可以選回去 (這是本次主要修正點)
- 鑽入 admin 之後再點「＋ 新增站台」: 根層選項應同樣看得到, 不會消失
- 編輯任何站台時點開上層站台下拉: **不應該**出現根層選項 (這是正確行為, 不是 bug)
- 上層選 admin 時, 站台類型應可自由選「線上」或「機台」, 核心貨幣跟著類型走, 不會被鎖成 USDT
- 實際在 admin 底下建立一個機台類型站台 (與 Arcade 同層), 確認建得出來
- 站長帳號: 上層站台仍為唯讀純文字, 行為與先前一致

### 備註

- 發現一的「唯讀樣式容易誤導操作者」屬視覺調整, 未處理; 若要調整需另外提出
- 「根層」選項保留與否經確認後決定保留: spec 明訂 Admin 可留空建立根層站台

## bug單_子站台類型與核心貨幣顯示錯誤

狀態: 主因已修復, 但 QA 重測的環境尚未帶上此修正; 另有一項體感缺口未處理

### 問題

機台站台底下新增子站台時,「站台類型」與「核心貨幣」顯示錯誤, 有兩種樣貌:

- 模式 A: 「線上」被選中,「機台」灰階不可點; 核心貨幣顯示 USDT (應為 TWD)
- 模式 B: 「線上」「機台」皆可點擊, 皆未鎖定; 核心貨幣完全空白

### 原因

QA 推論的根因正確: 前端沒有依所選的上層站台重新查詢, 而是帶入了登入者自身站台的資料。

舊版是用扁平樹 (query-site-main-and-childrens) 往上找根站台, 但那支 API 只涵蓋到直屬子站
那一層, 於是依上層站台的深度不同, 走進兩條不同的錯誤分支:

- 上層站台在扁平樹裡找得到 -> 往上找根站台時取到登入者自己的主站台 -> 帶回線上/USDT (模式 A)
- 上層站台在扁平樹裡找不到 (深度 2 以下) -> 誤判成「沒有上層」即主站台層 -> 類型解鎖,
  核心貨幣變成下拉且無預設值 (模式 B)

補充給 QA: 單內推測模式 A/B 的差異「可能與查詢逾時或 race condition 有關」, 實際不是。
兩者是同一個根因下、因上層站台深度不同而走進的兩條錯誤分支, 與時序無關。

### 修改

已改為直接查詢所選上層站台本身的資料, 站台類型與核心貨幣皆取自該筆,
不再自行往上找根站台。兩條錯誤分支都不再成立。

### 為什麼重測仍然重現

此修正在 QA 重測當下還是未提交的本機改動, 尚未合併到 QA 測試用的環境分支,
因此重測到的仍是舊版行為。**需重新部署後再驗一次**, 這是本項最優先的動作。

### 未處理: 繼承值查詢中或查詢失敗時的呈現

上層站台的資料是非同步查詢。在它回來之前, 以及查詢失敗時, 畫面會顯示前一個殘留的
站台類型 (通常就是「線上」) 並維持鎖定, 核心貨幣顯示 --。

也就是說, 這個中間狀態**看起來與模式 A 一模一樣**。查詢快時只是一閃而過,
但若請求變慢或失敗, 畫面會停在一個看似確定的錯誤值上, 且沒有任何提示。

此項尚未修改, 待決定是否要補。若要補, 方向是: 繼承值尚未確定時兩張類型卡都不高亮
(維持鎖定), 核心貨幣顯示載入中; 查詢失敗時明確告知取得失敗, 不靜默顯示線上。

### 驗證重點

- **先確認測試環境已帶上本次修正再開始測**, 否則會重現舊行為
- 母站台視角新增站台, 上層選 Arcade (機台/TWD): 類型應為「機台」已選中,「線上」灰階;
  核心貨幣應顯示「TWD（繼承主站台核心貨幣）」
- ACAA00263 於 Arcade 底下新增子站台: 應正確 (此情境舊版本來就是對的, 用於對照)
- ACAA00263 鑽入 Arcade 底下的子站台「as」後新增站台: 這是舊版出錯的情境, 應同樣正確顯示機台/TWD
- 在同一個新增視窗內反覆切換上層站台 (線上站台與機台站台來回切), 類型與幣別應每次都跟著變
- 送出後回頭編輯剛建立的子站台, 確認實際值與新增時顯示的一致

### 備註

- 後端資料從頭到尾都是正確的, 本項純屬新增視窗內的顯示邏輯, 與後端無關 (與 QA 判斷一致)

## 附錄: 待PM確認_站長最高權限定義疑問 (已結案, 非 bug 單)

不需修改程式碼。此文件是本批修正的權限模型依據, 記錄於此供日後查閱。

### PM 確認的權限模型

三層角色, 由高到低: 管理員 > 站長 > 操作員 (機台場館專用)。

「範圍由所屬站台決定, 不是角色本身」, 可見範圍與權限層級是分開的兩件事:

- 可見範圍 (看得到哪些站台) -> 由「被指派在哪個站台」決定
- 權限層級 (能做什麼操作) -> 由「角色」決定, 不論指派在哪裡都不會升級

本批第一項修正 (ZZAA00264) 就是照這個模型做的: 把原本混在一起的兩個概念拆開,
欄位權限一律看角色, 只有站台樹的上界仍看所屬站台。

### 順帶查核的兩點

- **文件仍有過時描述**: `前言與通用規則_spec_v01.md` 第 28 行仍寫著「站長 = 擁有後台最高權限的
  管理者」, 交付包 20260821 與 20260904_v2 兩份都有。PM 已確認此描述過時, 應以功能 spec 的
  三層模型為準。這是 PM 交付的 spec, 未逕行修改, 建議回報請 PM 於下一版更正,
  以免後續開發或測試再次依此誤判。
- **操作員無此頁權限**: 子站台管理選單僅開放管理員與站長 (role-000, role-100),
  操作員看不到此頁, 因此本次改動不影響操作員, 也沒有因為改依角色判斷而產生新的權限缺口。
